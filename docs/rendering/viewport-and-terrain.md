# Viewport, Camera & Zone Terrain

> NeoVeldrid graphics context, viewport windows, camera, and the zone terrain renderer (Phases 5A and 5B), plus the three-tier frame composition. Status and open work: [ROADMAP.md](../../ROADMAP.md) and GitHub Issues.

## Graphics context and viewport windows (Phase 5A)

- Graphics through [NeoVeldrid](https://github.com/jhm-ciberman/neo-veldrid) and NeoVeldrid.SPIRV 1.2.1 (#262, 2026-10-05), the maintained fork of Veldrid 4.9.0 with the same API (namespace `NeoVeldrid`). It has no Metal backend: macOS runs Vulkan through the bundled MoltenVK. `Veldrid.ImGui` was dropped unused; Tier 3 uses Hexa.NET.ImGui with our own NeoVeldrid renderer (chosen in #263, built in #30: [Tier 3 overlays and the performance overlay](#tier-3-imgui-overlays-and-the-performance-overlay-30)).
- Avalonia `NativeControlHost` cross-platform viewport control (`VeldridViewportControl`) supporting Windows (`HWND`), Linux (`X11`/`Wayland`), and macOS (`NSView`)
- Multi-backend auto-selection (Direct3D 11 on Windows, Vulkan on Linux/Windows, Vulkan through MoltenVK on macOS; a saved `Metal` preference from before #262 selects Vulkan). OpenGL is not a backend choice ([#390](https://github.com/jimmy58663/GordianXI/issues/390), maintainer decision 2026-10-13): it was offered in Settings but never implemented, so it silently ran the automatic choice (found in the #30 test: the overlay rightly said Direct3D11), and nothing needs it (macOS runs Vulkan through the bundled MoltenVK; unverified on real hardware, [#392](https://github.com/jimmy58663/GordianXI/issues/392)). It is no longer in the drop-down; a saved `OpenGL` setting loads as Auto with a one-time log notice, like the old `Metal` value. Settings > Display shows the backend that is really running, with the reason when it is not the selected one (`ViewportViewModel.BackendStatus`, `SharedGraphicsDevice.FallbackNote`; also logged as a warning when the shared device is created).
  - **Reopen to apply ([#319](https://github.com/jimmy58663/GordianXI/issues/319), [#320](https://github.com/jimmy58663/GordianXI/issues/320)).** The backend is chosen once, when the first viewport window creates the shared device; there is no live switching (rare, costly to rebuild, and it would fight the one shared device). Settings > Display says so ("A change applies when the viewport window is reopened"). `SharedGraphicsDevice` remembers the preference it was created for (`RequestedPreference`); `SharedGraphicsDevice.ReopenNeeded(selected, requested, running)` is true when the selection differs from that and is not already what runs, so a fallback (Vulkan asked, Direct3D 11 running) is not flagged for ever and Auto is satisfied by whatever runs. `ViewportViewModel.BackendReopenNeeded` (refreshed by the windows' 250 ms tick, on a backend change and after a reopen) shows the **Reopen viewport to apply** button in Settings and on the floating pill (`ReopenViewportCommand`). `ViewportWindowManager.ReopenViewports` closes every pop-out and the main window, waits (up to 5 s) for the last window to release the shared device, then reopens the main window with its active tab and each popped-out character's pop-out; windows return to their saved placement (`WindowPlacementManager` keys) and the sessions stay connected. A pop-out's drop-down sets the backend on the main view model (`SwitchTarget`), so one choice applies to every window.
- One `GraphicsDevice` per process shared by every viewport window, one swapchain per window, a render loop per window that throttles unfocused windows and stops for hidden ones, and a GPU zone cache: see [Shared device, render throttling and zone cache](#shared-device-render-throttling-and-zone-cache-300-301-322)
- Verification test scene: textured spinning 3D test cube and color gradient clearing to confirm GPU pipeline integrity
- **Decoupled 3D Rendering Window (`ViewportWindow`) & Lifecycle Coordinator (`ViewportWindowManager`):**
  - Gameplay graphics run in a separate hardware-accelerated window, preserving `MainWindow` as the central Control Panel (profiles, packet inspection, state diagnostics, chat console, and display settings).
  - Three display modes: **Borderless Window** (default, borderless work area alignment), **Windowed** (movable & resizable with min dimension safeguards), and **Fullscreen** (`WindowState.FullScreen`, toggleable via `F11`).
  - Character tab switcher styles (`ViewportTabStyle`, saved as `ViewportSettings.SelectedTabStyle`; a change in Settings applies at once, to pop-out windows too). See [Multi-box](#multi-box-windows-switching-and-input-154) for how each behaves.
  - **Pop-Out (`⧉`):** a character gets its own `ViewportWindow` (windowed, its own view model with `IsPrimary = false` and `SwitchTarget` = the main view model); the main window moves on to the next character not popped out. When there is none (the only character, or the last one not popped out), the tear-off opens no window: the main window switches to **Windowed** and keeps the character (nothing changes when it is already windowed; `ViewportViewModel.RequestPopOut`). Before, the main window kept drawing the same world as the new pop-out, and every per-frame entity update ran twice (animation, movement playback, head turns: round 3 test D23, [#307](https://github.com/jimmy58663/GordianXI/issues/307)); the maintainer chose this over making each entity update run once per frame, since it also avoids drawing one world twice. Entity animation additionally advances once per frame in wall time whatever draws it (`EntityAnimationState.ClaimFrameTime`). A popped-out character stays in the main window's switchers; choosing it (click or Ctrl+Tab) brings its window to the front. All windows draw on the one shared `GraphicsDevice`, each with its own swapchain ([#300](https://github.com/jimmy58663/GordianXI/issues/300)).
  - **Picture-in-Picture (PiP) deck:** cards for up to `MaxPipStreams` (5) background characters with 1-click `⇄` promotion into the main view and `⧉`. Each card shows a live render of that character's scene (#302, below) with name, job and HP; Settings > Display can turn the thumbnails off (`LivePipThumbnails`), leaving the status text.

- **Lobby and zoning (#32, #36).** While a character lobby is open (`ViewportViewModel.Lobby`) the viewport draws it instead of the active session (`LobbyFrameRenderer`: the lobby backgrounds, the preview model through the entity renderer alone, the lobby windows) and sends it the keyboard and mouse. While a session connects or zones, `ZoneLoadingScreen` fades the frame to black over the scene and the HUD, and the placeholder models are left out until it is clear again. Between a Log Out and the lobby's return (`ViewportViewModel.IsReturningToLobby`) the viewport draws black (`HoldBlack`), and a lobby fades in from black when it appears. See [character-lobby.md](../design/character-lobby.md).

## Multi-box: windows, switching and input (#154)

One process can hold several characters (`CharacterSession`, one per character; one per account, see [desktop-shell.md](../app/desktop-shell.md)). `ViewportWindowManager` gives all of them tabs in the main viewport window (`ViewportViewModel.CharacterTabs`; `ActiveTab` is the character drawn and driven there) and opens a pop-out window per torn-off character.

**Airspace (#152, 2026-10-07).** On Windows the 3D surface is a native child window (`Win32ChildWindowHelper`), and Avalonia cannot draw over it: every switcher overlaid on it was invisible (all four styles, the PiP deck and the free camera banner). Every switcher is now a `Popup` (a small window owned by the viewport window, not topmost, not light-dismissed, not taking focus) placed over the surface, opened by `ViewportWindow.UpdateOverlayPopups` and closed while the window is hidden or minimised. Switcher buttons are not focusable, so a click leaves the keyboard with the game. The old pill background `#1A1C24E0` was read as ARGB (10 % opaque), which is why its smaller text was hard to read; the colours are now `#AARRGGBB` with readable sizes (12-13 px names, 11-12 px job and hints, light grey on dark).

| Style | Shows | Where and when |
|---|---|---|
| `FloatingPill` (default) | collapsed: status dot, active character, `▼ n chars`; on mouse-over it expands to "Switch Character View" (Ctrl+Tab hint), a row per character (name, job, `Detach ⧉`, or "own window" when popped out) the camera mode button, the **Graphics** backend drop-down (with **Reopen viewport to apply** when it differs from the running backend) and, in the header, minimise and close buttons for the viewport window (#320; the sessions stay connected, reopen from Settings > Open Viewport Window) | top centre of the view, while a character is shown (not over a lobby or the black return to it) |
| `TopRibbon` | a tab per character (name, job, `⧉` or "(own window)"), FPS and backend, display mode, minimise and close | auto-hides: slides in over the top of the view while the pointer is within 6 px of the top edge or over the ribbon (also over a lobby, for its window buttons) |
| `SideRail` | "Character Deck" with a card per character (name, job, HP, `⧉`, Focus) | auto-hides: slides in over the left of the view while the pointer is within 6 px of the left edge or over the rail, while a character is shown |
| `HotkeysOnly` | nothing | Ctrl+Tab / Ctrl+Shift+Tab only |

The pill follows the original rendering-window mockup (minimal glass pill, expanding on hover). The mockup's in-engine ImGui switcher is left to a future addon, and its "Multi-Box split/tile" option is retired: tear-off and PiP are offered with every style (the settings never offered a split). The edge reveal works from the surface's pointer moves (`UpdateEdgeReveal`). A revealed ribbon or rail stays while the pointer is over it (`IsPointerOver`) or its display mode drop-down is open, and hides 300 ms after the pointer leaves it for the 3D view or elsewhere (`AutoHideDelayMs`). Round 3: it had hidden as soon as the pointer moved onto its contents, so nothing on it could be clicked. Events from a popup's content route up through the `Popup` into the viewport window, so the window's routed pointer handlers read a move over the ribbon as a move over the 3D view away from the edge, and hid it. Those handlers now ignore events from the window's popups (`IsFromOverlay`); before, a click on any switcher button also reached the active character as a game mouse press.

**Popups across monitors (rounds 2 and 3).** The PiP deck sat on the monitor to the right of a borderless window. The popup positioner keeps a popup on the screen that holds its anchor point, and the PiP deck was anchored at the view's bottom-right corner (then moved in by an offset). When the window fills its monitor, that corner is the first pixel of the next monitor, so the deck was slid onto that one, from the start, wherever the window then went. The pill's anchor (top centre) is inside the window, which is why it followed. The PiP deck and free camera banner now anchor at points inside the view (`PlacementRect`, 12 px in from the bottom-right corner and 24 px up from the bottom centre; `ViewportWindow.PlaceBottomPopups`, updated when the view resizes). They slide instead of flipping when they would leave the screen, and every open popup is placed again 150 ms after a move or DPI change. Checked with a borderless window on the 2560x1440 monitor next to a 1920x1080 one: the deck is in the window's bottom-right corner at launch, after moving the window to the second monitor and after moving it back.

Checked 2026-10-07 by launching the shell with three unconnected sessions (Gordian, Knot, Claude) and screen captures: all four styles as above; the pill expands on hover; the ribbon appears at the top edge and hides away from it; after moving the window from the 2560x1440 monitor to the 1920x1080 one, the pill and the PiP deck (bottom right) are on the new monitor; with another program in front, a click on Knot in the pill switched the view to Knot and made the viewport the foreground window; Ctrl+Tab with Claude popped out went Gordian -> Knot -> Claude's window (focused) -> back to the main window on Gordian.

**Switching (#151).** Ctrl+Tab / Ctrl+Shift+Tab (`ViewportShortcuts`) are read on the window's tunnelling key-down with the other window shortcuts (F8-F12). They were on the bubbling key-down, where Avalonia's keyboard navigation can take Tab (Ctrl+Tab included) when a control in the window has the focus. Cycling follows the main window's tab order, wraps, and includes popped-out characters: choosing one brings its window to the front (`ViewportViewModel.SelectTab` raises `TabPoppedOut`, which `ViewportWindowManager` answers by activating the existing pop-out). From a pop-out, Ctrl+Tab continues in the main window's order (`SwitchTarget`), so the next character is shown in the main window (which takes the focus) or in its own pop-out. Each switch is logged (`Viewport` `Ctrl+Tab: A -> B`, with "(its own window)" for a pop-out). The keys and buttons the previous character held are released (`InputState.Reset`), otherwise the Ctrl of Ctrl+Tab or a held movement key stayed down for it; the same happens when a viewport window loses the focus.

**Switcher clicks take the focus (round 2).** The switchers are popups, which never activate their window, so clicking a name from another program switched the view but left the window unfocused, and the gamepad (Always Enable off) did nothing until the 3D view was clicked. Choosing a character now raises `ViewportViewModel.WindowActivationRequested`, and the window activates itself (restoring it if minimised).

**Camera mode and free camera (round 2).** The camera mode button and the banner's Exit switch the active character's camera (`PlayerLocomotionController.CameraMode`). Free camera did nothing in game: the locomotion controller moved its own private camera, but the viewport draws with its own `ViewportCamera`, whose free camera branch only kept the aspect ratio, so the view froze. The viewport now starts the free camera at the view it had and moves it by the controller's free camera movement since then (WASD / left stick, display space), looking along the controller's yaw and pitch (`ViewportCamera.SetFreeCamPose`). The free camera's view direction (`ViewportCamera.FreeCamForward`) now tilts like the orbit camera's (a positive pitch looks down); it had looked up, the mirror of the orbit view, so entering free camera flipped the view and flying "forward" climbed while looking down. **Free camera entry (#551).** The free camera opened inside the character's head: Change View (V, right stick click) cycles third person, first person, free camera, so the view it started from was the first-person eye, and first person's pitch tilts the other way to the free camera's. The viewport now works out the entry pose (`ViewportCamera.FreeCamEntryPose`): from third person, the view on screen (its eye after wall pull-in, its look with any lock-on aim), so nothing moves; from first person, the third-person view of the same look direction at the profile's zoom (at least 2.0 yalms), around the character, with the orbit's pitch range (-15 to 80 degrees), ground guard and wall pull-in. The view on screen hands the entry look to the controller (`PlayerLocomotionController.BeginFreeCam`, taken on the next input tick; `FreeCamLook` reports it meanwhile, since the viewport renders on its own thread), so flying starts along the look shown. Tests: `ViewportCameraTests.ViewportCamera_FreeCamEntry_*`, `PlayerLocomotionControllerTests.BeginFreeCam_SetsTheFreeCameraLook`. **First-person eye height (#305).** The first-person camera sat a fixed 1.3 yalms above the feet (`ViewportCamera.EyeOffset`): an Elvaan's chest, above a Tarutaru's head. It now sits at the drawn character's own eye level, `FirstPersonEye.HeightOf(model)` times its size scale (`PlayerSizeScale`), set each frame as `ViewportCamera.FirstPersonEyeHeight` by `VeldridViewportControl.UpdateSessionCamera` (null, the old offset, until the model has loaded). The height is the mean of the eyelid joints the blink clip `eye3` moves, in the first frame of the idle (head joint if a model has no blink clip): Hume male 1.66, Hume female 1.54, Elvaan male 1.94, Elvaan female 1.80, Tarutaru 0.71, Mithra 1.53, Galka 2.14 yalms (retail race skeletons, 2026-10-12, `RestPostureRealDataTests`; [calibrations](../reference/calibrations.md)). It is fixed per model: it does not follow the head through the idle, a walk or the /heal pose (retail behaviour not checked). In first person the player's own body is not drawn (`EntityRenderer.HideLocalPlayer`; its motion still runs, so its effects follow), except while an event's camera holds the view. The orbit camera keeps the fixed 1.3 offset as its look-at height.

**Gamepad focus (#150, #304).** `ViewportWindowManager.WindowFocus` (`WindowFocusTracker`) records which viewport window has the focus and which character it shows, and whether any GordianXI window is active; the gamepad and the sound controls both read it (it merged the gamepad's `InputFocusTracker` and the sound's `SoundFocusTracker`, #304, so they always agree on the focused character). The pad drives the focused viewport's character (none while it shows a lobby); with the control panel or another program focused, the character of the viewport focused last. Every other character gets a disconnected pad. Before, the pad went to `SessionRegistry.PrimaryRenderingSession`, which each pop-out took when it opened, so the last window popped out kept the pad whatever had the focus. Enable, Always Enable and Rumble are read from Controls & Input for every character (round 2): they had been read from the driven character's own input profile, and only the console's selected character has the saved one ([#314](https://github.com/jimmy58663/GordianXI/issues/314)), so a pop-out lost the pad on alt-tab with Always Enable on. Since #314 every character runs on a copy of the saved profile (see [console-and-input.md](../input/console-and-input.md#input-profiles-and-multi-boxing-314)). Across processes, SDL's Raw Input, GameInput and Windows.Gaming.Input joystick drivers are turned off on Windows so every GordianXI process can read the pad (see [console-and-input.md](../input/console-and-input.md#input-subsystem)).

## Shared device, render throttling and zone cache (#300, #301, #322)

**One device (#300, 2026-10-10).** `SharedGraphicsDevice` holds the process's one `GraphicsDevice`, created without a swapchain (`GraphicsDevice.CreateD3D11(options)` / `CreateVulkan(options)`) by the first viewport window and disposed when the last one closes. Each `VeldridViewportControl` creates its own `Swapchain` on it (`VeldridDeviceManager.InitializeShared`), draws into `Swapchain.Framebuffer` and presents it with `GraphicsDevice.SwapBuffers(swapchain)`; resizes stay per swapchain. The first window's backend preference wins; a later window preferring another backend shares the open device (logged). `GpuSharedResources` holds what windows share: the resource layouts the zone and entity pipelines bind (so a resource set made by one window binds in another's pipeline), the zone point-light table, the zone and entity texture caches, the GPU copies of entity models and the resident zones. Per window stay the pipelines (built for that swapchain's output description), command lists, per-frame uniform buffers, sub-environment uniforms, the particle simulation, the stock UI and the lobby renderer. Offscreen tests still create a device of their own (`VeldridDeviceManager.Initialize`, `new ZoneTerrainRenderer(gd)`), which then gets private shared resources.

*Locking.* The render loops still run one per window on their own threads. Every frame (record, submit, present), every zone upload chunk and every swapchain resize is made under `SharedGraphicsDevice.Lock` (the control's `_renderLock`), so the device's immediate context is used by one thread at a time and a resource two windows share (a generator mesh's uniform buffer, the light table, a weighted mesh's dynamic vertex buffer) is written and drawn by one frame's command list before the next window's frame is recorded. Background windows present without VSync so they never hold the lock through a vertical blank.

**Throttling (#301).** `ViewportWindowManager` tells each window whether it is the focus target (`WindowFocusTracker.IsFocusTarget`: the focused viewport window, or the one focused last while the control panel or another program has the focus; every window before any was focused), and the window sets `VeldridViewportControl.RenderMode` (`ViewportRenderPolicy.Resolve`):

| Mode | When | Render loop |
|---|---|---|
| `Full` | the focus target | every frame, VSync as set in Settings |
| `Background` | any other shown window | `ViewportRenderSettings.BackgroundFrameRate` (Settings -> Framerate, 30 fps default, 10-60 offered), no VSync |
| `Paused` | minimised, hidden, or (Windows, background windows only) fully covered by other windows | no frames; ticks zone loads, action playback and sound every 100 ms |

Covered detection (`Win32OcclusionProbe`, twice a second) walks the top-level windows above the viewport's in z-order and subtracts their visible frames (DWM extended frame bounds) from the surface rectangle; layered, transparent and cloaked windows never count, so an overlay cannot pause a window that can be seen. The settings are process-wide (`ViewportRenderSettings`, saved in `viewport_settings.json` as `BackgroundFrameRate`, `ZoneCacheBudgetMb` and `IsVsyncEnabled`) and apply to every window at once. VSync from Settings now reaches the swapchain; it had been saved but never applied (every window presented with VSync on).

**Zone cache (#322).** Measured first (offscreen, D3D11, this machine's GPU, Southern San d'Oria 230 / Lower Jeuno 245 / Bibiki Bay 4, terrain only, 2026-10-10): a cross-zone switch ran `ResourceManager.TryLoadZone` (cached after the first read: 0 ms; first read 230-720 ms), then `ZoneTerrainRenderer.LoadZone` re-created and uploaded every buffer under the render lock (34-143 ms; the view froze), and the zone change had cleared the texture cache, so the next frames uploaded each texture on first draw and pre-warmed the particle emitters again (first frame 9-80 ms; 140 ms the very first time in San d'Oria). Shaders and pipelines were not involved (built once per window) and no mipmaps are generated.

Now `ZoneResidencyCache` (in `GpuSharedResources`) keeps `ZoneTerrainRenderer.ResidentZone`s: a zone's vertex, index and generator buffers and its textures, uploaded once per device and shared by every window (`ResidentZone.Build`, off the render thread, taking the device lock per 256 submeshes or 8 textures so the windows keep drawing). A window showing a zone holds a reference; `ActivateZone` swaps the renderer's lists to the resident zone and resumes that window's simulation of it (emitters, weather and map routines, door animator, sub-environment uniforms: a `ZoneRuntime` kept per resident zone), so a switch back does not pre-warm the emitters again. Unreferenced zones stay while they fit in `ZoneCacheBudgetMb` (1536 MB default; 0 keeps only zones on screen) and at most 12 zones; over that, the least recently used unpinned zone goes first, then pinned ones; a zone read before a VFS reload goes as soon as no window shows it (`SelectVictims`). Evicting a zone frees its buffers and those of its textures no other resident zone uses (`GpuTextureCache.Evict`). Zones a logged-in character is in are pinned and preloaded once a second, one at a time and only while expected to fit (`PreloadSessionZones`). DAT reads go through `ZoneResidencyCache.TryReadZone`, one reader per zone, so a window's load and the preload never parse a zone twice.

A switch to a resident zone binds it on the same frame (`TryShowResidentZone`, logged `Showing Zone N from the GPU zone cache in x ms`). A switch to a character whose zone is not resident yet (just zoned, or over budget) keeps drawing the current character (`ActiveSession` is the requested one, `DisplayedSession` the one drawn) while that zone reads and uploads in the background (`PrepareZone`), at most 3 s (`DeferredSwitchTimeout`), so the view never shows the new character on the old zone's terrain or fades to black.

*After (same offscreen run):* switching to a resident zone 0.07-0.16 ms, first frame after it as any other (1-3.5 ms); a zone not resident uploads in 41-141 ms in the background (24-58 MB each with textures). The first frame the first time a window shows a zone still pre-warms its emitters (138 ms in San d'Oria). A second window's renderer still builds its own pipelines (about 0.5 s when a pop-out opens).

*Frame cost by window count (offscreen, Southern San d'Oria, 1280x720 each, terrain only, one window every 60 Hz tick):* 1 window 2-3 ms per tick; 2 windows 4.1 ms with both every tick, 3.1 ms with the second at 30 fps; 6 windows 12.2 ms every tick, 7.1 ms with five at 30 fps. All windows in one zone share one upload. *In game (maintainer, round 1, 2026-10-10; dedicated VRAM 1.6-1.7 of 8 GB):* 1 character average 7 ms per frame; 3 characters in 1 zone, 1 viewport average 5 ms (high 8); 3 characters in 3 zones average 5.5 ms; 3 viewports about the same.

**Each character keeps its camera (round 2).** Round 1 in game: cross-zone Ctrl+Tab was fast, but the camera rose or dropped into the new character's view, sometimes through floors or walls. The viewport had one `ViewportCamera` and one set of smoothers for whichever character it showed, so on a switch the follow height eased from the previous character's height (`FollowHeightRate`, below `FollowHeightSnapDistance` = 8 yalms), the collision distance released from the previous character's pulled-in value (`CollisionReleaseSpeed`), and the orbit smoother interpolated from the old angles. Pop-out windows did not show it because each has its own camera. Now every logged-in character has a `SessionView` in each viewport (its `ViewportCamera`, the player and orbit smoothers, the unwrapped yaw and the free camera), and the views of the characters not on screen are updated about 30 times a second against their own zone's collision (`TickHiddenCameras`), so a switch, same zone or not, shows the new character's settled camera on the first frame. A view not updated for more than 0.5 s (a paused window, a character just logged in) is placed outright (delta 0: no follow-height ease, no collision release, smoothers reset). Paused windows keep their cameras updated too. In game: pending (round 2).

Verification: `dotnet test --filter SharedDeviceAndZoneCacheTests` (headless D3D11 device with two swapchains, zone sharing and eviction, texture eviction, victim selection, focus target, render policy). In game: see the test checklist in the PR.

## Camera and zone terrain (Phase 5B)

- **Smooth camera follow while engaged (#547).** The locomotion controller ticks on a UI timer (mostly about 16 ms, sometimes 31 ms or more when the UI thread is busy), and the viewport draws at its own rate. It shows the player's position and the orbit (yaw, pitch, distance) slightly in the past (`TickPositionSmoother`), interpolating between the two ticks around that moment. Two inputs made the engaged camera shake while strafing or circling a mob locked on (auto-face only runs while locked on), found by replaying the viewport's path headlessly (`LockOnCircling_ViewTurnsEvenly`: strafing round a drifting mob, ticks of 16 ms with a 31 ms one every 12, drawn at 144 fps):
  - *The render delay jumped.* It was the longest of the last 8 tick intervals, so it changed by a whole tick (16 to 31 ms and back) whenever a long tick entered or left that window. The player and the camera then stepped back or forward by that much motion in one frame, and the view stalled while waiting for a long tick. The delay now eases toward that interval: it rises at `DelayRiseRate` (0.25 s/s, the render clock briefly 25% slow) and falls at `DelayFallRate` (0.01 s/s, 1% fast), so it holds the longest interval of about the last second and never steps.
  - *The lock-on aim used the target's tick sample.* The locked view yaw turns to the bearing from the camera to the target. That bearing used the target's position as the last input tick read it, while the mob is played back every frame (`WorldEntity.InterpolatePosition`), so the aim moved in tick-sized steps toward a moving mob. `ApplyLockOnAim` now aims at the target's live position (the tick sample is kept only for the ease-out after the target is gone).
  - Locked on, the view aims at the target, so any small step of the camera's position became a turn of the whole view. In the replay, the largest frame-to-frame change in the view's turn rate went from 57.8 to 7.3 degrees/s; what is left is the path drawn straight between ticks. The rates are chosen, not measured against retail; no retail reference video was taken, since retail shows no jitter to match. The character's own heading still turns in steps of 1/256 of a circle (the wire heading), which the camera does not follow while locked on.

## Zone visibility (#70)

Which zone placements draw each frame, in the client's order (xi-tools `docs/zone/lod-draw-distance.md` "Culling pipeline", from xiclient; `docs/zone/format.md` "Visibility"). `ZoneVisibility` (Engine) holds the rules; `ZoneTerrainRenderer.Visibility.cs` applies them to the zone's placed submeshes, door leaves and elevator parts before frustum culling. Interiors, vessels and effect layers are not ZoneDef placements of the zone and are never culled this way (`PlacementVisibility.Always`).

1. **Culling table (PVS).** ZoneDef header `+0x14` points at a u32 table count, then that many tables of `count` + `count` u32 record indices (`ZoneCullingTables`). A collision transform's `+0xA8` points at the count word of the table a camera over that object's floor draws with (0 = none); the record's own `+0x48` holds the same pointer. Each frame the highest collision floor at or below the camera **eye** (`ZoneCollisionMesh.CullingTableUnder`, re-probed after half a yalm) picks a table, and only the placements it lists draw; a floor with no table, or no floor within `ZoneVisibility.CameraFloorReach` (30 yalms) below the eye, draws everything. The reach is GordianXI's bound (*inference*, round 1): from 200 yalms over Valkurm retail draws the whole area around (`image-20`), where the hilltop far below would pick a table that leaves most of it out. Generator-bound records (BlockID not `_`/`@`) leave the quad-tree pass the tables gate, so no table hides them. An interior's floors (merged collision) and a voyage's deck pick none: their tables belong to another ZoneDef.
2. **Distance.** Distance is from the camera eye to the placement **origin** (not its bounds), as the client measures it. A record with `+0x46` bit 0 set is culled at its own `+0x40` distance times the multiplier; any other at the global draw distance.
3. **Level of detail.** A mesh id ending `_h`/`_m`/`_l` loads all three variants (`ZoneDefDecoder.ResolveLodTemplates`), each tagged with the slots it fills; a missing variant falls back like the client's `InitializeMeshLOD` (one variant fills all; `h`+`m` gives low → `m`; `h`+`l` gives mid → `h`; `m`+`l` gives high → `m`, by symmetry). The slot is high inside `+0x38`, mid up to `+0x3C`, low beyond, each times `ZoneEnvironmentSettings.LodDistanceScale` (default 5/3, **not retail**: the maintainer asked for full detail to about 50 yalms in round 1, and 5/3 moves West Ronfaure's 30-yalm tree switch to 50). Before, `ResolveTemplate` always drew `_h`.
4. **Global draw distance, far clip and fog.** `ZoneVisibility.GlobalDrawDistance` = 0x2F keyframe `+0x58` × multiplier, floored at 43 yalms (the client's `MinimumDrawDistance`). The viewport sets the camera's far clip to it (was a fixed 5,000); the near clip stays 0.1. The sky dome and sky generators are drawn at the far plane by their shaders, so they do not depend on it. Outdoors `ZoneEnvironmentSettings.ApplyKeyframe` scales the fog distances by the same multiplier (xi-tools: the client takes the draw distance and the fog from the same environment field); indoors the authored fog stays. The outdoor fog end is floored at the global distance (round 2), but the global distance is not stretched to the fog end: retail cuts terrain off in blocks before the fog covers it (`image-20`).

## Building interiors (#68)

Format: xi-tools `docs/zone/subareas.md` (after xim `SubAreaManager`), in [dat-files.md](../world/dat-files.md#zone-files). Each interior has `'m'` volumes in the zone's 0x36 tables (`ZoneInteraction.Param` = the interior id), placeholders (ZoneDef record +0x50 `FileIdLink`, `MeshGroup.SubAreaLink`) and its DAT (`ZoneSubAreas.InteriorFileId`).

- *The volumes straddle the doorways.* Lower Jeuno's are room-sized (6-10 x 5 x 6-10 yalms), but the food shop's `m6t9` is centred 2.5 yalms west of its interior's floor, which runs 19 yalms east. So the player is in an interior while in one of its volumes or over its collision floor (`SubAreaTracker.ActiveSubArea`).
- *The placeholder is a plug, not the facade.* Offscreen in Lower Jeuno (2026-10-20): hiding `r_syoku` changes nothing seen from the street, and from inside it is a dark block filling the tavern. The retail capture (`Shop_Interior.mp4`) shows the lit room through the open door from outside and the street from inside, with no fade. So interiors within `ZoneSubAreas.NearMargin` (6 yalms) of their volumes or floors are drawn and their plugs hidden (`SubAreaTracker.NearSubAreas`); **Differs from xi-tools**, whose rule draws an interior only while active.
- *Loading.* The tracker updates from the local player's position each locomotion tick. Every interior's collision of the zone loads in the background on the first update (Lower Jeuno: 13 interiors, about 70,000 triangles), so each room's floor bounds are known before the player gets there; before, a shop entered through its wall (collision walls off) was found only once the player came near its doorway volume (round 2). Interior geometry still loads when an interior comes near (its parse and upload take a fraction of a second), which keeps the GPU cost to the rooms near the player. Interior collision (`SubAreaTracker.InteriorCollisionLoader` → `ResourceManager.TryLoadSubAreaCollision`) and is merged with the zone's (`ZoneCollisionMesh.Merge`) into `WorldState.Collision`. The zone's own triangles inside an interior's footprint (its bounds, 0.5 yalms in from the sides, between floor and ceiling with a yalm to spare, and only over the interior's own floor) are dropped: they are the closed building's shell, and Lower Jeuno's chocobo stables have zone walls running through the room the interior opens (round 3: the maintainer was blocked at `!pos -87.19 -0.10 -186.15 245`, Windower (-87.19, -186.15, -0.10); `SubAreaTests` checks that every wall within 1.5 yalms there is the interior's). - *Lighting (round 1: the tavern was bright and grey where retail is dark and warm).* An interior's placements link its own sub-environment (`ev10`, keyframes under `r_3j/ev10/*`): each interior gets its own scene uniforms filled from its DAT's environment.   - *Retail client on local LandSandBoat (2026-11-06; `Retail Captures`, `NorthernSandoria_CarpentersGuild_*`, `LowerJeuno_MerryMinstrel_*`; the positions and NPCs are LandSandBoat's, the drawing is the client's).* Walking in through the opened door, Andreas stands on the platform with his feet on it, as GordianXI now draws him, and the Merry Minstrel's NPCs stand on the floor in both clients. ## Resource cache keys

A cache key must say what the data *is*, unique across the whole install, not what it is called (#163, 2026-09-30). Names (texture names, section ids) repeat across DATs with different contents; keying on them drew one NPC model's face on another.

- **Textures:** every decoded texture carries `DecodedTexture.Source`, the DAT it came from (`file<id>`, or a path for DATs loaded by path such as `ROM/0/0.DAT`) and the section's offset in it (`file1364@266384`). The loaders stamp it: `EntityModelLoader.ParseDatContainer` (model, face and gear DATs), `ZoneDataLoader.ParseZoneContainer` (zones, actor effects), `SharedEffectResources.Parse`. `GpuTextureCache` uploads once per source, shared by every model or zone that loaded that section, and caches a texture without a source on its own (code-built textures, UI). A name is only used to find a texture inside one model's or zone's own texture table (`GpuTextureCache.Resolve`).
- **Not entity ids:** many entities share one model (and its textures), and an entity can change its look under the same id, so per-entity keys would multiply uploads and still need invalidation. Per-entity state (joint palettes, event poses) is keyed by server id because it belongs to the entity.
- **Audited (2026-09-30):** models (`Monster_<model id>`, or race + face + the full gear table), GPU models (the model object), zones, collision and actor effects (zone / model id), item names (item id) and VFS resolution (path) were already keyed by what they are. The stock UI's textures are looked up by name inside one UI library, which is replaced as a whole.

## Live PiP thumbnails (#302)

Each PiP deck card holds a `PipThumbnailControl`: a `VeldridViewportControl` with `IsThumbnail` set, bound to that card's character (`ViewportCharacterTabViewModel.LiveSession`). It is a native child with its own swapchain on the shared device (#300), so it reuses the whole scene path (zone residency, entity models, the character's own camera) rather than a second renderer. The deck is a popup, so the controls exist only while it is open: a hidden deck, a minimised window, or `LivePipThumbnails` off costs nothing (with the setting off a card's control shows no character and draws no frames). `ViewportViewModel.RefreshPipThumbnails` applies only the difference to `PipThumbnails`, so a refresh does not restart the cards that stay.

What a thumbnail does and does not do, so nothing runs or is drawn twice: it draws only the Tier 1 scene (no stock UI, no ImGui, no performance overlay) at `ViewportRenderSettings.PipThumbnailFrameRate` (5 FPS by default, `ViewportSettings.PipThumbnailFrameRate`, clamped 1-30) without VSync, and pauses when its surface is fully covered (the background window rule). It leaves to the main viewport everything that viewport already does for characters it is not showing: `TickHiddenCameras` (their cameras and `ActionPlayback.Update`), the zone preload and the sound (`GameAudioService`; a thumbnail never claims it). The character on a card is neither the main window's active tab nor a pop-out (`RefreshPipThumbnails`), so no world is drawn by two viewports; swapping a card in removes its thumbnail in the same step. Cost against the resource baseline: N Windower clients each draw a full window; a card is a 170 x 76 px picture at 5 FPS from a zone the main viewport keeps resident anyway (#322), plus one small swapchain and one render thread per visible card (at most `MaxPipStreams`, 5).

In-game check pending: a native child inside a popup window is the new part (airspace is per window, so the popup's own surface should show it); `LivePipThumbnails` is the fallback.

## Tier 3: ImGui overlays and the performance overlay (#30)

Each viewport window draws its Tier 3 pass after the stock UI and before present (`VeldridViewportControl.RenderTier3_ImGuiOverlays`, in `VeldridViewportControl.Overlays.cs`); the lobby frame draws it too. It owns its own Dear ImGui context (`ImGuiOverlayLayer`, Hexa.NET.ImGui 2.2.9 = Dear ImGui 1.92.2b), created the first time an overlay is shown. A frame sets the context, runs `NewFrame`, the overlays, `Render` and the GPU draw under the device's GPU lock, then restores the previous context, so the windows' render threads never share ImGui's global context. No `imgui.ini` or log is written. The performance overlay takes no input (its windows are `NoInputs`); interactive ImGui windows (addon canvases, debug windows) get the mouse and keyboard as described under [Input for interactive overlays](#input-for-interactive-overlays-380).

### Input for interactive overlays (#380)

An interactive overlay implements `IImGuiOverlay` (`IsVisible`, `Draw`) and registers with `ImGuiOverlayRegistry` (process-wide, copy-on-write). While no registered overlay is visible the viewport runs no ImGui frame for them, `ImGuiInputBridge` queues nothing and captures nothing, and every input path is exactly as before: **hidden overlays never take input**, and the performance overlay alone captures nothing. Ctrl+Shift+F11 shows the built-in `ImGuiInputTestWindow` (a button, slider, checkbox and text field) to check the routing in game.

- **Feeding.** `VeldridViewportControl.ImGuiInput` (an `ImGuiInputBridge`) is filled on the UI thread by `ViewportWindow` and drained by the layer on the render thread just before `NewFrame` (`io.AddMousePosEvent` / `AddMouseButtonEvent` / `AddMouseWheelEvent` / `AddKeyEvent` / `AddInputCharactersUTF8` / `AddFocusEvent`; at most 1024 queued events per frame). Positions are the framebuffer pixels the raw mouse events and the stock UI already use (`DisplaySize` is the framebuffer), so there is no conversion. Keys map through `ImGuiKeyMap.FromAvalonia`; modifier keys are fed so Ctrl/Shift combinations work inside ImGui. ImGui sees every event, so a click outside its windows ends text editing; keyboard navigation is off.
- **Routing (what the game still gets).** After each ImGui frame the layer publishes `io.WantCaptureMouse`, `WantCaptureKeyboard`, `WantTextInput` and the cursor shape to the bridge (one frame behind the pointer). `ViewportWindow` gives a mouse press to ImGui when `WantCaptureMouse` is set and not to the character, stock UI menus or drag mode; that button's release then goes to ImGui too (`_imguiButtons`), and one pressed outside ImGui stays the game's. While the pointer is over an ImGui window or dragging in one, moves do not reach the stock UI (its pointer is cleared) and the wheel goes to ImGui. Keys: window shortcuts (Ctrl+F12, F11, ...) come first; then, while `WantCaptureKeyboard` is set (a text field or drag is active), the key is not game input. Character keys are left unhandled so the platform's text input follows (Avalonia drops the WM_CHAR after a handled key, see the stock chat line), and that text goes to ImGui when `WantTextInput`. Key releases go to ImGui and to the game, so a key held before a field took the keyboard is not left down. Deactivating the window sends ImGui a focus-lost event.
- **Cursor.** On Windows the native surface asks the control for its cursor (`CursorQuery`): over an ImGui window it is the system cursor for ImGui's shape (arrow, I-beam, resize, hand, not-allowed; `LoadSystemCursor`), else the stock arrow as before. Elsewhere `ViewportWindow.UpdateViewportCursor` sets the matching Avalonia cursor.
- **Limits.** The registry's overlays are drawn in every viewport window's ImGui frame, each window with its own ImGui context (window positions are per context); an addon that wants one canvas decides in `Draw`. ImGui's clipboard is its own (no system clipboard bridge yet), IME composition is not fed, and gamepad navigation is not wired.

**Renderer (`ImGuiRenderer`).** No maintained ImGui renderer exists for NeoVeldrid, so this one is written clean-room from Dear ImGui's documented backend contract (`imgui.h`, `docs/BACKENDS.md`): GLSL 450 shaders cross-compiled by NeoVeldrid.SPIRV (like the stock UI's), dynamic vertex and 16-bit index buffers that grow as needed, one `DrawIndexed` per `ImDrawCmd` with its clip rectangle as the scissor and `VtxOffset` honoured (`RendererHasVtxOffset`), straight alpha blending, no depth. It implements the 1.92 texture protocol (`RendererHasTextures`): each frame it walks `ImDrawData.Textures` and creates (`WantCreate`: full upload, `SetTexID`), updates (`WantUpdates`: the changed rectangles) or destroys (`WantDestroy` once unused for a frame) GPU textures, RGBA32 or Alpha8 widened to white. On dispose it destroys every texture ImGui still holds, then the context. Style (AGENTS.md): ImGui's dark theme, `WindowRounding = 6`, translucent window background (alpha 0.72), soft blue-grey border.

**Performance overlay (`PerformanceOverlay`, `PerformanceOverlayMode`).** Three modes, process-wide (every viewport window), saved as `ViewportSettings.PerformanceOverlay`:

| Mode | Shows |
|---|---|
| `Hidden` (default, as retail) | nothing; the frame does no overlay work beyond reading the mode |
| `Fps` | top-right corner: FPS (green from 55, amber from 30, red below) and the average frame time |
| `Detailed` | adds min / max frame time and the 1% low, the frame pacing graph (the last 240 frame intervals, oldest left, scaled to at least a 30 FPS frame), draw calls (scene, stock UI batches, overlay), meshes drawn / culled and UI quads, a CPU / GPU table per pass (Scene, Stock UI, Overlay, and the frame's CPU time), managed heap, allocation rate and GC counts (sampled twice a second), backend, resolution, vsync and GPU name |

Ctrl+F12 in a viewport window steps Hidden -> Fps -> Detailed -> Hidden (`ViewportShortcut.CyclePerformanceOverlay`); `/perf [off | fps | full | next]` does the same from the chat line (`PlayerActionService.PerformanceOverlayCommand`, set by `ViewportWindowManager` for each session); Settings > Display has a drop-down. A change from the key or command is saved by the main window's view model (`ViewportRenderSettings.PerformanceOverlayChanged`).

**What is measured, and the cost.** While hidden nothing is recorded, no ImGui frame runs and no GPU queries are issued. While shown, `ViewportPerformanceStats` keeps everything in buffers allocated once (the 240-interval ring, a sort scratch array, the pass arrays), and the text is formatted into stack UTF-8 buffers, so a shown overlay allocates nothing per frame either. The frame interval is measured from frame start to frame start (drawn frames only), the CPU pass times from `Stopwatch` timestamps around each pass's recording and submit (smoothed, 10 % per frame), the CPU frame from frame start to before present (so a vsync wait is not counted).

**GPU pass timings (`GpuPassTimer`).** NeoVeldrid has no query API, so each backend needs native code. Direct3D 11 (`D3D11GpuPassTimer`): a `TIMESTAMP_DISJOINT` query around the frame and a `TIMESTAMP` before the scene and after each pass, on the immediate context from `GetD3D11Info().Device` (under the GPU lock, which every immediate-context use already takes), read back with `D3D11_ASYNC_GETDATA_DONOTFLUSH` from a ring of five frames, so it never waits for the GPU; a disjoint frame is dropped. The timer exists only while the detailed overlay is shown. Vulkan shows "n/a" for now ([#381](https://github.com/jimmy58663/GordianXI/issues/381)). The queries are flushed by the frame's present; the offscreen test presents to read them (`ImGuiOverlayRenderTests`).

Checked offscreen on D3D11 (`ImGuiOverlayRenderTests`, 2026-10-12, 800 x 600 over a green clear): the FPS line and the detailed panel draw in the top-right corner and nothing elsewhere, hidden draws nothing, and the D3D11 timer reports pass times after a few presented frames. Set `GORDIAN_UI_DUMP` to a folder to save the frames as PNG.
