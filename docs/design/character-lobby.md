## Launch

`MainWindowViewModel.LaunchSelected` keeps two paths for LandSandBoat profiles:

- **Login mode (profile editor):** a radio choice, "Character Select screen" or "Auto-Login" (`AccountProfile.LoginMode`, saved in the profile JSON). Auto-Login needs a Character Name or a Character Slot 1-16; saving without one is refused. A profile saved before the choice existed has no `LoginMode` and keeps its behaviour (`EffectiveLoginMode`): Auto-Login when it names a character, character select otherwise. Auto-Login with no character falls back to character select. The Character Name and Character Slot fields show only while Auto-Login is chosen (character select picks the character on screen); hiding them keeps their values, which the profile still saves and which return when Auto-Login is picked again. Slot is a drop-down, "Not set (use the name)" then 1-16; its selected index is the stored `CharacterSlot` (0 = not set), so existing profiles load unchanged.
- **Auto-Login (the fast path, unchanged):** logs straight in as the named character (`LsbLoginClient.LoginAndSelectAsync`, now running over `LobbySession`).
- **Character select (retail behaviour):** (`UsesCharacterSelect`) logs in, opens a `LobbySession` and a `LobbyController`, and shows the lobby in the primary viewport window (`ViewportWindowManager.ShowLobby`). Only one lobby is open at a time; a second character-select profile is skipped with a status message. The chosen character's ticket starts the game session through the same code as Auto-Login (`StartLsbSessionAsync`); the lobby leaves the viewport once the session's tab is registered. Decline on the licence page, Back on the title menu, or a lost lobby connection closes the lobby and disconnects.
- **Log Out returns to the title menu, in the same window:** a session reopens it, whether it came through character select or an Auto-Login profile skipped it (an Auto-Login Log Out ended the session until round 2 of the #368 / #377 tests; the maintainer wants the lobby in both cases, and the launcher logs in to the lobby servers afresh either way), when the server ends the session with S2C 0x00B state Logout (`/logout` or the menu's Log Out; `SessionNetworkManager.LoggedOut`, raised before the session disconnects). The handler first calls `ViewportWindowManager.BeginLobbyReturn`, so when the disconnect removes the tab the viewport window stays open and shows black (`ViewportViewModel.IsReturningToLobby` -> `VeldridViewportControl.HoldBlack`). The launcher then logs in to the lobby servers again underneath (a new xi_data / xi_view session: LSB's map session is gone after a Log Out, so the old lobby connection cannot be reused), shows the title menu in that window (without the licence page), and the lobby fades in from black over `LobbyFadeInSeconds` (0.5 s; every lobby appearance fades in). `EndLobbyReturn` then lets the window close again if the lobby could not be shown (the error goes to the status line). From the black screen on, the zone's music, ambience and sounds fade out (#368, [audio.md](audio.md#music-and-ambience-42-114)); the lobby plays no music yet ([#378](https://github.com/jimmy58663/GordianXI/issues/378)). A Shut Down ends as before: the registry unregisters the session on Disconnected and the window, with no tab and no lobby, closes. Before round 3 a Log Out did that too and the lobby opened a new window and graphics device.
- **Log Out and Shut Down look the same on the wire, so the client's own request decides ([#270](https://github.com/jimmy58663/GordianXI/issues/270)):** LandSandBoat answers both with S2C 0x00B state 1 (`Logout`). C2S 0x0E7 (`c2s/0x0e7_reqlogout.cpp`) only adds or changes the LEAVEGAME effect, storing the kind (1 logout, 3 shutdown) as its power; `scripts/effects/leavegame.lua` uses the kind only for the "Executing logout/shutdown" countdown message and, after it, calls `leaveGame` -> `charutils::SendDisconnect`, which always queues state 1. XiPackets (`world/server/0x000B`) notes the retail client only looks at states 1, 4 (Cancel) and 8 (Timeout), so retail too must decide from its own request. `LifecyclePacketModule` therefore keeps the kind of the last 0x0E7 still standing (`PendingLogoutKind`, updated the way LSB applies it: Toggle starts or cancels, On starts or switches kind, Off cancels, a mismatched On does nothing; cleared on a new connect), and `SessionNetworkManager.LoggedOut` passes a `SessionLogout` (state + requested kind). The handler returns to the lobby only when `ReturnsToLobby` (state 1 and not a shutdown request); a logout the server forces without a request (a GM, an LSB `ForceLogout`) also returns there. The PR #269 handler acted on every state 1, so Shut Down returned to the lobby. The menu's Shut Down / Log Out and the new `/shutdown [on|off]` / `/logout [on|off]` commands all go through this. **Unverified:** that retail returns to the title menu on a server-forced logout; standing up cancels LSB's countdown (losing Healing removes LEAVEGAME) without telling the client, so a cancelled shutdown followed by a server-forced logout would close instead of returning (rare); retail's fade timings.

Retail profiles use the same lobby screen through the direct retail login ([network/retail-login.md](../network/retail-login.md)).

## What the lobby is made of

Sources: xi-tools `docs/title/` and `docs/dats/ROM_0_23.md`, checked against the retail install.

## Title fly-through (#552)

Read from the retail file 2026-11-13 (`TitleSceneResource`, Core; dump of every section and command). The file is an ordinary section file, played with the cutscene machinery GordianXI already has.

- **Segments.** 22 `0x07` routines, each flying one zone (numbered 1-22 in file order, xi-tools' section numbers). Each starts with op `0x7B` (u32 zone id at +8, then 12 zero bytes), op `0x7C` (the weather FourCC at +8: `fine`, `suny`, `clod`, `mist`, `rain`) and op `0x7D` (the Vana'diel clock, u32 at +8, in 1/60 s of the game day: 2,592,000 = 12:00, 900,000 = 04:10, so hour = value / 216,000), fades in from black (op `0x0F` to 80 80 80 over 100 frames), then plays camera shots (op `0x04` naming a `0x06` route over its duration), cross-dissolves (`0x10`), blur (`0x0E`) and dark fades between shots (`0x0F` to 02 06 04 and back), with more `0x7C` / `0x7D` changes, usually under a cut or a dark fade, and fades to black over its last 100 frames. They run 8,900-14,461 frames (2.5-4 minutes at 60 a second). North Gustaberg (`mov5`, segment 12) goes 12:00 sunny, 08:50 fine, 17:30, 19:00, 23:00 mist, 03:30 cloudy, 07:00 fine. One segment (`mov1`, La Theine Plateau) uses op `0x7E` (FourCC at +8) to light its scene with the file's own environment `s101`; the file's other two environments (`0620`, `1700`) are named by nothing. There is **no fog in the file**: the zone's own `0x2F` environment applies at the segment's hour and weather.
- **Order.** `main` repeats `loop` (op `0x73`). `loop` is four random choices played in turn, each entry an op `0x3B` (play the routine and wait for it): op `0x3D` opens a choice of `mov1`, `mov2`, `mov3`, `mov5`, `mov4`, `mov6`, `mov7`, `mov8` and `0x3E` closes it; then op `0xAF 1` opens `ex1a`-`ex1c` (Rise of the Zilart zones), `0xAF 2` `ex2a`, `ex2d`, `ex2b`, `ex2c` (Chains of Promathia) and `0xAF 3` `ex3a`, `ex3d`, `ex3e`, `ex3c` (Treasures of Aht Urhgan), each closed by `0x3E`. `0xAF n` is read as "a choice taken only with expansion n" (**inferred** from its operand and the zones it holds). `ex3b`, `ex2e` and `ex2f` (segments 4, 21, 22) are in no choice and never play. Segment 12 always plays first (xi-tools' experiment, `docs/title/README.md`); how retail starts there is not in the file.
- **Differs from xi-tools** (`docs/dats/ROM_0_23.md`): it reads the file as tagged nodes with "zone sections" behind an 8-byte marker `0x67b` and "weather records" carrying fog colour and range; the marker is op `0x7B`'s command header (op 0x7B, size 6 dwords), and each "weather record" is an op `0x7C` followed by an op `0x7D`, whose clock value was read as a fog colour. **Beyond xi-tools**, which says the picker is not in the file: `loop` above.
- **Playback (`TitleFlythrough`, Engine `Ui/Lobby/`).** Each segment routine is played through the fly-through's own `EventPresentation` (camera shots, fades, cross-dissolves and blur, as a cutscene's are), whose clock stands still on black until the segment's zone is on screen. Order: segment 12, then one random segment of each choice in turn (the base game's, then each expansion's), over and over, as `loop` does; a choice none of whose zones is installed is skipped (GordianXI's stand-in for the expansion test: the zone's model file must resolve). The maintainer's interim rule (segment 12, then the segments in file order) is used only when the file has no choices. The next segment is chosen when one starts, so its zone loads in the background meanwhile (`ZoneResidencyCache.PreloadInBackground`): a segment ends on black and the next fades in once its zone is on screen, so a slow load shows as a longer black, never a stall or a half-drawn zone. A new visit to the title screen (after a Log Out) starts on the next segment, as retail changes the zone on each return (xi-tools).
- **Drawing (`VeldridViewportControl.Title.cs`).** The viewport loads the segment's zone through its usual zone loading and GPU zone cache (the lobby asks for no session's zone, so no fade gate applies), lights it from the zone's `0x2F` environment at the segment's hour and weather (a weather change cross-fades as in game) or from the file's own environment for `0x7E`, places a camera on the presentation's shot as an event camera is placed (route points mirrored in X and Y, far clip at the environment's draw distance), and draws it with the zone renderer (the presentation drives its post-process for the blur and dissolves). The lobby then draws the segment's scene fade over the zone, the backdrops' art without their plain `newtex` fill, the preview model and the windows. Leaving the lobby asks for the session's zone and lighting again. **Screens:** the title menu, character select, creation and deletion; the licence page keeps its own backdrop (the opening zone loads behind it). Retail's creation and deletion may show another scene; none was found in the lobby DATs, so they show the fly-through until one is captured.
- Verified offscreen (`TitleFlythroughRenderTests`, `lobby_title_*.png` with `GORDIAN_UI_DUMP`): North Gustaberg under the title art at the segment's noon and at its 19:00 shot. **Unverified against retail:** that the clock stands still between `0x7D` commands (they mostly change under a cut or dark fade, so a running clock would barely show), that `0x7E` replaces the zone's environment for the rest of the segment, the expansion reading of `0xAF`, and the creation / deletion scene.

## The lobby stage (#552 round 2)

Character select, deletion and creation stand the character on a stage instead of the fly-through (`Lobby_Title_Select_Create_Delete_Retail.mp4`, the maintainer's capture at 2558 x 1440, 2026-11-13): the same grassland on all three, the character in front of a rock ridge rising to pink peaks on the right; purple dusk on the list, red sunset on the delete list, blue daylight in creation.

- **The file.** `ROM/1/5.DAT` (file 83935) is the model file of zone id 300 in the client's own numbering (`ZoneDataLoader.GetZoneModelFileId`: 0x147B3 + 300 - 256), laid out as any zone model file: a `mode` directory with the 0x1C map and 141 0x2E meshes (fields `_hatake*`, fences `_saku*`, rock walls `slab_*`, trees, `tobi` birds), textures, `weat/suny` with seven 0x2F environments (00:00, 05:00, 06:00, 12:00, 17:00, 18:00, 21:00), stars and moon. The spot, direction and hours are matched by eye to the capture. Tracked in [#558](https://github.com/jimmy58663/GordianXI/issues/558).
- `ROM/0/24`-`26` (`sel_`) are **not** the select scenes: they are section files like the title's (0x06 routes `s101`...; `main` sets the zone with op 0x7B and loops `mov1`, a 7,300-9,000-frame camera flight with op 0x7D clock changes and op 0x7C `suny`) over zones 231 (Northern San d'Oria), 235 (Bastok Markets) and 239 (Windurst Walls): read as the creation nation step's city flights (not drawn yet). **Differs from xi-tools** (`docs/dats/ROM_0_24.md`), which reads them as character-selection control with unknown `s###` records: those are 0x06 camera routes, `suny` is op 0x7C's weather.
- Verified offscreen (`LobbyStageRenderTests`, `lobby_stage_*.png` with `GORDIAN_UI_DUMP`): the list at 16:00 and 18:00, the delete list and creation, the model on the grass.

An error shows its message lines and then the code line ("Error code: FFXI-3313"); **unverified** that retail shows both.

## Screens and input (`LobbyController`)

`LobbyController` (Engine `Ui/Lobby/`) is the lobby's state machine; `StockUiLobby` and `LobbyFrameRenderer` (App) draw it.

- **Licence page:** before the title menu the lobby shows `ptc8lice` (Accept / Decline, `lobbywin` #101 / #102) with `ROM/165/71` row 158, the notice about the User Agreement and Rules of Conduct, over the title art without the title buttons. Accept (the default) shows the title menu; Decline (or Cancel) leaves the lobby. It shows once per launch. Confirmed as the page retail shows by the maintainer's screenshot (image-8, round 2); its look is described under Drawing.
- **Title menu:** `loby2win` over `loby1win`; the cursor follows the buttons' authored links (wrapping). Select Character and Delete Character open the list (nothing happens without a character), Create Character starts creation ([#33](https://github.com/jimmy58663/GordianXI/issues/33)), Back leaves the lobby; Config does nothing yet (`lobycwin` / `lobyc360` is not built: [#554](https://github.com/jimmy58663/GordianXI/issues/554), with its layout). Cancel does nothing here (retail behaviour not checked).
- **Character list:** `dbnamese` over `bgnamese`; the cursor skips free slots (LSB fills them with a one-space name) and starts on the first character. Each bar shows the name (yellow when the character must be renamed, the star when a race change is available). The selected character stands in the preview, with its name and job / level under the logo. Confirm plays the character: a `ptc2warn` status window with row 10 while 0x07 / 0xA2 run, then the ticket goes to the launcher. Cancel returns to the title menu.
- **Errors:** a refused request shows its text in `ptc5ok`; after OK the list is back, unless the server dropped the connection, in which case the lobby closes.
- **Keys:** arrows and keypad 8 / 2 / 4 / 6 move, Enter / keypad 5 confirm, Escape cancels (`ViewportWindow.HandleLobbyKey`). Every key goes to the lobby while it is open. **Mouse:** hovering a button of the window taking input moves the cursor there, a left click activates it, a right click cancels (`StockUiLobby.HitTest`). **Gamepad ([#553](https://github.com/jimmy58663/GordianXI/issues/553)):** the buttons the user's input profile gives the menu functions (`GamepadAssignments`: Confirm, Cancel and the four "Menu ..." directions; A, B and the d-pad by default) drive every screen as Enter, Escape and the arrows do, so a reassignment made in game (Config -> Gamepad, or Controls & Input) applies here too (`LobbyGamepad`, Engine; fed by the launcher's input loop). The pad is read in the menu context, a held direction repeats at the stock menus' rate, and buttons still held when the lobby appears (the A that chose Log Out) wait until let go. The lobby takes the pad while its window (the primary viewport) is the one in use (`ViewportWindowManager.GamepadLobby`); no character gets it meanwhile. Typing a name still needs the keyboard (no on-screen keyboard, maintainer 2026-11-13); on the name step the pad moves the caret, confirms and cancels. **Button hints:** none of the built lobby screens carries one. A scan of every lobby menu for the hint glyphs (the font `+`, `marubatu`, `abxy360`; 2026-11-13) found them only in `chfwin` (`+`) / `chf360` (the 360 controller's Y, `abxy360` (16, 16)), the "+ : Settings Management" window, which is not built; the help bar lines name no key. When that window is built it takes `StockUiButtonHints` as the in-game windows do.
- **Help bar:** the selected title button's or the screen's line from `ROM/165/71`.

## Character deletion (#34)

Delete Character opens the same list with row 105 in the help bar ("Select a character to delete. Deleted characters cannot be restored."). Confirm on a character opens `ptc9dele`: the warning sign, the character's name and row 172 "The data will be lost forever. Proceed?", Delete / Cancel with the cursor on Cancel, and row 229 "Select cancel to terminate the deletion process." in the help bar. Cancel (the button or the key) leaves the character; Delete sends 0x14 (status row 28 "Deleting from Lobby Server."), reads the refreshed list and returns to it on the next character, or to the title menu when none is left.

- **Round-1 bug, fixed:** the first in-game test got FFXI-3115 and a closed lobby after Delete, though the character was deleted (log: "Lobby character list: no reply from the data server"). LSB's `view_session.cpp` writes the 0x14 OK before its database work, and its `handler_session::do_read` clears the shared read buffer when that write completes; a 0x1F that arrives in between is read as zeros, fails the session-hash lookup and is dropped without a reply. `LobbySession` (then `LsbLobbySession`) now waits 250 ms after the OK, sends 0x1F again when no account prompt comes within 1.5 s, and skips a late duplicate prompt (0x01) on the data channel. Reproduced in `FakeLsbLobbyServer.LoseRequestAfterDelete` (`LsbLobbySessionTests.Delete_WhenTheServerLosesTheRefreshRequest_ResendsItAndKeepsTheSession`, which also plays another character with the +4 key) and a slow answer (`DelayRequestAfterDeleteMs`).
- **Security flow:** LandSandBoat enforces none: `view_session.cpp` 0x14 answers OK, checks that the character is on the account (else it drops the connection) and, with `login.CHARACTER_DELETION` off, refuses with 332 (shown as FFXI-3332). The 0x14 `passwd` field (retail's MD5 of PlayOnline's session password) is not read and is sent empty. LSB keeps the character in the database (`accid = 0`, `original_accid` = the account), so a deletion can be undone there.
- **Key accounting:** LSB raises the session key by 4 per deletion; the ticket of a character selected afterwards in the same lobby session carries it ([session-and-packets.md](../network/session-and-packets.md#lobby-session-35)).
- **Unverified against retail:** whether retail asks once or twice, the name line in the window, and Cancel being the default.

- **`ZoneLoadingScreen`** (Engine `Ui/`) decides and fades: the view counts as loading while the session is connecting to or zoning into a map server (`SessionState.ConnectingToGameServer` / `ExchangingCryptoKeys` / `LoadingWorldData`, which `PerformZoneTransitionAsync` enters and the next zone-in leaves), while its zone-line request waits for the server (#350) or, once in the world, until the session's zone is the zone on screen and the player's own model loads (`playerReady`: the local entity is in the world and `TryLoadEntityModel` succeeds, i.e. its look has arrived, and the zone-in has settled onto the floor with the camera following, `PlayerLocomotionController.ArrivalReady`, #350; at most 20 s, so a zone or model that cannot load does not stay black; an event's scene zone does not count). A fade-out, once started, always reaches full black, and the black then holds at least 0.2 s (`MinimumBlackSeconds`, guessed) before the fade-in, even when the zone was ready sooner, so the swap, the settle and the camera snap all happen unseen (round 3 saw unrendered parts of the zone and a camera jump through the fade). **The pose holds through the rest of the fade-out** (round 4): the maintainer's recording of 2026-10-13 (1894 x 986, 30 fps: two zone lines into cached zones and a GM `!zone 260`) showed, frame by frame, the old zone still fading while the player and camera already stood at the next zone's arrival point from S2C 0x00A (the old zone's geometry out of sight, only its fog and sky), for all three; LandSandBoat's `setPos` with a zone sends no placement before the 0x00B, so the jump is the 0x00A position.
