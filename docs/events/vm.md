# Event VM

How GordianXI runs the retail event scripts: the per-zone event files, the byte-code interpreter (`EventVm`), the entities that play an event together (`EventScene`), cutscene staging and schedulers, and the session around them (`EventDialogController`). Moved from [ui/stock-ui.md](../ui/stock-ui.md#dialog-text-chunk-6) on 2026-10-01; the dialog window, query window and NPC talk input stay there.

Related references:
- [opcodes.md](opcodes.md): every opcode, what it does, and what GordianXI does with it.
- [opcode-usage.md](opcode-usage.md): how many retail events use each opcode and sub-case (generated).
- [schedulers-and-motions.md](schedulers-and-motions.md): the scene tasks, motion packages and clip names the scripts name.
- [message-codes.md](message-codes.md): the control codes inside dialog strings.

Formats and semantics are referenced from XiEvents (https://github.com/atom0s/XiEvents) and xi-tools (https://github.com/vekien/xi-tools), restated in our own words; the code is clean-room C# in `Gordian.Core.Events`, `Resources/Events` and `Resources/Tables`.

## Event files

- *Zone files (`ZoneDialogTable.GetFileId`, `ZoneEventScript.GetFileId`):* zone z's English dialog table is file id 6420 + z (Japanese 6120 + z), its event scripts 5820 + z; zones 256-299 continue at 85591 / 85291 / 84991 + (z - 256) (the zone entity list, 6720 + z, continues at 86491 + (z - 256)). Every ROM path in XiEvents' zone list resolves to those ids in the retail file table (2026-09-28); zone 256 (Western Adoulin) is ROM9/5/53 (events), ROM9/5/101 (dialog), ROM9/5/77 (Japanese dialog), ROM9/6/45 (entities). The earlier 256-299 formulas were 256 ids low (#71). Southern San d'Oria: ROM/25/39 (16,941 messages) and ROM/21/39 (502 blocks, 4,819 events).
- *Dialog table (`ZoneDialogTable`):* first dword `0x10000000 | (size - 4)` in the clear, everything after XOR 0x80; a dword offset table (count = first offset / 4, offsets from byte 4) then control-coded strings. Message ids are LandSandBoat's `IDs.lua` text ids (24 = "Home point set!", 6439 = "Obtained: <item>.", 7239 = "You accept the mission." in that zone).
- *Event scripts (`ZoneEventScript`):* block count and sizes, then per actor (server id; 0x7FFFFFF0 = the player's block, 0x7FFFFFFF = zone events): event count, ushort offsets, ushort event ids (0xFFFE answers any id), immediate data dwords, byte code. `EventOpcodeTable` holds every opcode's length (sub-case byte for the variable ones). *Corpus walk (2026-09-28, #73, `EventOpcodeCorpusTests`):* each event entry of every retail zone with an event DAT (296 zones, 209,144 entries) is stepped from its start by the table and must land exactly on the next offset (or the end of the block's code); 99.29% do (98.27% before #73; xi-tools' `docs/events/typed_opcodes.md` lengths reach 99.30%). The misses hold inline data (strings after `1F 17`, sub-case 0x80 records). Corrections from that walk, checked against XiEvents' pseudo code where it has the opcode: 0x5F subs 2-7 = 6/16/16/18/18/14, 0x7E (CodeCHOCOBO) subs 0/1/2/4/5/8 = 6, 3 = 16, 6 = 18, 7 = 8, 0xB4 sub 0x14 = 12 / 0x15 = 2, 0xB6 subs 0x14/0x15 = 6, 0xC4 = 12, 0x75 sub 2 = 2, 0x60 subs 0/1 = 4, 2 = 6, else 2, 0xBF subs 0x20/0x40 = 10, 0x72 subs 0/1 = 4/6, 0xA6 subs 1/2 = 2/4, 0x9D subs 7/8/0x0C/0x0D/0x0F/0x10 = 6/23/8/10/10/10, 0xD4 subs 0/2 = 8.

## Interpreter

runs one entity's part of an event (see [Entities and request stacks](#entities-and-request-stacks)): control flow (0x00/0x01/0x02/0x1A/0x1B), work arithmetic and bit fields (0x03-0x15, 0x19, 0x3C-0x41, 0x57), messages (0x1D entity, 0x2B named actor, 0x48/0x49 no speaker, 0xB0), waits (0x1C, 0x6F, 0x58), the prompt wait 0x23, queries (0x24 with 0x25/0x7F; 0xD4 sub-cases 0/2 are the same query with the zone map behind it, not drawn yet), the 0x43 update handshake and the 0x47 position update (0x05C mode 1, a same-zone warp), the scripts' tables (0x9D: runs of 16-bit work references inside the byte code, read/written by index, shared through 64 zone-wide pointer slots, or jumped through), event position (0x36/0x37), control lock 0x20, entity test 0x44, facts 0x83/0x9C/0xBE and the ends 0x21/0x26; the staging, look, scheduler and session opcodes are covered in the sections below, and everything else is stepped over by length ([opcodes.md](opcodes.md) gives the status of each). Operands: bit 15 = immediate data, 0-79 locals, 4096+ the zone's shared work values (`EventWorkZone`: the server's 0x034 parameters land in slots 2-9, a choice in slot 0 (0-based; 254 cancelled), slot 1 is the 0x05B EndPara), 5888+ the 1700 block, 0x7F00+ entity facts. Message parameter n is slot 2 + n, then the 1700 block from n = 8 (`GetMessageParameter`: the home point script writes its lists there and names parameter 33 for the zone). Waits count 60 Hz frames: every opcode of a tick sees the same frame delay (the 60 Hz frames since the last tick), which 0x1C/0x6F subtract and 0x57 adds to its work value (XiEvents' `GetFrameDelay`); 0x6F starts a 16-frame sleep only when no wait is running. A tick runs up to two million opcodes (the home point script walks its tables in long loops). An event runs until an end opcode (0x00, 0x21, 0x1B with an empty stack, 0x26) or the end of its block's code, not to the next event's offset: actor blocks share code, and 18,948 jumps and calls in the retail corpus land past their event's next offset (e.g. Northern San d'Oria actor 0x010E7017, event 4865, is one call to offset 176 in a range ending at 156; #72). 0x72 (CodeGETWEATER) is stepped over: retail's sub 1 writes the weather forecast from file 7033/7037 into zone work values 2-4, which is not decoded yet.

## Entities and request stacks

(`EventScene`, [#85](https://github.com/jimmy58663/GordianXI/issues/85)) an event is played by several entities at once, as in retail (XiEvents "Event VM Functions.md": InitEvent2, XiEventInit, EventIdle; "Event VM Structures.md": `reqstack_t`). At the start every actor block that carries the event id, or the 0xFFFE catch-all, gets its own `EventVm` on its entity, all in one `EventScene` on the shared work zone: 0x7FFFFFF0 / 0x7FFFFFC0 is the local player, 0x7FFFFFC1-C5 and 0x7FFFFFF1-F5 the other members of the player's party by slot, 0x7FFFFFC6-CB and 0x7FFFFFCC-D1 alliance parties 1 and 2 (skipped when the slot is empty), anything else the NPC with that server id (target index = id & 0x3FF); the zone's block (0x7FFFFFFF) runs only when no entity carries the id. In the retail intro zones only the player's block has a catch-all, a bare 0x00, so it never adds work. Each VM has 16 request stacks (priority, program position, wait timer, slot, request flag, who asked): its own event starts in stack 0 at priority 16, and every frame each VM runs its most urgent stack (lowest priority number; 255 = free) until it yields. 0x00, and 0x1B with nothing to return to, free the running stack; 0x21 ends the whole event (retail's global `EventExecEnd`), as does a cancelled query. The event is over on that end, or once every entity that carries the id itself has no stack left (catch-all-only entities do not hold it open). The message window is the scene's: 0x23 on any entity waits while a line is open. 0x1C / 0x6F waits are per stack, 0xBE stores the entity that asked for the running request.

*Companion requests:* `27|28|29 priority actor:u32 slot` queue a request on the named entity (XiEvent::ReqSet): it runs the event at that **slot of its own offset table**, not that event id (xi-tools `docs/events/retail-events.md`, "The one rule"); 0x27 goes on at once (retrying while the entity has no free stack), 0x28 waits until the entity has started it, 0x29 until it has finished it; `2A priority actor:u32` waits until the entity has nothing queued at or above that priority (XiEvent::GetReqLevel). An entity outside the event is skipped. XiEvents' decompiled status tests for 0x28/0x29 read inverted against the opcodes' PS2 names (CodeREQSW / CodeREQEW: start wait / end wait) and would never release an end wait, so the waits follow the names.

*Tested in-game (2026-09-30):* NPC talks work and the intro cutscenes play (without their camera); the cutscene-only NPCs now disappear at the end (see below).

*Checked (`MultiEntityEventTests`, `EventSceneTests`, 2026-09-30, retail DATs):* Bastok Mines event 1 runs on 22 entities: NPC 0x010EA001's block narrates and has Deidogg (0x010EA003) and Gumbah (0x010EA004) speak through 66 request opcodes, ending with 0x21 after about 26 s of waits (before, only the player's 8 bytes ran and the event ended at once); Windurst Woods event 367 (13 entities) plays Nanaa Mihgo and the Star Onion Brigade from NPC 0x010F100B's block; Bastok Markets event 0 (17) and Port Bastok event 1 (16, the player's block directs) run to their end; in Southern San d'Oria's event 663 the player's block has Femitte ask "Rouva?" and Rouva (0x010E60C4) answer from her own block. Many event ids are carried by several NPC blocks (Southern San d'Oria: 141 of 749), the shared staging of a scene; Home Point events are one per crystal (8700-8702 each on one block).

*Cutscene-only NPCs:* LandSandBoat keeps an intro's extra NPCs at status Disappear (2) or CutsceneOnly (6), which is the low byte of the entity update's Flags1 and so sets its HideFlag; it sends them only when asked (our C2S 0x016 at the event's start). The renderer does not draw an entity with HideFlag unless it takes part in the running event (`WorldEntity.IsInEvent` / `IsDrawn`; actor effects likewise), so they appear for the scene and are gone once it ends (the maintainer's in-game test, 2026-09-30: before this they stayed visible after the Windurst Woods intro; LandSandBoat `data/enums/status.yaml`, `src/map/packets/entity_update.cpp`, `0x016_charreq.cpp`).

## Cutscene staging

([#86](https://github.com/jimmy58663/GordianXI/issues/86), first part, 2026-09-30) the scripts now place, walk, turn and hide the entities of the event. Each VM keeps its entity's event position and heading (retail `EventPos` / `EventDir`), starting where the entity stands (XiEventInit); from the first staging opcode on, the event owns the entity's pose (`WorldEntity.EventPose`) and the renderer draws it there instead of its server position (retail CopyAllPosEvent), on the floor below it; the local player's own position stays the controller's, only its drawing moves. Opcodes (semantics from XiEvents OpCodes): 0x36 / 0x37 place the entity (operands x, y, height, and 0x37 a heading of 4096 steps per turn; internal Y is the height), 0xBA places another entity of the event, 0x32 sets the walk speed (tenths of a yalm per second; default the entity's speed byte / 10, else 4.0), 0x1F sub 0 stores a goal in the running stack and sub 1 walks toward it at that speed, facing its way, one frame at a time until it arrives (0x5A the same in three axes); an entity whose place is unknown (not in the zone and never placed) is put at the goal at once. 0x39 sets the heading, 0x4B another entity's, 0x1E turns toward an actor and 0x4A turns one actor toward another (both also set the head look, below). While walking, the entity plays its walk (up to 2.5 yalms/s) or run clip (`AnimationStateClassifier`), else it stands. 0x22 / 0x4E set the event hide flag (`WorldEntity.IsEventHidden`, retail `Render.Flags0` bit 17), which the renderer honours (`IsDrawn`: not event-hidden, and not server-hidden unless in the event). 0x67 turns on the event message mode and 0x68 turns it off (see [Event message mode](#event-message-mode-and-late-arrivals)). 0x77 stops the session's clock at an hour (`WorldState.LockTimeOfDay`, read by the sky and lighting) and / or sets the weather, 0x78 undoes both. The mode flags of the event (`CutsceneFlags`, from LandSandBoat `scripts/enum/cutscene_flag.lua`): NO_PCS hides the other players and NO_NPCS the NPCs and monsters that take no part (entities that arrive after the start are sorted as they come: see [Event message mode and late arrivals](#event-message-mode-and-late-arrivals)). When the event ends every pose and hide flag goes back, the cutscene HUD ends and the clock and weather are released.

*Tested in-game (2026-09-30):* cutscenes play with their actors placed and walked, without the camera; Prince Trion in a Southern San d'Oria scene slid without a walk cycle and a weapon or shield seemed to hit the floor ([#163](https://github.com/jimmy58663/GordianXI/issues/163)).

*Checked (2026-09-30, retail DATs):* all nine intros (ten events) run to their end on every entity (`MultiEntityEventTests.NewCharacterIntro_RunsToItsEnd`: 14 to 111 s of script time with each line confirmed at once); the Windurst Woods intro from S2C 0x00A with LandSandBoat's flags hides the bystanders, hides the four NPCs its blocks flag (`22 01`), walks Nanaa Mihgo, stops the clock and gives it all back at the end.

### Actor opcodes ([#166](https://github.com/jimmy58663/GordianXI/issues/166), 2026-10-01)

0x5E / 0x6B (stop the entity's action and return it to idle; the idle name they carry, `idl0` / `dft0`, is not used) end the event gesture playing (`ActionMotion.EventMotionStop` with an empty name). A turn (0x39 / 0x4B / 0x1E / 0x4A) keeps the entity "turning" for the time the viewport's ease takes to arrive (`ln(angle / 0.05) / 8` s; retail's own rate is not measured) and 0x76 / 0x70 wait for it (retail `Render.Flags3` bit 1); 0x80 (wait for the action resources) passes at once. 0x2F (Render.Flags0 bit 19), 0x33 (bit 21), 0x7C (Flags2) and 0x42 (cancel flags) are stepped over without a diagnostic: the scripts use 0x2F only beside the 0x22 / 0x4E hide that does the work (Southern San d'Oria: `2F 00 actor` then `4E 00 actor` to show, `4E 01` then `2F 01` to hide).

### Head look ([#174](https://github.com/jimmy58663/GordianXI/issues/174), 2026-10-01)

0x1E, 0x4A and 0x79 sub 0 / 1 call retail's lookatone (XiEvents "Event VM Functions.md": the entity's InteractionTargetIndex, a Render.Flags3 look mode and its NpcSpeechFrame, 6 from these three, a work value from 0x79 sub 1); here they set `WorldEntity.EventLook` (target and speech frame), and 0x7B (`op actor:u32`) clears it. The renderer turns the head toward the target while the body keeps its heading (`HeadLook`, see [world/entities-and-animation.md](../world/entities-and-animation.md)); the maintainer's retail recording shows Ceraule's head turning to the player as they walk up (2026-10-01). Tested in-game (2026-10-01): the heads turn. 0x79 sub 2 (a look axis from two work values, Flags3 mode 2) and 0x59 sub 2 / 3 (the head turn speed) hold the head on a fixed axis, read provisionally as a turn and a tilt ([#188](https://github.com/jimmy58663/GordianXI/issues/188), see [world/entities-and-animation.md](../world/entities-and-animation.md)).

### Talking mouth ([#185](https://github.com/jimmy58663/GordianXI/issues/185), 2026-10-01)

each line an actor speaks plays its skeleton's mouth clip `mou4` once (three flaps over 2 s; looping it while the speech frame was set left mouths flapping through other actors' lines in the in-game test, 2026-10-02), and every humanoid blinks with `eye3` (`FaceMotion`, see [world/entities-and-animation.md](../world/entities-and-animation.md)). The face texture's corner patches are not alternate frames: the dark square is the inside of the mouth and the other patch the eyeball, both always mapped, and the mouth and eyelid joints move the face vertices over them. The speech frame is kept but not drawn; what its value (6) changes in retail is not known. The 0x79 sub 2 look axis is [#188](https://github.com/jimmy58663/GordianXI/issues/188), done provisionally.

### Emotes and the mode mask ([#176](https://github.com/jimmy58663/GordianXI/issues/176), 2026-10-01)

0x6E (`op actor:u32 value:u16`, XiEvents OpCodes/0x006E) plays an emote on the actor: the work value's low byte is the emote id of C2S 0x05D / LandSandBoat's `Emote` enum (13 clap), its high byte a variant passed along; while the actor still plays an event action the opcode waits. The emote is the race's own motion (`EmoteMotion`, see [world/entities-and-animation.md](../world/entities-and-animation.md)); a fixed-model NPC has none and the opcode passes at once. The two uses are Rahal's clap in the Southern San d'Oria intro (emote 13, right before his line "General Curilla, bravo.") and Northern San d'Oria's 0x010E70C5 after "But, I ramble. Many pardons!" (emote 6, no); the id reading follows the line, and the maintainer's retail recording, shot from behind Rahal, shows his arms brought together in front at that moment (2026-10-01). 0x99 (`op actor:u32`) yields one frame while the actor plays an action and then goes on: retail steps past it before yielding, so it does not wait for the end. 0x38 stores its mask (`EventScene.EventModeLocal`: the operand's low byte | 0x2000, retail `CliEventModeLocal`): the Southern San d'Oria intro sets 0x13 for its aerial shots and 0x03 at 25 s when the player walks in, Bastok Markets 0x12; which bit does what is not known, so nothing reads it yet.

### Another zone for a scene ([#175](https://github.com/jimmy58663/GordianXI/issues/175), 2026-10-01)

0x34 / 0x35 (`op zone:u16`, XiEvents OpCodes/0x0034, 0x0035: delete every actor, yield while the map loads, XiZone::Open on the work value) open another zone for the scene. The Windurst intros are the only users: Windurst Waters (238/531), Windurst Woods (241/367) and Port Windurst (240/305) open Windurst Walls (239) with 0x34 at their start, lock the clock at midnight (0x77) and show only camera shots (0x45 tasks `s000`-`s005` of file 0x8B and the `fdi?` / `fai1` fades) under seven timed narration lines, with no actor placed; then 0x35 opens the player's own zone again (the operand's immediate data, read with the retail DATs). Here the VM asks the host to open the zone (`IEventVmHost.OpenEventZone`): `WorldState.EventZoneId` holds it (0 when it is the session's own), the viewport loads that zone's terrain, sky and lighting in place of the current zone's (`SceneZoneId`) and draws no entity and no name plate while it is open, and the opcode waits until the viewport reports it drawn (`DisplayedZoneId`), at most 15 s (a session not on screen waits that long). The player's collision stays the own zone's. The event's end, or a zone change, clears it. With the narration's own timing the Windurst Walls scene lasts about 85 s (`MultiEntityEventTests`); tested in-game (2026-10-01). The maintainer's retail recording of the Windurst Waters intro as a Galka (2026-10-02, recorded from the moment the character enters the game) is black for its first 24 s (the login zone load and then the Windurst Walls load, with only the HUD minimap drawn), shows Windurst Walls from 24 s to 90 s with three short fades to black between shots (34-37 s, 53-56 s, 72-75 s), then is black again for 18 s (90-108 s) while 0x35 loads Windurst Waters back. The black stretches are load time, not script time: nothing in the script waits there, and how long they last depends on the machine. The retail scene's 66 s is shorter than the 85 s estimate above, which is not yet explained. Still stepped over: 0x5C / 0x5D music and 0x69 / 0x6A sound volumes ([#167](https://github.com/jimmy58663/GordianXI/issues/167)), 0xC8 / 0x8B / 0x8A the world-map tutorial ([#168](https://github.com/jimmy58663/GordianXI/issues/168)).

## Cutscene schedulers

([#165](https://github.com/jimmy58663/GordianXI/issues/165), 2026-09-30) Camera, fades and gestures. The scheduler opcodes now run instead of being stepped over.

**Scene tasks:** 0x45 (`op p:u16 actor:u32 target:u32 routine:u32 value:u16`) plays a routine of the scene resource DAT `p` names (from the block's immediate data; file `30704 + p` below 300, `56641 + p` for 300-599, `70347 + p` above: XiEvents OpCodes/0x0045 `FUNC_DatIdHelper`, xi-tools `docs/events/camera_scene_ids.md`) as a task on the two actors; the task lasts the routine's length (header +0x1C, 60 Hz frames), 0x52 stops it, 0x55 waits while it runs, and the same task started again replaces the old one. A task whose file or routine is missing lasts no frames, so a wait on it never holds the scene; a task on an actor that is not in the zone is stepped over (retail). The trailing value of 0x45 (0 in every intro) is not used.

**Scene resources (`EventSceneResource`):** `evte`, camera Routes (Section 0x06, `CameraRoute`: a 32-byte header with flags at +0x00, the key count at +0x10 and an easing mode 0-4 at +0x14, then 48-byte keys: eye, focal length, look-at, roll, normalized time; the vertical field of view is `2 atan2(192, focal)`, 350 = 57.5 degrees; layout from xi-tools `docs/events/scene_dat_writer.md`), routines (Section 0x07, `SceneRoutine`, read with the effect routines' command walk: each command runs at the sum of the delays before it) and particle generators. The command meanings were read from the retail files (the Port Bastok and Windurst Woods intros' 30840 / 30843 / 30845 and the shared 30904, 2026-09-30): op 0x04 plays the Route its FourCC names (every `sNNN` shot plays `cNNN`) over its duration; op 0x0F moves the 3D scene's colour to its B, G, R bytes (0x80 = as drawn; `fdo?` fade to 0, `fdi?` back to 0x80, and the Port Bastok opening shot `s00s` starts black and fades in with its first move); op 0x51, same layout, is read as the 2D interface's fade (`fao?` / `fai?`: the Windurst Woods intro alternates them on a black screen while its narration lines come and go). Op 0x0E (blur) and 0x10 (cross-dissolve) are played since #205 ([Post-process](#post-process-blur-and-cross-dissolve)). Not played: sounds (op 0x60, [#167](https://github.com/jimmy58663/GordianXI/issues/167)). Effects are played since [#192](https://github.com/jimmy58663/GordianXI/issues/192) (next paragraphs).

**The second scene range (0x9F / 0xA2 / 0xA3, [#192](https://github.com/jimmy58663/GordianXI/issues/192), 2026-10-02):** the same task, wait and stop on file `51183 + p` without 0x45's remapping (XiEvents OpCodes/0x009F, 0x00A2, 0x00A3; `EventSceneResource.GetSecondFileId`). Port Jeuno event 324 starts the blink and the sky flash this way.

**White fades and flashes (op 0x72):** `op size delay duration B G R A`, like 0x0F, but the colour is added over the scene at full scale (FF FF FF = white): `who0`-`who3` of 30905 go to white, `whi0` / `whi1` back to 00 00 00, and 324's `fall` flashes 44 30 3A for 6 frames. `EventPresentation.SceneFlash` follows them like the fades, and the HUD adds it over the 3D scene under the interface (`StockUiRenderer.DrawScreenFlash`). The recording's white-out (about 1:37-1:41), grey at 1:42 and black from 1:43 match `who?` followed by the black card. *Read from the retail files, not established:* the issue's guess that 0x73 is the fade back is wrong: in 51327 0x73 names routines (`loop`, `tama`), see below.

**Effect commands (`SceneEffectPlayer`):** the effect routine commands of the zone runtime run inside scene routines too. Read from 324's scene files (51402, 51327, 51328; meanings inferred from how the routines use them): 0x02 starts a generator of the file emitting for the command's duration; 0x1E kills one (only `kill`, after `bl00` started it); 0x3F names two generators in 8-byte slots (+8 and +16) and replaces the first, which an earlier routine left running, with the second (`bk00` -> `bk01`, `mb00` -> `mb02`); 0x03 starts another routine of the file, 0x73 starts one repeating, 0x5F stops one by name (51327's `stop` ends `loop` and `tama`, which `mai1` / `mai2` started). A stopped routine starts nothing more and its particles live out their life; a task stop (0x52 / 0xA3) ends only the task's own routine, not the ones it started, since the files stop those by name. One player serves every task of the same file on the same actor, so one task's `kill` reaches another's `bl00`. The scene file's generators are loaded like a model's (`ResourceManager.GetSceneEffects`, `ActorEffectLoader` with `cameraEffects`) and run as an `ActorEffectInstance` on the task's first actor: in its model space at the generator's joint reference (the model origin for unattached generators), at the actor's event position when it is not drawn (the invisible marker 0x010F608F of the sky flash). Camera-following generators (setup flag 0x04: the blink's black cards `bk00`-`bk02` 0.3 in front of the camera, `fall`'s `bl00`, the sparkles `tub5` / `tub6` of 70443) are simulated in camera space (raw DAT axes: +Z ahead, -Y up) and drawn at the eye (`ZoneTerrainRenderer.UpdateSceneEffects`); the second in-game round showed the sparkles falling where retail has them rise, from the display flip applied twice, checked offscreen since (`SceneEffectRenderTests`). Nothing in a scene file runs by itself: an auto-running generator there (all of 70443's) waits for its spawn and then emits until a kill (`ZoneParticleEmitter.StartsOnTrigger`), which is how the files use them (`s002` spawns, `kil2` kills). Every scheduler band runs (#199), so 0xCD's sparkles play too. The presentation logs each task with effects (`EventPresentation.CopySceneEffects`) and the renderer follows the log. Not played: 0x05 (a motion clip, `o0l0` / `ban2`, on the actor), 0x29 / 0x43 / 0x46 / 0x48 / 0x54 (colours and values of 51327's `cas1`, meaning not known), 0x22, 0x7F ([#206](https://github.com/jimmy58663/GordianXI/issues/206)); generators drawing weighted meshes (the eye-shaped mask `mb00`-`mb02`) are drawn since #204, so the blink opens as an eye ([particles.md](../rendering/particles.md#weighted-meshes-0x25)).

<a id="post-process-blur-and-cross-dissolve"></a>**Post-process: blur and cross-dissolve (#205, 2026-10-02).** Op 0x0E carries B, G, R, A at +8 and a float at +12 and moves toward them over its duration like the fades (`SceneCommandKind.Blur`, `EventPresentation.Blur`). The values in the retail files: `blon` A0 A0 A0 30 / 0.98 over 15 frames and `blof` 80 80 80 00 / 1.0 (30904; 30812's `blon` 80 80 80 1E / 0.98 over 30, `blof` over 60); the `0dkn` / `1dkn` pulses jump to 80 80 80 2D / 0.92 and return to 00 / 1.0 over 40-50 frames, `ati1` / `ato1` to 28 / 0.95; Port Jeuno 324's `fall` (51328) goes to 80 80 80 20 / 1.0 over 40 frames at frame 22 and back over 18 at 77. It is read as the feedback motion blur: A how much of the previous frame each frame keeps (0x80 = all, like the fades' 0x80 = full; 0 = off), B G R its tint (0x80 = as drawn; `blon`'s A0 brightens the trail), the float its zoom about the screen centre (below 1 the trail spreads outward). *Inferred* from the values (A returns to 0 in every `off`; the float is 1 where only A changes); the retail recording of 324 at 2 frames per second does not show the trail, so the in-game test settles it. Op 0x10 carries only its duration (`ovl1` / `ovl2` 60 / 120 frames, 30812's `olp1` / `olp2` 60 / 90): a cross-dissolve from the frame before it into the scene (`SceneCommandKind.CrossDissolve`, `EventPresentation.CrossDissolve`). While the event holds the camera (0x46), a shot runs, or either effect is on, `ZoneTerrainRenderer` draws the 3D scene into an offscreen target and `ScenePostProcess` composites it: the previous composited frame tinted, zoomed and mixed in by the blur amount, then the frame held when the dissolve started mixed in by its remaining share, into a history target that is the next frame's previous frame, then copied to the real target; the stock UI and its screen tints draw on top as before. The blur's per-frame amount and zoom are raised to the frame's 60 Hz frame count, so the trail does not depend on the frame rate. Ctrl+F8 turns the post-process off and on in the viewport (`ZoneTerrainRenderer.EnablePostProcess`), to compare. Checked offscreen over Bibiki Bay (`ScenePostProcessTests`): the pass-through is pixel-exact, `ovl1` starts on the shot before the cut and is half-way at 30 of its 60 frames, `blof` leaves the scene as drawn.

*First in-game test (2026-10-02):* the white flash, the black fades and the lightning from `fall` showed; the explosion and the floating sparkles did not. The explosion's marker is held about 50 yalms up by 0x59 sub 5, which was stepped, so the marker was drawn on the street with the explosion under the floor (0x33 / 0x59 sub 5 now keep the placed height, [opcodes.md](opcodes.md#0x59)); the sparkles are 0xCD's, a band that was stepped, and their colour rate (updater 0x0B) was read in 0-1 units instead of colour bytes, so they went black in two frames ([rendering/particles.md](../rendering/particles.md)). *Checked offscreen (2026-10-02, Port Jeuno rendered with the retail scene files):* with the marker at its event position `mai1` / `mai2` draw the magenta cloud, its white core and wisps as the recording shows them (about 1:13-1:30), and `s002` draws the sparkles until `kil2`. `bl00` takes the frame to black (mean brightness 20.9 -> 0.0) and `open` holds it for about 90 frames and brings the scene back by frame 240; `fall` draws its glows and beam above the director and dims the screen with its black card; `mai2` raises its beam at the marker. Not yet compared in game.

**Presentation (`EventDialogController.Presentation`, `EventPresentation`):** the controller loads each scene DAT once per zone and schedules a routine's shots and fades on a clock from its start; the viewport samples them every frame. The shot started last holds the camera (`ViewportCamera.SetEventView`, display axes (-x, -y, z) like the rest of the scene; the orbit camera keeps its own state and takes over again when released); a move runs over its duration and then holds its last pose (a still of duration 0 holds its first key) until another shot starts, 0x52 stops it where it is, and 0x46 00 (retail kills every camera task and gives the camera back) or the event's end releases it. 0x46 01 marks the camera held and 0x46 02 reads it (0 while held). A fade moves from the colour on screen when it starts; the scene fade is a full-screen quad under the stock UI (black with opacity 1 - colour, white added above 1) and the interface fade scales the stock UI's opacity (`StockUiRenderer.Opacity`). Actor-relative Routes (flag bit 0, seen on a ship shot and the shared twelve-direction orbit shots whose points lie a few yalms around the origin) are placed at the task's first actor where the event shows it, not turned with it.

*Chosen, not established:* the easing modes follow the five smoothing kinds a client reimplementation names (xi-tools `docs/events/cutscenes.md`: 0 linear, 1 decelerate, 2 accelerate, 3 decelerate to the midpoint then accelerate, 4 accelerate and decelerate); two keys join by a line, more by a Catmull-Rom curve through the keys; holding the last pose after a move (xi-tools reads retail's camera task as deleting itself and reverting to the default framing, which the intros never show because they wait for each shot).

**Gestures:** 0x2C (`op actor:u32 target:u32 routine:u32`) plays one of the actor's own motion routines; 0x5B (`op resource:u16 actor target routine`, 15 bytes) first loads the event motion DAT `resource` names onto it (`32104 + n` below 512, then `49135 + n`, `56345 + n` from 1024, `59739 + n` from 2048, `66339 + n` from 3072: XiEvents OpCodes/0x005B ReadEventMotionRes) and 0x66 plays from its player-model motion package (ReadTpcEventMotionRes; located for [#176](https://github.com/jimmy58663/GordianXI/issues/176), 2026-10-01: package n is file `32360 + 2n` with the gestures' waist part, else `32712 + n` without it, loaded onto the entity like a 0x5B bank, `EventMotionBank.PackageFileIds`; the San d'Oria intros' packages 20, 21 and 29 are Elvaan talk, salute and thought sets, which the maintainer's in-game test of the emotes showed missing: every gesture of the Southern San d'Oria intro but Rahal's clap is a 0x66); both yield a frame after starting (RetFlag 1). Routine 0 and `xxxx` start nothing. The gesture is an `ActionMotion.EventMotion` request on the entity's `EntityAnimationState`: it kills the action playing (retail KillLastAction), and plays from the entity's event motion banks (`EventMotionBank`: the `mot_` DAT's routines and clips; bank 70 = file 32174 holds `tlk0` / `tlk1` / `thk0-2` / `pas0` / `tla0`...), newest first, then the model. The event remembers each entity's gesture for its one-pass length (a looping last clip counted once): 0x53 waits while it plays and 0x50 stops it. Banks are dropped when the event ends.

*Checked (2026-09-30, retail DATs):* every Port Bastok and Windurst Woods task finds its routine; all nine intros run to their end with the waits held for the real routine and gesture lengths (`MultiEntityEventTests`, 32-199 s of script time with each line confirmed at once); the Port Bastok shots rendered offscreen from their Routes frame the city's arches, harbour and tower from inside the zone.

*Tested in-game (2026-09-30):* the Southern San d'Oria intro as a Mithra, compared with the maintainer's retail recording over four rounds (the fixes below); the other intros are not compared with retail yet. Zone schedulers (0x2D / 0x51 / 0x54) stay stepped over.

## Event message mode and late arrivals

([#165](https://github.com/jimmy58663/GordianXI/issues/165), second round, 2026-09-30; checked against the maintainer's retail recording of the Southern San d'Oria intro as a Mithra).*

**Event message mode:** 0x67 (`op a:u16 b:u16`, two work values; XiEvents OpCodes/0x0067: PresetEventMessageMode on both event message objects, and the whole HUD hidden) turns it on, 0x68 off. While on, `EventDialogController.IsCutsceneHud` hides the HUD windows (log and input windows, party and alliance windows, target cursor and window, status icons; menus, the query window and the name plates stay: the recording shows every NPC's plate, and the player's, through the aerial shots with the log hidden, 2026-10-01); the name plates fade with the scene's own fades (`fdo?` / `fdi?`: drawn at the scene's brightness times the interface opacity), so they are gone while the screen is black (maintainer's request after the #176 test, 2026-10-01), and an event line goes to `EventDialogController.EventText` instead of the log: the HUD draws it in the log font, white with a one-pixel dark shadow, lines 16 layout pixels apart, while the line is open. The recording shows the narration at the top left, the log and party window hidden until the scene's 0x68, when Ceraule's talk goes to the log. Placement (third round, 2026-09-30): each narration line carries its own screen position, message code `0x02 x:u16 0x03 y:u16` (the Southern San d'Oria lines start `02 50 00 03 54 01`: x 80, y 340; the decoder had read it as a 5-byte code and swallowed the next 84 bytes as a name block, which showed as `<u0>` / `<f0>` and cut the lines' starts). The HUD puts the text's left edge at x and its first line's middle at y, in pixels of the recording's 1416-pixel-high client area, scaled to the screen's height so it stays near the top left at 1080p too (`StockUiHud.DrawEventText`; measured: x 78, top 332 at UI scale 1). A line without the code falls back to the 0x67 values, whose meaning is not known (100 / 380 here; Port Bastok 80 / 340, Windurst Woods 80-130 / 80-340).

**Gender words:** `0x7F 0x85 "[his/her]"` picks by the player's sex (the look's race byte: 2, 4, 6 and 7 female), as the recording shows (a Mithra's lines read "her" and "she"); left as written when the look is unknown.

**Timed lines:** the message code 0x7F 0x34 n closes a line by itself after n seconds (`EventMessage.AutoCloseSeconds`; the narration carries 9 and one line 5, and the recording shows them for 9.2-9.3 s and 5.1 s, text gone as the `fdo1` fade starts). Lines without it still wait for Confirm: the talk after 0x68 carries only the prompt (0x7F 0x31), and the recording's auto-advance of those lines is presumably the Enternity addon, as in the chunk 6 recordings.

**Late arrivals:** a zone-in event comes with the zone, before the zone's NPCs (the recording's session: the event at 13:54:53, its 35 NPCs at 13:55:00), so a zone-in start (`CutsceneEventInfo.FromZoneIn`) waits up to `ZoneInEntityWaitSeconds` (15 s) for the first of them, then `EntityWaitSeconds` (1.5 s) after the last one that came. An entity that still arrives after the start is sorted on the next tick (`SortArrivals`): one taking part is marked as in the event (drawn though the server hides it) and gets the pose and hide flag its script gave it meanwhile (kept by `SetEntityPose` / `SetEntityHidden` until it comes); any other is hidden by NO_PCS / NO_NPCS. Before this, the soldiers, Rahal and Curilla stayed invisible. **Hidden participants (fourth round, 2026-09-30) * an entity the server hides (a cutscene-only NPC) that takes part in the event starts with its event hide flag set, so it stays out of sight until the script shows it with 0x4E 00 / 0x22 00. The Southern San d'Oria intro places the returning knights (0x010E60D5-DC) at its start and shows them only for their scene with 0x4E 00, with nothing hiding them before; drawing every participant had them standing at the gate from the start (the retail recording: absent at 1:21, walking in at 1:50). The Windurst Woods intro shows the hidden Nanaa Mihgo the same way. 0x2F (`op n actor:u32`) sets Render.Flags0 bit 19, not the hide bit (XiEvents OpCodes/0x002F); the scripts pair it with the hides, but nothing else is known about it, so it has no effect here (#166). The mapping from the server's hide state to the event hide flag is inferred from these scripts.

**End of the event:** an entity the event placed goes straight back to its server position and heading (`SnapToTargetPending`), instead of walking back from the event's spot.

## Session

S2C 0x032/0x033/0x034 start the event on every entity that takes part ([Entities and request stacks](#entities-and-request-stacks)) and end it with the work zone's end value (0x40000000 after a cancelled query); without scripts the event is ended at once so the server never waits. Before starting, the NPCs whose blocks carry the event and that are not in the zone are asked for with C2S 0x016, and the start waits for them up to `EventDialogController.EntityWaitSeconds` (1.5 s; retail waits for all), then runs anyway. Checked on Northern San d'Oria's zone-in cutscenes (`ZoneInCutsceneTests`): event 878 (Seekers of Adoulin 1-1) is carried by eight NPC blocks, Anilla's directs it (the "Start Seekers of Adoulin?" query and 13 lines) and the other seven only toggle render flags (0x92). A zone-in event from S2C 0x00A (see [session-and-packets](../network/session-and-packets.md)) starts the same way as an event of the player, after the zone change, so it reads the new zone's scripts ([#122](https://github.com/jimmy58663/GordianXI/issues/122): before that the client ignored it, and LandSandBoat kept the character in the event, refusing NPCs and logout); the VM ticks with the locomotion update; the character is held (`IsMovementLocked`) until the event ends; a prompt line stays open until Confirm or Cancel, and the log draws the `kaipage` page-wait arrow (the six-frame gold arrow, stepped like the target cursor) 2 px after the line's text while it waits (retail holds the character and shows that arrow; the maintainer's first recording only seemed to auto-advance because the Enternity addon pressed Enter); 0x43 sends 0x05B mode 1 and waits for 0x052 mode 1 (`EventUpdateAcknowledged`); the end sends 0x05B mode 0 with work value 1 (0x40000000 after a cancelled query); 0x052 mode 2 drops the event, a zone change drops everything. 0x052 mode 0 no longer ends the event (it is the control release retail sends after every end and update). Lines go to the log as `Name : text` on the first line (channel `Dialog`, white until the Font Colors defaults are captured, [#53](https://github.com/jimmy58663/GordianXI/issues/53)); the recording confirms the `Name : text` form ("Authere : ...", "Rolandienne : ...") and shows wrapped continuation lines indented by two spaces (a log-wide rule, not done).
