# Command Console & Input

> The in-client command console, `PlayerActionService`, and keyboard/mouse/gamepad input (Phase 5). Status and open work: [ROADMAP.md](../../ROADMAP.md) and GitHub Issues.

## Command console and action service

- Unified `PlayerActionService` in `Gordian.Core` (typed methods for combat, magic, abilities, targeting, and locomotion)
- In-client interactive console tab in `Gordian.App` with history navigation (Up/Down arrows), color-coded output, autoscroll, and slash commands (`/pos`, `/target`, `/attack`, `/ws`, `/magic`, `/vitals`, `/nearby`, `/moveto x y z`, `/collision [ground|walls|entities|all] [on|off]`, `/anchor [on|off]`, `/uilayout [scale n | reset | <window> <args>]`, `/lockstyle [on|off]`, and the C2S 0x01A kinds `/fish`, `/dig`, `/sprint`, `/blockaid [on|off]`, `/callforhelp`, `/monsterskill <id>`, `/refa <name|all>`, and while dead `/homepoint`, `/acceptraise [decline]`, `/accepttractor [decline]` (GordianXI commands for the death menus, #103); see [session-and-packets.md](../network/session-and-packets.md#c2s-0x01a-action-kinds)), and the everyday commands `/heal [on|off]`, `/sit [on|off]`, `/sitchair [n] [on|off]`, `/logout [on|off]` and `/shutdown [on|off]` (C2S 0x0E7, [#270](https://github.com/jimmy58663/GordianXI/issues/270)), `/random`, `/nominate [scope] "question" "option" ...` (`/propose`), `/vote <n> [proposer]`, `/widescan`, `/track [index|name|off]` (`/untrack`), `/conquest` (`/cq`) and `/jobmasterdisp on|off` (C2S 0x11B, [#115](https://github.com/jimmy58663/GordianXI/issues/115)); see [session-and-packets.md](../network/session-and-packets.md#everyday-commands-111). `/jump` sends the character's own target index, which LandSandBoat requires. Wide scan lists, vote text and the conquest summary print to the message log until their windows exist Debug audio commands, client only: `/playsound <id> | stop` and `/playmusic <n> | stop` ([audio.md](../design/audio.md#debug-commands)).
- **Spells, job abilities and weapon skills by name ([#240](https://github.com/jimmy58663/GordianXI/issues/240), [#353](https://github.com/jimmy58663/GordianXI/issues/353), awaiting the in-game test).** `/ma` (`/magic`, `/cast`), `/ja` (`/jobability`) and `/ws` (`/weaponskill`) take the name as retail does: quoted or not, any case, extra spaces ignored (`/ma "Cure IV" <t>`, `/ma cure iv <t>`, `/ja Provoke Forest_Hare`), or the numeric id as before. Names come from `ActionCatalog` (Core `Actions/`): the client's spell and command tables (file id 81, `SpellCommandTables`) with the d_msg name tables ROM/181/73 (spells, row = spell id) and ROM/181/72 (commands: weapon skills at their id, job abilities at 512 + the LSB ability id), loaded once from the game's resources by the app (`ActionCatalog.Provider`). `ChatCommandRouter.SplitActionArguments` splits name and target: a quoted name, then anything; an unquoted name ending in a placeholder; a number, then anything; else the whole text is the name, and the action service splits a trailing target name off when the whole text is not a known name (`/ma Cure Gemini`). Targets: a name, or `<t>` (current target), `<me>` / `<p0>`, `<p1>`-`<p5>` (party slots, party window order), `<bt>` (the engaged monster), `<lastst>` (the last sub-target), and the **sub-target cursor** `<st>` (any target the action allows), `<stpc>` (players), `<stnpc>` (NPCs and monsters), `<stpt>` (party), `<stal>` (alliance). Without a target an action only you can take (target bits 0x01: Trusts, Berserk) goes on yourself, anything else opens the sub-target cursor (PROVISIONAL: that retail does the same for a macro without a target). Without the game's tables only numbers work and no target means the current target, else yourself, as before. Unknown names and missing targets warn and send nothing; whether the action is learned, the MP, TP and recast are left to the server for typed commands. Casting or using a job ability on yourself now sends your own ActIndex (it was 0; LandSandBoat finds the target by the index, so `/ma ... <me>` failed). The C2S 0x01A kinds are cast magic 3, weapon skill 7 and job ability 9 (LandSandBoat `c2s/0x01a_action.cpp`).
  - *Sub-target cursor (`SubTargetSelection`, `PlayerActionService.BeginSubTarget` / `BeginItemSubTarget`):* the entry point for anything that needs a target picked on screen: typed placeholders, every spell or ability chosen in the Magic and Abilities windows (even self-only ones: the maintainer's retail video, 2026-10-11, Advancing March), ranged attacks from Abilities, and item use (`BeginItemSubTarget(container, slot, itemId, validTargets, preferred)` maps the item DAT's target bits, 0x01 self, 0x02 party, 0x04 enemy, 0x08 alliance, 0x10 player, 0x40 NPC, with `ItemTargetFlags.ToActionTargets` and sends C2S 0x037 with count 0 on Confirm, as LandSandBoat requires). It starts on the preferred entity (a command menu's target) when allowed, else on the current target, else on yourself, else on the nearest allowed entity (50 yalms). Your own target, the target window and lock-on do not change; the cursor is the target arrow in violet (peak (132, 102, 213) in the video), drawn 12 px above the gold target arrow when both mark the same entity, and above the name plate otherwise (`EntityRenderer.SubTargetAnchor`, `StockUiHud`). The menu keys and the target keys (Tab / Shift+Tab, d-pad, arrows) move it through the allowed entities in screen order, wrapping; F1 puts it on yourself, F2-F6 on party members; Confirm (Enter too) runs the action there and Cancel drops it. A menu choice sets the menus aside while it is up (`StockUiMenuController.Suspended`) and brings them back after (the video). Allowed entities follow the action's client target bits (`ActionTargetFlags`: 0x01 self, 0x02 player, 0x04 party, 0x08 alliance, 0x10 NPC, 0x20 enemy; party and alliance from the party list; trusts and pets count as party, PROVISIONAL). The help bar's "Select target of spell." and the AoE range guide the video shows are not drawn yet ([stock-ui.md](../ui/stock-ui.md#magic-and-abilities-windows-240-353)). PROVISIONAL: the start rule beyond the captured case, the cycling order and keys, the menus returning after Cancel.
- Command permission & policy gating: distinction between standard vanilla commands (always allowed), server admin passthrough (`!pos`, `!zone`), and synthetic locomotion gated behind `FeatureRestrictions.Movement`
- Console text selection & copy support (`SelectableTextBlock`), robust comma/parenthesis coordinate parsing for `/moveto`, categorized command discovery (`/help`, `/commands`), GM command discovery (`/gmhelp`, `/gmcommands`) gated by GM permissions (`"You are not a GM."`), and `FeatureRestrictions` filtering
- Headless/early verification of movement, combat, and zoning against live server without requiring 3D rendering
- Robust locomotion keepalive synchronization and automated C2S 0x016 CharReq entity discovery for reliable live server and Windower multi-session pairing

## Input subsystem

- **Keyboard & Mouse:** Default layouts for FFXI Compact (WASD + IJKL camera) and FFXI Full (Numpad) with smart text-input isolation
- **Gamepad / Controller:** Full XInput, DirectInput, and SDL gamepad support (Xbox, PlayStation, generic HID) with deadzone, rumble, and axis calibration
  - Driver order (`MainWindow`): `SdlGamepadDriver` when SDL initializes, else `XInputGamepadDriver` on Windows, else `VirtualGamepadDriver`.
  - Which character the pad drives (#150): the one in the focused viewport window, main or popped out; with no viewport focused, the one in the viewport focused last (`ViewportWindowManager.WindowFocus`, the app's one window-focus tracker, shared with the sound controls since #304; see [multi-box](../rendering/viewport-and-terrain.md#multi-box-windows-switching-and-input-154)). The pad is read while a GordianXI window has the focus, or always with *Always Enable Gamepad* (Controls & Input; Enable, Always Enable and Rumble apply to every character, and since #314 so does the rest of the profile, see [below](#input-profiles-and-multi-boxing-314)). Every other character gets a disconnected pad.
  - Several GordianXI processes (#150, 2026-10-07): on Windows `SdlGamepadDriver` turns off SDL's Raw Input, GameInput and Windows.Gaming.Input joystick drivers (`SDL_HINT_JOYSTICK_RAWINPUT` / `_GAMEINPUT` / `_WGI` = 0), which can hand the pad to one process (fits "only the last launched window"); XInput pads are then read through XInput and others through DirectInput / HIDAPI, which any process can poll, and each process acts on the pad only while one of its windows has the focus. Checked in game with two processes (2026-10-07).
  - `SdlGamepadDriver` runs on SDL3 through [ppy.SDL3-CS](https://github.com/ppy/SDL3-CS) (#261, 2026-10-05; SDL2 through Silk.NET.SDL before). It polls each frame: `SDL_PumpEvents`, then slot N opens the Nth gamepad in `SDL_GetGamepads()` by instance id, and a slot whose gamepad reports disconnected is closed and refilled on a later poll (hot-plug). Face buttons map by position (South/East/West/North = A/B/X/Y), sticks are normalized to -1..1 with Y inverted (+Y up), triggers to 0..1 with a 0.15 press threshold, and rumble refreshes a 1000 ms `SDL_RumbleGamepad`. Background joystick events are allowed so a pad works while the window is unfocused.
  - Native library: `SDL3.dll` / `libSDL3.so` / `libSDL3.dylib` from the package's `runtimes/<rid>/native` (win x86/x64/arm64, linux x86/x64/arm/arm64, osx x64/arm64). A `DllImport` resolver falls back to that folder when the host's dependency manifest doesn't list it (the CI test host).
- In-game chat line: Enter (outside menus) or the `OpenChat` key (slash; Space in the Full layout; Back on a gamepad, B closes it) opens the stock chat input, which then owns the keyboard and runs lines through the same dispatcher as the console (see [ui/stock-ui.md](../ui/stock-ui.md#chat-and-log-windows-chunk-5)); walk/run toggle is on keypad `/`; keypad + / gamepad Y select a log window to scroll; Tab / Shift+Tab cycle targets left and right on screen (see [Target cycling](#target-cycling))
- Rebindable control mapping engine with JSON persistence and modifier key support (`keybinds.json`)
- Real-time 60Hz locomotion and camera controller updating `WorldEntity` coordinates and dispatching to server Pos loop
- Dedicated "Controls & Input" dashboard tab with live input monitor and preset switcher

### Input profiles and multi-boxing (#314)

- The user's input profile (`input_profile.json` under LocalAppData/GordianXI: key bindings, mouse and gamepad sensitivity, deadzones, the gamepad button map, axis inversion) is the same for every multi-boxed character. `ControlsInputViewModel` loads it and publishes it to `InputProfileHub.Default` (Core `Input/`); each `CharacterSession` runs on its own deep copy (`InputProfile.Clone`, a JSON round trip so no setting is left out) and takes a fresh copy whenever the hub reports a change (Controls & Input, or the in-game gamepad key-assignment list).
- Copies, not one shared object: a session applies its server-stored config choices (the Mouse/Cam. page's axis rows, `CharacterSession.ApplyCameraSettings`) to its own copy, so one character's config page never changes another's. Those choices are applied again after every fresh copy.
- Before #314 only the Command Console's selected character got the saved profile (`ControlsInputViewModel.SetSession` handed it the object); the others ran on `InputProfile.CreateCompact()` defaults. `SetSession` now only picks whose telemetry the page shows.

### Gamepad layout and key assignment (#21, #326)

- **Defaults** (`InputProfile.BindDefaultGamepadButtons`), retail's layout from the maintainer's checks (in-game test rounds 1-2, 2026-10-10) plus the GordianXI additions:

  | Button | In a menu | Otherwise |
  |---|---|---|
  | A / B | Confirm / Cancel | Confirm / Cancel |
  | X | page turn | main menu |
  | Y | select window | select window |
  | Back | | chat line |
  | Start | | /logout (`Logout`, a toggle: again cancels) |
  | D-pad up / down | menu cursor | target party up / down (`TargetParty1` / `TargetParty2`: the second and third party slots) |
  | D-pad left / right | menu cursor | cycle targets left / right through yourself (`TargetCursorLeft/Right`), repeating while held |
  | LT / RT | | hold for the Ctrl / Alt macro palette (`MacroPaletteCtrl/Alt`, [#339](https://github.com/jimmy58663/GordianXI/issues/339)) |
  | L3 | | lock-on with a target, /heal without one (`LockOnOrHeal`) |
  | R3 | | camera: third person -> first person -> free camera -> third person (`ToggleCameraMode`) |
  | RB | | auto-run |
  | LB | | next character (GordianXI multi-box) |

  The d-pad is two-purpose, as in retail: each direction is bound to a menu action and a targeting action, and `InputProfile.TryGetAction`'s menu context picks one. Its menu bindings are part of the gamepad layer (`BindDPadDefaults`); in rounds 1-2 they were only bound with the keyboard presets, so the gamepad reset (Controls & Input or the in-game list) dropped them (round 2, B12). Held left / right repeat the target cycle after 0.5 s, then every 0.10 s (`PlayerLocomotionController.TargetRepeatDelay` / `TargetRepeatInterval`, the maintainer's values from in-game rounds 2-4; 0.10 s is the floor they chose); the same holds for Tab / Shift+Tab. L3's "target" means a selected target, a lock-on, or a fight the server started (which lock-on then selects); the keyboard's T / keypad `*` stay plain lock-on. Earlier layouts: round 0 had L3 walk / run, RB / LB macros Alt+1 / Ctrl+1; round 1 LT / RT cycled targets and Start opened the main menu; rounds 1-2 had L3 plain lock-on and R3 reset camera. Cycle Target Left / Right (skipping yourself, Tab / Shift+Tab) and plain lock-on (T / keypad `*`) are keyboard-only: the list has no rows for them since round 4, the combined d-pad and L3 rows covering them on the pad. Walk / run keeps keypad `/` and the stick tilt (walk below `WalkTiltThreshold`).
- **Macro palettes:** while LT or RT is held the pad's other buttons drive nothing (`InputState.Update`), so LT + A does not also confirm, as with retail's palette. The palette window and running a macro from it are not built yet ([#339](https://github.com/jimmy58663/GordianXI/issues/339)); the triggers are only reserved.
- **Next character** (`InputAction.CycleCharacter`, LB) is a GordianXI multi-box function, not retail: the main window's input loop runs it for the gamepad's character with `ViewportViewModel.CycleFrom`, as Ctrl+Tab does (#151), popped-out characters included. One cycle per press: a character that takes the pad ignores the buttons still held from the previous one until they are let go (`InputState.IgnoreHeldGamepadButtons`, called by `MainWindow` when the gamepad's character changes). Round 1 cycled through every character while LB was held, because each newly focused character saw LB as a fresh press.
- **Saved profiles** move to the new buttons on load only where the old default still stands: `InputProfile.EnsureGamepadShortcutBindings` (L3 / RB / LB; an empty `CycleCharacter` entry marks it done), `EnsureGamepadRetailBindings` (LT / RT from Cycle Target, Start from the main menu; marker `MacroPaletteCtrl`), `EnsureGamepadStickBindings` (L3 from Toggle Lock-On to Lock On / Heal, R3 from Reset Camera to Change View; marker `LockOnOrHeal`), so a later choice of no button is kept. `EnsureNoHiddenGamepadBindings` (every load) takes a plain pad button off any action the list has no row for, so no button stays bound where the list cannot show it; keyboard bindings stay. `EnsureDPadBindings` runs on every load: a d-pad direction that drives nothing in one context (menu, or the rest) gets its default function there back; a direction the user gave another function in that context keeps it.
- **Retail check:** the layout above is from the maintainer's knowledge of retail; retail's PC client itself has no in-game gamepad assignment. The config list's Gamepad entry "Boots up the FINAL FANTASY XI GAMEPAD Config program" (help text 1092, ROM/165/75), the separate `FFXiPadConfig.exe`, which stores its layout in the registry (`padsin000`, `padmode000`, `padguid000` under the FinalFantasyXI key). That function order is not decoded, so retail's default button for each function (and whether L3 / R1 / L1 carry a retail function) is **not confirmed**; to check against FFXiPadConfig's defaults. The in-game `k1assign` / `k2assign` windows ("Key Assignment (Movement/Camera/Cursor, etc.)", help 277 "(Only when using compact keyboard.)"; "Key Assignment (Shortcut Commands)", help 278) are the keyboard's, opened from Misc. 2's Key Assignment row, and `keypad*` is the software keyboard; none is a gamepad editor.
- **Binding model** (`GamepadAssignments`, Core `Input/`): one row per function; a function that does different things by context names both, menu first, as retail's own "Menu/Target Cursor Left" does ("Menu Up / Target Party Up", "Lock On / Heal (no target)"). So a two-purpose button shows on one row that says both purposes, rather than on two rows. The assignable functions (`GamepadFunction`: a label, the config row table row with retail's wording where there is one, ROM/165/74 rows 89-142, and the actions one button drives), each function's buttons in a profile, and `Assign`, which gives a function one button and swaps: another function of the same context (menu navigation vs. the rest) that had the button gets the function's previous one, and actions outside the list let it go. A function can drive actions of both contexts (Menu/Target Cursor Left = `MenuLeft` + `TargetCursorLeft`), resolved by `InputProfile.TryGetAction`'s menu context. Only plain gamepad chords are touched; keyboard bindings never. `ResetDefaults` restores the default buttons and keeps the gamepad settings.
- **The list** (Config -> Gamepad, [stock-ui.md](../ui/stock-ui.md#gamepad-key-assignment-21)): Confirm on a row waits for the next pad button (`InputState.GamepadButtonsPressed`, the edge of the effective buttons, triggers included) and assigns it to the shared profile. While it waits, and until the assigned button is let go, the pad drives no action (`InputState.SuppressGamepadActions`, set from `StockUiMenuController.IsCapturingGamepad` each tick), so assigning L3 never also toggles lock-on. The keyboard's Cancel or 5 s without a button give up.
- The Controls & Input page lists Toggle Lock-On, Change View and Next Character with their chords.

### Moving stands you up from /heal

- Any movement input (movement keys, the left stick past its deadzone, auto-run) while the server reports the Healing status (S2C 0x037 status 33, LandSandBoat `xi.animation.HEALING`) sends /heal off (C2S 0x0E8, `RestMode.Off`) once (`PlayerLocomotionController.UpdateHealCancel`); it can be sent again only after the status has left Healing. The maintainer's request (round 3). The resting animation itself is #343.

### Auto-run

- R (keyboard) or RB toggles auto-run (`InputState.AutorunActive`). Retail behaviour (the maintainer's check, 2026-10-10): the character runs the way it faces; left / right (A / D or the stick sideways) steer it round in an arc at the turn speed (`TurnSpeedDegreesPerSec`, full rate at full tilt) and it carries on the new way when released; running backwards (S, or the stick pulled mostly back past `PlayerLocomotionController.AutorunCancelStickY` = 0.5) ends it. Forward input keeps running. Before round 2, auto-run ran toward the camera's direction and the stick ignored it. Locked on, auto-run still runs toward the target as before.

### First- and third-person camera settings (#306)

- Mouse (`InputProfile`) and gamepad right stick (`GamepadSettings`) each have a separate first-person set: `SeparateFirstPersonMouse` / `SeparateFirstPersonCamera` plus first-person inversion per axis and sensitivity. Off by default: first person uses the shared (third-person) settings, as before. `PlayerLocomotionController.UpdateCamera` picks the set by camera mode (`InputProfile.MouseCamera(firstPerson)`, `GamepadSettings.Camera(firstPerson)`).
- Legacy parity: retail's Mouse/Cam. config page (`conf7`) already has separate Third-Person and First-Person Camera Y / X Axis rows. The third-person rows set the session's mouse inversion as before; choosing a first-person row now turns the separate first-person mouse set on for that session (its other values start from the shared ones) and sets its inversion. Retail's page has no sensitivity rows; first-person sensitivity is a GordianXI setting on Controls & Input.
- Controls & Input: "Separate First-Person Mouse Settings" and "Separate First-Person Camera Settings" (gamepad) reveal the first-person controls; turning one on copies the shared values in, so it changes nothing until edited.

### Target cycling

`TargetCycling` (Core) picks the target for the targeting keys, matching retail (checked in retail by the maintainer, 2026-09-29, #134).

- **Candidates:** spawned, not hidden or invisible, named entities other than elevators and ships, within 50 yalms of the player (the monster draw distance) and inside the camera's horizontal field of view, ordered left to right on screen (at the same position, nearest first). The screen side is worked out on the ground plane in the renderer's mirrored display space ((-x, z); the camera's yaw is a display-space yaw, `TargetCycling.ViewBasis`), with the orbital eye `Distance` behind the player; projecting raw world positions instead mirrors left and right and misplaces the eye (the first in-game test: d-pad reversed, only a Rarab 5 yalms away targetable). `Gather_ScreenSideMatchesTheRenderedCamera` checks the side against the display camera's own matrices.
- **A current target that leaves the screen** (or the 50-yalm range) stays in the order past the edge it left by, so the next press carries on from that side (maintainer's in-game test).
- **Tab / Shift+Tab** (`TargetNearest` / `TargetPrevious`, also the right / left triggers): with nothing targeted, the closest candidate by distance; otherwise the next candidate to the right / left of the current target, wrapping to the left-most / right-most. Your own character is never picked.
- **D-pad right / left** (`TargetCursorRight` / `TargetCursorLeft`): with nothing targeted, yourself; otherwise the next candidate to the right / left, with you in the order at your own screen position (the centre in first person); past the edge of the screen it returns to you. Profiles saved before these actions existed have the d-pad moved onto them on load (`InputProfile.EnsureTargetCursorBindings`).
- **Gamepad A** (Confirm from a gamepad button, `InputState.WasActionTriggeredByGamepad`) with nothing targeted targets the closest candidate. Confirm from the keyboard (Space, Enter, keypad 5) never targets; on the keyboard only Tab and Shift+Tab do.
- **F1-F6:** F1 targets yourself, F2-F6 (`TargetParty1`-`TargetParty5`) the other members of your own party in party window order (`PlayerActionService.SetTargetByPartySlot`); an empty slot or a member outside the zone does nothing.

### Engage versus lock-on (#137)

Evidence: the maintainer's retail recording of 2026-10-03 (29 s, an Island Rarab in a canyon, 1 fps frames f01-f29) and the maintainer's in-game description of retail lock-on (2026-10-04): "while locked on you strafe or back up while facing the target, it limits how far your camera can go left and right, and if you push it all the way left it stays there, it doesn't snap back behind the player".

**Retail-confirmed:**
- Engaging does not turn the character (f03-f05: "Start auto-attack", weapon drawn, target window turning red; the character keeps facing the camera, away from the Rarab, through f09).
- Facing away from the target the client keeps reporting "Unable to see the Island Rarab" / "is out of range" (chat from f09): auto-attack needs the player to face the target and the client does not turn you for it while not locked.
- The command menu stays open while engaged (f05-f29), so lock-on keys must work with a menu open.
- Locked on, the character circles the target facing it: forward runs toward the target, back backs away from it, left/right strafe around it (maintainer's description; f11, f19, f23 show the character side-on to the Rarab with the Rarab beside it while the player moves round it, f13 / f25 behind it).
- Locked on, the camera is limited to an arc left and right and stays at the limit when pushed (maintainer). In the recording the Rarab stays within about 100 px of screen centre (about 10 degrees) in f11-f29 while the player moves from its left (f11-f17) to its right (f21-f29).

**What GordianXI does (`PlayerLocomotionController`):**
- Engage / disengage touch only the engaged flag and target. Lock-on (`PlayerActionService.IsLockedOn`) is set by T / NumPad `*` / gamepad L3 (#326), `/lockon`, or auto lock-on, and cleared by the same key, target clear, `/attackoff` and Cancel.
- Auto lock-on (`AutoLockOnEngage`, `/lockon auto [on|off]`, default **on**): engaging selects the fought target if none is selected and locks on. Not a retail config row (none of the ten decoded pages has one; "Controls: Auto-target during battle" is the server's re-target flag, LandSandBoat `AutoTargetOffFlg`). Not confirmed: whether retail locks on at engage.
- Locked-on locomotion: input is relative to the target (forward toward, back away, strafe around) and the character turns to face the target at the stick-turn rate (720 degrees/s, `TurnTowards`) **only while the player is moving**, never on the engage or lock frame and not while idle. This choice is PROVISIONAL: the recording does not show when retail starts turning, so "once you move, at the stick-turn rate" was chosen over snapping.
- Locked-on camera, measured from the maintainer's retail recording of 2026-10-03 (10 fps frames, tNNN = (NNN - 1) / 10 s; 60 degree vertical field of view assumed, as the name-plate calibration does; details and constants in [calibrations](../reference/calibrations.md)):
  - *Yaw arc* (`LockOnCameraArcRightDegrees` 32, `LockOnCameraArcLeftDegrees` 31): at the right limit (10.2-10.6 s) the character stands at x = 175 of 640 (145 px left of the view centre), at the left limit (11.8-12.6 s) at x = 460 (140 px right of centre). With a 91 degree horizontal field of view that is 24.9 / 24.2 degrees of view offset, plus about 6 degrees of parallax (target about 10 yalms off per the retail distance read-out, camera about 3 yalms behind the character after the zoom) = about 32 / 31 degrees of camera yaw either side of the character-to-target line. Left and right agree within the measuring error.
  - *Pitch* (`LockOnCameraPitchMinDegrees` 0, `LockOnCameraPitchMaxDegrees` 14.5): at 17.8-18.0 s the horizon sits on the view centre (level); at 16.7-17.3 s the far horizon is 120 of 540 rows above centre (14.4 degrees down). The high value comes from the far hills' base, so it is good to a few degrees.
  - *Zoom* (`LockOnZoomFactor` 0.48, `LockOnZoomSeconds` 0.3): at engage, 4.1 s nothing, 4.3 s about 40 %, 4.4 s about 95 %, 4.5 s done; the character grows from about 125 px to 250-275 px tall (2.0-2.2 times), so the camera distance drops to about 0.48 of what it was. It eases (a smooth rise over about 0.3 s), it is not instant. Retail turns the zoom back out when lock-on ends (maintainer); the recording does not show the return, so ours eases back at the same speed. Whether retail zooms to a share of the user's distance or to a fixed one is not known (one sample). `CameraDistance` itself is never changed, so the user's distance is back when lock-on ends.
  - *Unassisted* (12-16 s, the player runs left starting from the left limit, no camera input): the camera does not turn on its own. The character crosses the screen from x = 460 to x = 180 between 12.6 and 13.8 s (the camera holds its world yaw while the player circles), then stays at x about 165-190 for 13.8-14.4 s and after, running (the camera is carried along at the limit). `ClampLockOnCamera` does exactly this: it only acts when a limit would be passed (by input or by the player's circling) and never eases or recentres. A camera already outside the arc is left alone and cannot go further out.
  - *Re-aim* (`ViewportCamera.AimPoint` / `AimBlend`, `LockOnAimWeight` 1.0): retail keeps the target within about 5 degrees of the view centre throughout (the Rarab sits at x = 290-350 of 640 in 10-18 s, run1/run2/pitch frames) while the character moves across the screen, so the view faces the target while the camera keeps orbiting the character. Measured how: yaw only. When the camera is level (17.8-18.0 s) the Rarab sits on the centre row (275 of 540), and pitched down (16.7-17.3 s) it sits 45 rows above it, so the vertical view is the camera pitch, not an aim at the target's body. Exactly at the target in yaw (weight 1): the plus or minus 5 degrees scatter looks like lag in the aim, which is not modelled. **Why T and NumPad `*` did nothing in-game (found 2026-10-04):** the toggle lived in `UpdateActionTriggers`, which `PlayerLocomotionController.Update` skips while a stock menu is open, and the command menu is open while engaged. It is now evaluated before that gate (`UpdateLockOnToggle`). The key path is traced in `logs/gordian_system_<date>.log` under `LockOn` (`KeyDown ... reached the game input`, `Lock-on key held (...)`, `Lock-on toggled by key`). Saved input profiles with no `ToggleLockOn` binding get T and NumPad `*` on load (`InputProfile.EnsureLockOnBindings`).

**Where the zoom and aim reach the screen (found 2026-10-04):** the viewport draws with its own `ViewportCamera` (`VeldridViewportControl.Camera`, display space), fed from the controller's public values, not with the controller's private `_camera`. The first zoom and aim code only changed the private camera, so neither was ever drawn (yaw, pitch and the arc worked because they travel through `CameraYaw` / `CameraPitch`). The viewport now draws with `PlayerLocomotionController.EffectiveCameraDistance` (the zoomed distance, through its tick smoother) and calls `ApplyLockOnAim(Camera)` each frame. The zoom is logged under `LockOn` (`Zoom in starts: distance a -> b`, `Zoom in done`, `Zoom out starts`, `Zoom out done`) in `logs/gordian_system_<date>.log`. `RenderedCamera_*` tests run the same path the viewport does and measure the eye that would be drawn.
