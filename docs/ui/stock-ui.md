# Stock DAT 2D UI

> The Tier 2 stock UI: Section 0x30/0x31 decoding, the sprite renderer and layout model, HUD windows, menus and config pages (Phase 5E Tier 2), plus Tier 3 ImGui overlays. Status and open work: [ROADMAP.md](../../ROADMAP.md) and GitHub Issues.

## Data layer (chunk 1)

- **Chunk 1: UI data layer.** `UiElementGroupDecoder` (Section 0x31: texture list, images of 61-byte parts = destination quad TL/TR/BL/BR, source rect, flags, per-corner RGBA colours in the 0x80 half-scale convention, sampled texture id), `UiMenuDecoder` (Section 0x30: frame with 2-bit screen anchor, buttons with 4-way nav links, 20-byte shape references to group images, help/title text ids) and `UiResourceLibrary` (English menu DAT 39542 = ROM/119/51, base menu DAT 1 = ROM/0/1 for fonts it omits, window skins 14-21 = ROM/0/14-21 overriding `newtex`/`hfr1`/`corner`/`vfr1`; textures decode lazily). Every group and menu in the retail DATs decodes to within its section padding; 3625 of 3630 shape references resolve (the rest are lobby-only); menus are authored in the 512 x 448 PS2 layout; UI textures wrap (window backgrounds tile `newtex`); menu labels are pre-rendered sprites (`windowps`), and `fontshp` glyphs run from ASCII 0x20. A software composite of the log, party, target and main-menu windows matches the retail look.

## Renderer and layout model (chunk 2)

- **Chunk 2: Tier 2 sprite renderer & layout model.** `StockUiRenderer` draws element-group images and text as batched screen-space quads after the 3D pass (`RenderTier2_StockUi`): per-corner vertex colours doubled from the 0x80 half scale, texture alpha normalized on upload (DXT3 UI sheets peak at 0x88, DXT1 at 0xFF; both mean opaque), bilinear wrap sampling. Window backgrounds fade to half brightness and half opacity toward the bottom through their authored corner colours (0x7F top, 0x40 bottom), which is the retail translucency. `StockUiLayout` (Core) resolves every persistent window from its authored position and anchor corner plus an optional per-window override (anchor, position, scale, hidden), clamped on screen; keys are logical window ids (`StockUiWindowIds`) because windows swap layouts at runtime (party `ptw1`..`ptw6` by member count, log `log1`..`log8` by line count). Default scale 1 = the retail PC layout (one screen pixel per layout pixel). `StockUiLayoutStore` shares one layout per character (`ui_layouts/<name>.json`, saved on change) between the HUD and `/uilayout [scale n | reset]` / `/uilayout <window> <hide|show|reset|scale n|move x y [anchor]>`; `MoveTo` (for chunk 4b) re-anchors to the nearest corner. `UiFont` measures and draws `fontshp` glyphs. Compared against Windower captures (2026-09-25; retail draws the UI at one screen pixel per layout pixel at 2560 x 1440): part corner colours are stored bottom row first, so windows are translucent at the top; the attributes' second byte is the part blend mode (2 = darken, used by text shadows, the band behind window titles and separators; 1 = add); the client draws its own window border (the skin's `hfr1` strip along the top and bottom edges, added at ~85% so the bottom line reads lavender over the navy, fading over 16 px at the ends). The party window uses `ptw0` (titled Solo) outside a party; the log window stretches right to meet the party window (2 px gap) unless moved. Party rows (`StockUiPartyWindow`) are composed by the client, not the DAT: name, HP number (hpcol colours by HP%) and MP number in `fontshp` at 7/8 size (the glyphs carry their own dark outline; the client adds no shadow) (names that do not fit before a four-digit HP number keep their longest fitting prefix plus "..", as retail shows "Tarudrake" as "Tarudra.."), the HP gauge (5 x 5 knob + strip middle stretched to 64 px) and MP gauge (unstretched strip) from the `gauge` texture tinted by measured fills, and the party-leader ball; positions within a pixel of the capture. Opt-in (not retail): party TP under the name (`/uilayout tp on`). **Members in another zone (#146):** the server sends no vitals for a member who is not in your zone, so the row shows the name and the zone's compact name in parentheses on the second line (`(SSandOria)`, `PartyRowVitals.ZoneName`) instead of the HP/MP numbers and gauges (retail capture, Windower 2026-09-29: "Cybin" / "(SSandOria)"); the leader ball still shows and the opt-in TP is not drawn. The text is `ROM/165/85` (`DMsgCategory.ZoneNamesCompact`, indexed by zone id like ROM/165/84: 230 `SSandOria`, 231 `NSandOria`, 232 `PSandOria`, 233 `ChatdOrag`, 234 `BastokMine`, 235 `BastokMark`, 236 `PortBastok`, 244 `UpJeuno`, 246 `PortJeuno`; no spaces or punctuation; not ROM/165/83, which holds the display abbreviations "S.San d'Oria"). "Another zone" is decided by `PartyMember.IsInOtherZone(currentZone)`: a reported ZoneNo that is non-zero **and** differs from your zone. LandSandBoat's S2C 0x0DD / 0x0E2 set ZoneNo only for a member elsewhere (0 = same zone, vitals present), but S2C 0x0C8 lists every member's zone, same-zone ones included, so non-zero alone would mark everyone; comparing against `WorldState.CurrentZoneId` handles both packets. `PartyState.UpsertMember` stores a 0x0DD/0x0E2 ZoneNo as given (0 clears it, so a returning member's gauges come back) and skips the zeroed HP/MP/TP/percent fields while the member is elsewhere (the last real vitals are kept); a 0x0C8 ZoneNo only overwrites when non-zero. The party window and the alliance windows share the rule; an alliance row (16 px, no second line) shows the zone where its gauge would be, right-aligned to the HP number's edge. Evidence: LandSandBoat `0x0dd_group_list.cpp` and `0x0c8_group_tbl.cpp`, the retail capture above and the issue text. **Unverified against retail:** the zone text's exact position and colour (right-aligned, as retail, at the MP number's right edge, row x + 96, 10 px below the name, default white `fontshp` at 7/8; confirmed right-aligned in-game 2026-10-03), and the alliance placement (right edge at the HP number's, row x + 87, 4 px below the row top). Party vitals: member HP/MP/TP changes arrive as S2C 0x0DF and now update `PartyState` (previously only 0x0DD at roster changes, so members froze), roster tables (0x0C8) no longer zero stored vitals, and the local player's row reads its own live vitals. Verified offscreen on D3D11 (`StockUiRendererTests`); the depleted-gauge look was accepted in-game.

Players always keep the gauge. Passing states (an event hiding names, 0x92) do not take it away.
  - *Name wrapping ([#258](https://github.com/jimmy58663/GordianXI/issues/258)):* a name too wide for one line wraps instead of being cut (`StockUiTargetWindow.WrapName`). Rule fitted to the maintainer's retail list (2026-10-04) and measured on the retail captures of Synthesis Focuser II, Door: Chocobo Stables and Door: Jeuno Duty-Free (all without a gauge), aligned on the "Target" title: a name up to 98 layout pixels wide (7/8 font) stays on one line at y 13; a wider one breaks after its first word ("Synthesis" / "Focuser II", "Door:" / ...: "Door: Chocobo" is no wider than "Mewk Chorosap", which stays whole, so the first line is not filled by width), and the rest is filled greedily ("Jeuno Duty-" / "Free"), breaking at a space or after a hyphen; a word with no break that does not fit is cut at the last character that fits. Wrapped lines start at y 7, 12 pixels apart, each 4 pixels further right than the one before (and 4 pixels narrower, so all end at the same edge); the measured baselines are 17, 29 and 41 pixels below the title's top, the same as the captures. Up to three lines without the gauge, two with it (the gauge at y 28 leaves room for two; the descenders of a second line touch its top edge); what does not fit on the last line is cut with "..", as before. The width limit lies between Mewk Chorosap (95.4, one line) and Treasure Coffer (104.1, wraps); 98 is 112 font pixels at 7/8. Checked by `WrapName_MatchesRetailTargetWindow` (every Port Jeuno name in the list), `WrapName_FirstBreakThenGreedyThenTruncate` and offscreen `RendersTargetWindowWrappedNamesWithAndWithoutGauge` (`GORDIAN_UI_DUMP` writes `target_wrap.png`).
  - *Confirmed in game (maintainer, 2026-10-06, Port Jeuno):* the first line ends at the first break, not at a narrower width limit: retail shows "Door: Arrivals Exit" as "Door:" / "Arrivals Exit", as GordianXI does (a narrower first line would give "Door: Arrivals" / "Exit"). The other Port Jeuno targets checked matched retail too.
  - *Unconfirmed (in-game checks):* where a wrapped name sits with the gauge shown (taken as y 7 and 19, like the no-gauge captures; Squintrox Dryeyes, Synergy Enthusiast); where a one-line name sits without the gauge (kept at y 13; target ??? or a short Door:); whether a hyphen also counts as the first break; the exact width limit; whether a name can exceed three lines. Party and alliance rows keep retail's ".." truncation ("Tarudra.." beside 9999 HP in a capture); no capture shows them wrapping.
- *Status icons:* `StatusIconLibrary` reads the status resource DAT (file id 87, ROM/119/57: 640 records of 0x1800 bytes in status-id order, icon at +0x280 like item icons); `LocalPlayerState.GetStatusEffectIds` decodes the 0x037 slots (low byte + 2 high bits, 0xFF empty); icons draw 24 x 24 on the `buff` menu grid (frame (142, 48), 26 px pitch, nine per row), matching the capture.
- *Target cursor:* the "anc_s" group (ROM/0/1 `anc` texture; the same diamond-and-arrowhead cursor as the menus, authored pointing right) turned to point down, drawn at UI scale with its tip at the skeleton's overhead point, projected from the entity pass (`EntityRenderer.TargetAnchor`). That point is skeleton reference 2, a straight offset up from the root joint authored per skeleton (Goblin 1.8, Island Rarab 1.7, Raven 2.8, Marine Dhalmel 6.05; Hume 2.0, Tarutaru 1.3, Galka 2.6 yalms), fixed per model so the cursor does not bounce with the animation (it followed the live pose until a bird's wing beat showed that). A skeleton without the reference falls back to its highest idle joint plus 0.6 yalms; it shades through the six frames and back at ~67 ms a step (0.8 s cycle), measured from a retail capture.
- *Target selection flash:* a newly selected target's model brightens in three triangular pulses of ~0.72 s (`TargetFlash`, light added before the texture modulate, peak +0.5, so the colour roughly doubles as in the capture); selecting another target restarts it there and cuts the old one short.
- *Lock-on:* while locked on, the "targetlo" overlay (windowps image 212: red corner brackets, "Locked" between two arrow key-tops, side glow bars from "colorbal") draws over the target window.
- *Alliance windows:* "raid1"/"raid2" (authored at 48 and 150, 100 tall, 16-pixel rows, directly above the target window's slot so they do not move with it); rows are name, HP number and HP gauge at the party rows' offsets, no MP (measured from 1:1 retail alliance captures). Party, target and each alliance window are separately placeable (`party`, `target`, `alliance1`, `alliance2`). Leader balls now come from "colorbal" (the captures' greenish yellow; the alliance leader shows a cream-white ball with the yellow one beside it, AllianceLeaderFlg bit 3). The group table (0x0C8) now also drops members it no longer lists.
- *Party member status icons* (opt-in, not in the legacy client): `/uilayout buffs <on|off|left|right>`, 16 x 16 icons in a line beside each party row, first nearest the window; other members from S2C 0x076 (now stored on `PartyMember.StatusEffectIds`), your own row from your live status.
- *Idle step fix:* S2C 0x037 no longer copies the movement speed stat into the local entity's current Speed (a standing player took a step on every status update, ~3 s apart).
- [ ] *Expiring status icons blink:* needs status durations (S2C 0x063 status-icon packet) wired into `LocalPlayerState`.
- Claimed-by-others target names are pink (240, 122, 180 from an alliance capture of Tiamat); confirm against a capture where the claim is known to be another group's.

## Menu input (chunk 4)

- **Chunk 4: Menu input.** `StockUiMenuController` (Core `Ui/`, owned by `PlayerActionService.Menus`) keeps a stack of open DAT menus and is fed each locomotion tick: `OpenMenu` (`-`/`M`, pad `X`/Start) opens the main "Commands" menu and, pressed again, turns its page (retail; only `Cancel` closes); the new `MenuUp/Down/Left/Right` actions (arrows, keypad 8/2/4/6, d-pad) move the cursor along each button's authored navigation links with key repeat (0.4 s, then every 90 ms); `Confirm` activates and `Cancel` closes the top window. The menu bindings share their keys with the camera and party-targeting actions, so `InputProfile.TryGetAction` takes a menu context (`InputState.MenuContext`): in a menu the shared keys navigate and the camera keys pause, while WASD and the left stick keep moving the character, as in retail (confirmed in-game 2026-09-26). Left/right on a list whose links point back at the button flip the main menu's pages (`menuwind` ↔ `socialme`, keeping the row; the page arrows, buttons 13/14, draw only on paged menus); the cursor position of every menu and the last page are remembered. The DAT carries no meaning for the buttons, so `StockUiMenuEntries` maps them (labels read from their `windowps` sprites): page 1 Status, Equipment, Magic, Items, Synthesis, Abilities, Party, Trade, Search, Linkshell, Region Info, Map; page 2 Missions, Quests, Key Items, View House, Bazaar, Macros, Config, Help Desk, Current Time, Communication, Shut Down, Log Out. Config opens the `configwi` list (Gameplay, Chat Filters, Font Colors, Windows, Log, Misc. 1-4, Effects, Mouse/Cam., Global, Gamepad); Windows opens the `conf5m` list (Shared / Window 1 / Window 2), which replaces the config list in its corner, and Shared opens `conf5win` ("Window Settings (Shared)") at the left, as a retail capture shows: its eight Window Type digits (`keytops3` sprites) select the window skin (ROM/0/14-21), the skin in effect underlined with retail's red bar, applied live by reloading the UI resources and persisted in the layout (`StockUiLayout.WindowSkin`, also `/uilayout skin <1-8>`). Log Out / Shut Down ask "Log out?" / "Shut down?" through `PromptYesNoAsync` (the `comyn` window with client-drawn text, `yesno` without one; cancel = No, default No) and then send the 0x0E7 logout request. Current Time posts the Vana'diel date; entries whose window does not exist yet post a notice to the log (`NoticePosted`, shown in the stock log and by `ChatViewModel`). Drawing (`StockUiMenuWindow`, from `StockUiHud`): the root menu takes the layout's `menu` placement and sub-menus keep their authored place relative to it (they follow a moved main menu rather than taking overrides); a window whose authored rectangle a later window covers is hidden (a sub-menu opened in the same corner replaces its parent, as retail); the cursor is the frame's kind-6 element group (`anc_s`, the six-frame gold arrow authored 32 px to the left of its origin, not the `yubi` hand, which is the mouse pointer), drawn at the selected button's origin plus the frame's and button's cursor offsets and animated with the target cursor's 67 ms ping-pong; the selected entry is tinted orange, glyphs (light, peak FFC05C in a retail capture; key-cap digits included) and capsule (deeper: (127, 133, 186) becomes (133, 87, 48)); the darkening shadows keep their colour; the alternate (kind 4) images some buttons carry (Synthesis, Party, Gamepad) are not the selected look and are not drawn until their meaning is known. The DAT's navigation link bytes are up, down, right, left (the first reading had left/right swapped; caught in-game on the three-column settings rows). Verified offscreen on D3D11 (`RendersOpenMainMenuWithCursor`, `RendersWindowSettingsPage`): cursor beside the entry, title band, page arrows, prompt text, highlighted digit and red bar.
  - Still open: help text (`helpwind` at the top of the screen) and window titles are not drawn yet (the string tables they need are decoded, see [Menu string tables](#menu-string-tables-19)); the windows behind Status, Equipment, Magic, Items, Map and the rest of the entries (client-composed content) are later chunks; the config pages beyond Window Type are chunk 4c; mouse input is below ([#22](https://github.com/jimmy58663/GordianXI/issues/22)).
  - Menu labels are pre-rendered sprites (`windowps` images referenced by each button's shape references); a button's second shape reference (kind 4) is its alternate/highlighted image; frames carry the cursor group reference (kind 6: `anc_s` on list menus, `anc_equi`/`anc_item`/`anc_shop` on grids; the chat input line `inline` names `yubi`).

## Menu string tables ([#19](https://github.com/jimmy58663/GordianXI/issues/19))

Research only (2026-09-28), nothing reads these tables yet. Found by searching every ROM DAT for known help strings (plain and XOR 0xFF), then checked against the menu DAT.

- **Where the text lives.** Three `d_msg` tables in ROM/165, XOR 0xFF, variable-stride layout (`tsize` > 0, 8-byte offset/length pairs), one string per record. `DMsgStringTable` already parses them. Indexes are the raw ids from the menu records, starting at 0; `-1` means none.

  | Table | English | Japanese | Records | Indexed by |
  |---|---|---|---|---|
  | Help text (`helpwind`) | 55651 = ROM/165/75 | 55531 = ROM/165/59 | 1099 | `HelpTextId` on frames and buttons |
  | Window titles | 55652 = ROM/165/76 | 55532 = ROM/165/60 | 201 | `TitleTextId` (frames; the main menu's buttons carry the title of the window they open) |
  | Config rows | 55650 = ROM/165/74 | 55530 = ROM/165/58 | 206 | nothing in the DAT; the client picks rows by index |

  The Japanese table is 120 file ids below the English one. The rest of ROM/165/69-87 is the English set of other client strings (lobby errors 70, lobby status 71, party and system messages 72-73, regions, weather, days, directions, moon phases, zone names, job names); ROM/165/53-68 is the Japanese set.
- **Check.** Every help and title id in the English menu DAT (39542, all 404 menus) is in range and resolves to non-empty text: 676 distinct help ids (up to 1098), 132 title ids (up to 198). Samples: main menu Status = help 321 "View status." / title 81 "Status"; `menuwind` Synthesis = help 816 / title 170; `chatctrl` = help 595 "Set your default chat mode." / title 129 "Chat"; `conftxtc`/`textcol1`/`textcol3` = title 55 "Font Colors", help 488 "Select a text category.", 489 "Set RGB color values."; `fxfilter` = help 599 / title 128 "Filter"; `conf11l`/`conf11s`/`conf11m` = title 175 "Log Settings", help 901-907; `playermo` Request = help 954.
- **ROM/97 is the legacy set, not the current one.** xi-tools points at ROM/97; it holds `XISTRING` tables (magic `XISTRING`, u32 file size / count / index size / data size at 0x20, index at 0x38 of 12-byte entries: u32 offset, u16 length, u16 flags where bit 0 marks format codes, 4 unused bytes, then NUL-terminated CP932 strings). English help is ROM/97/42 (file id 54, 653 records) and titles ROM/97/41 (53, 143 records); Japanese ROM/97/24 and 97/23. They are an older snapshot: the titles are a prefix of ROM/165/76, the help table has 31 older wordings ("Dismount your chocobo." vs "Dismount."), and ids above 652 / 142, which today's menus use, are missing. Use ROM/165.
- **Config row table (ROM/165/74), by index.** 0-10 channel names (Say, Shout, Tell, Party, Linkshell, Linkshell 2, Assist J, Assist E, Unity, Emotes, Messages from alter egos); 11-32 and 171-182 battle message categories (on/by you, NPCs, party, allies, others, foes); 33-35 System Lv. 1-3; 36-47 long channel descriptions ("Immediate vicinity ("Say")"...), 196 Yell; 48-62 effect and system categories (HP/MP you recover... Basic system messages); 63-72, 197 and 204-205 the Font Colors rows ("Player: Color of "say" text"...); 73-88 Font Colors sample lines ("Player recovers 10 HP."...); 89-142 key and gamepad assignment names (Move Up... Hide/Show Window); 143 the key-reset prompt; 144 Lot results; 145-152 list headings; 153-170 Effects filter rows (All effects during battle, You → you ... Screen shaking); 183-201 assorted prompts; 192-195 spam and emote filters and Yell; 202-203 Battle Messages / Calls for help. The 55 Chat Filters labels that `StockUiConfigPages.ChatFilters` types in (from retail captures) all appear here word for word. The groupings are read from the text; which rows each page shows, and in what order, still needs retail captures (Log page categories, Font Colors list, Effects list).
- **Text.** Plain CP932 with no control, glyph (0xEF) or auto-translate (0xFD) codes in any of the three English tables; the only byte below 0x20 is a newline (0x0A) in three help lines (69, 71, 74, e.g. "Stop tracking current target / and proceed with wide area scan?"). The Effects rows use CP932 0x81A8 (→) and the list headings 0x816B/0x816C (〔〕).
- **Not yet decided:** how `helpwind` lays out long lines (wrap width, one or two lines) and when retail shows it (on cursor move, frame help vs button help precedence). Check against a capture when it is wired.

## Menu mouse input and pointer ([#22](https://github.com/jimmy58663/GordianXI/issues/22))

- **Mouse on menus (2026-09-28, tested in-game).** The HUD publishes where it drew each visible open menu every frame (`StockUiMenuController.SetScreenPlacements`, `StockUiMenuPlacement` = menu, screen origin, scale; windows hidden behind a later one are left out) and `ViewportWindow` offers each mouse event to the stock UI before the input bus: the unlocked UI's drag first (left button), then the menus. Hit-testing uses each DAT button's rectangle (`X`, `Y`, `Width`, `Height` from the frame origin, times the scale), topmost window first; only buttons the cursor can reach take the pointer (a navigation link, list rows only while they show an entry), plus a paged menu's page arrows (buttons outside the frame, drawn only on the main menu). Behaviour: hovering an entry of the window taking input moves the cursor there; a left press on an entry selects and activates it as Confirm does; on an entry of a parent window still on screen it first closes the windows opened from it; while a yes/no prompt is up only its own buttons answer; a page arrow turns the page; a slider takes the value under the pointer (the bar's share, snapped to the setting's step) and follows the pointer until release; a press on a window's body or title is swallowed without selecting. A right press over a menu cancels (closes the top window) as the Cancel key does; elsewhere it is still camera look. The wheel over a scrolling list (Chat Filters) scrolls it an entry a notch without wrapping and is swallowed over any other menu (it does not zoom the camera). Presses outside every menu stay game input, and a release is the menus' whenever its press was.
- **Pointer (retail capture, 2026-09-28):** retail's pointer over the game is a small yellow arrow with a dark outline; over a clickable menu entry it becomes a grey ring over the arrow's tip, the rest of the arrow showing below right. The arrow is a Windows cursor in the client's `FFXiResource.dll` (cursor group 102/105: cursor 1 is the 32 x 32 8-bit arrow, hotspot (19, 19); cursor 2 is a blank 1-bit cursor, which suggests the client hides the system cursor over entries and draws the ring and arrow itself); the ring is in none of the 78 UI DAT textures, and a scan of every ROM DAT for cursor-like names found nothing. Neither is copied: `StockUiPointerArt` (App) draws GordianXI's own look-alikes in code (the arrow from a polygon, amber gradient and dark outline; the ring from two circles), a deliberate exception to legacy parity (the maintainer chose look-alikes over reading the DLL at runtime). The arrow is the viewport's system cursor, so it never lags a frame: on Windows an `HCURSOR` made from the bitmap (`Win32ChildWindowHelper.CreateCursorFromRgba`, per-pixel alpha) that the child window sets on `WM_SETCURSOR`; elsewhere an Avalonia bitmap cursor. Over a clickable entry (`StockUiMenuController.IsOverEntry` at `PlayerActionService.UiPointer`) the system cursor is hidden (`StockUiHud.PointerDrawn`) and the HUD draws the arrow and ring over everything (`StockUiMenuWindow.DrawHoverPointer`, one screen pixel per image pixel like the system cursor). The child window asks for `WM_MOUSELEAVE` (`TrackMouseEvent`) and elsewhere `PointerExited` clears the pointer, so the hover pointer is not left at the edge. (A first pass drew the `yubi` hand; retail PC does not show it over the game.)
- Not yet compared with retail: whether retail activates on press or on release, whether right-click cancels anywhere or only over a window, hover over a parent window (ignored here), the retail "Mouse Control Type 1/2" setting (Mouse/Cam. page; stored, not applied), and the pointer while the camera turns. Verified by `StockUiMenuControllerTests` (`Mouse_*`) and offscreen on D3D11 (`RendersOpenMainMenuWithCursor` draws the hover pointer).

## Config pages and settings (chunk 4c)

- **Chunk 4c: Config pages and settings (2026-09-26, tested in-game).** Every page the `configwi` list opens is navigable and live: Gameplay (`conf2win`), Chat Filters (`cfilter`), Windows -> Shared (`conf5win`) / Window 1 (`conf5w1`) / Window 2 (`conf5w2`), Misc. (`conf3win`), Misc. 2 (`conf6win`), Misc. 3 (`conf12wi`), Misc. 4 (`conf13wi`), Mouse/Cam. (`conf7`) and Global (`conf4`). The DAT gives the buttons no meaning, so each page's label sprites were composited and read first (`GORDIAN_UI_DUMP_MENUS`, see the working notes) and `StockUiConfigPages` (Core `Ui/`) describes every row: option rows (one button per value; the value in effect gets retail's red bar, confirm selects) and slider rows (the 192 x 16 button is an invisible hit region over a bar authored in the frame art; left/right move the value by its step, and the client fills the bar with rows 1-6 of the `gauge` strip drawn opaque and tinted light blue, 12 px tall inside the 16-px bar, as a retail capture shows (`framesus` #103 is the same strip tinted (64, 96, 127); the capture reads a little more lavender, tint (0x68, 0x60, 0x84)); `conf5w1`/`conf5w2` bake an orange sample fill (gauge texels 48,16) into their first bar, which is skipped when drawing). Values live in `StockUiSettings` (one integer per `StockUiSettingKey`, retail defaults where known), saved per character in `ui_settings/<name>.json` by `StockUiSettingsStore`; Window Type and Party Icon Display stay on `StockUiLayout` (routed through the controller's delegates). Glyphs and icons are drawn with half a texel trimmed from each edge (`StockUiRenderer.TexelInset`, the quad trimmed by the same share), because bilinear scaling otherwise samples the neighbouring atlas cells and draws faint box edges around them (in-game 2026-09-29; retail shows a few such lines too). The letter spacing is the font's own advance; the captures suggest a wider gap (about 15-17 px between neighbouring fills at the 24 px size), still to be measured.

## Working notes

- Verify against Windower captures: the user supplies crops at 2560 x 1440 (retail draws the UI 1:1). Upscale with ImageMagick (`C:/Program Files/ImageMagick-7.1.1-Q16-HDRI/magick.exe`, `-filter point -resize 800%`) and sample pixels to measure.
- Offscreen checks: `GORDIAN_UI_DUMP=<dir>` makes `UiResourceRealDataTests.DumpMenuComposites` and `StockUiRendererTests` (real D3D11 renders: HUD, party rows, target window + status icons) write PNGs. Dump harness flags:
  - `GORDIAN_UI_DUMP_MENUS=conf5win,conf*`: composites named menus with their label sprites into `menu_<name>.png` and dumps frame, buttons, navigation links, and referenced image parts to `menu_<name>.txt`.
  - `GORDIAN_UI_DUMP_GROUPS=group[:i-j+k],...` (default: `yubi,fontshp,framesus`): renders element group images onto 512 x 512 sheets with stock font index readouts. Also generates `groups.txt` cataloging every element group with image count and texture references.
  - `GORDIAN_UI_DUMP_TEXTURES=<name|*>`: writes decoded UI textures to `texture_<name>.png` and raw alpha channels to `texture_<name>_alpha.png`.
  - `GORDIAN_UI_DUMP_IMAGES=group:i-j+k,...`: dumps detailed quad destination vertices, UV coordinates, blend modes, and corner colors into `images.txt`.
- Reference DATs: EN menu 39542 (ROM/119/51), base menu 1 (ROM/0/1), window skins 14-21, status icons 87 (ROM/119/57), spell icons 39551 (ROM/280/15). Retail layout space is 512 x 448 with corner anchors; part colours are RGBA, bottom row first, 0x80 = 1.0; attribute byte 2 is the blend mode (2 = darken).
- Party/target rows are client-composed (not DAT layouts): `StockUiPartyWindow` / `StockUiTargetWindow` hold the measured offsets, font scale (7/8), gauge tints and leader ball (8 px by request; retail ~6 px).
- Events: `GORDIAN_UI_DUMP_MENUS=query` shows the choice window's frame. Reading zone scripts: [events/vm.md](../events/vm.md#working-notes).
- Menus: `StockUiMenuController` (stack, nav links, prompts, config rows, list pages) + `StockUiMenuEntries` (what each button means) + `StockUiConfigPages` / `StockUiSettings` (config rows and values) in Core; `StockUiMenuWindow` draws one open menu. `RetailMenus_EverySelectableButtonHasAnEntry` covers every driven menu and config page. Upscale `menu_<name>.png` with ImageMagick to read the labels; render label sprites alone with `GORDIAN_UI_DUMP_GROUPS=windowps:13-28`. The group dump draws images in ascending index order, not in the order listed in the variable. Beware the older page variants that share a title (`conf5` vs `conf5win`, `conf2` vs `conf2win`, `conf10`/`conf6win`, `conf12`/`conf12wi`): `configwi` opens the `*win`/`*wi` ones.
