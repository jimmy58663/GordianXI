# Stock DAT 2D UI

> The Tier 2 stock UI: Section 0x30/0x31 decoding, the sprite renderer and layout model, HUD windows, menus and config pages (Phase 5E Tier 2), plus Tier 3 ImGui overlays. Status and open work: [ROADMAP.md](../../ROADMAP.md) and GitHub Issues.

## Data layer (chunk 1)

- **Chunk 1: UI data layer.** `UiElementGroupDecoder` (Section 0x31: texture list, images of 61-byte parts = destination quad TL/TR/BL/BR, source rect, flags, per-corner RGBA colours in the 0x80 half-scale convention, sampled texture id), `UiMenuDecoder` (Section 0x30: frame with 2-bit screen anchor, buttons with 4-way nav links, 20-byte shape references to group images, help/title text ids) and `UiResourceLibrary` (English menu DAT 39542 = ROM/119/51, base menu DAT 1 = ROM/0/1 for fonts it omits, window skins 14-21 = ROM/0/14-21 overriding `newtex`/`hfr1`/`corner`/`vfr1`; textures decode lazily). Every group and menu in the retail DATs decodes to within its section padding; 3625 of 3630 shape references resolve (the rest are lobby-only); menus are authored in the 512 x 448 PS2 layout; UI textures wrap (window backgrounds tile `newtex`); menu labels are pre-rendered sprites (`windowps`), and `fontshp` glyphs run from ASCII 0x20. A software composite of the log, party, target and main-menu windows matches the retail look.

## Renderer and layout model (chunk 2)

- **Chunk 2: Tier 2 sprite renderer & layout model.** `StockUiRenderer` draws element-group images and text as batched screen-space quads after the 3D pass (`RenderTier2_StockUi`): per-corner vertex colours doubled from the 0x80 half scale, texture alpha normalized on upload (DXT3 UI sheets peak at 0x88, DXT1 at 0xFF; both mean opaque), bilinear wrap sampling. Window backgrounds fade to half brightness and half opacity toward the bottom through their authored corner colours (0x7F top, 0x40 bottom), which is the retail translucency. `StockUiLayout` (Core) resolves every persistent window from its authored position and anchor corner plus an optional per-window override (anchor, position, scale, hidden), clamped on screen; keys are logical window ids (`StockUiWindowIds`) because windows swap layouts at runtime (party `ptw1`..`ptw6` by member count, log `log1`..`log8` by line count). Default scale 1 = the retail PC layout (one screen pixel per layout pixel). `StockUiLayoutStore` shares one layout per character (`ui_layouts/<name>.json`, saved on change) between the HUD and `/uilayout [scale n | reset]` / `/uilayout <window> <hide|show|reset|scale n|move x y [anchor]>`; `MoveTo` (for chunk 4b) re-anchors to the nearest corner. `UiFont` measures and draws `fontshp` glyphs. Compared against Windower captures (2026-09-25; retail draws the UI at one screen pixel per layout pixel at 2560 x 1440): part corner colours are stored bottom row first, so windows are translucent at the top; the attributes' second byte is the part blend mode (2 = darken, used by text shadows, the band behind window titles and separators; 1 = add); the client draws its own window border (the skin's `hfr1` strip along the top and bottom edges, added at ~85% so the bottom line reads lavender over the navy, fading over 16 px at the ends). The party window uses `ptw0` (titled Solo) outside a party; the log window stretches right to meet the party window (2 px gap) unless moved. Party rows (`StockUiPartyWindow`) are composed by the client, not the DAT: name, HP number (hpcol colours by HP%) and MP number in `fontshp` at 7/8 size (the glyphs carry their own dark outline; the client adds no shadow) (names that do not fit before a four-digit HP number keep their longest fitting prefix plus "..", as retail shows "Tarudrake" as "Tarudra.."), the HP gauge (5 x 5 knob + strip middle stretched to 64 px) and MP gauge (unstretched strip) from the `gauge` texture tinted by measured fills, and the party-leader ball; positions within a pixel of the capture. Opt-in (not retail): party TP under the name (`/uilayout tp on`). **Members in another zone (#146):** the server sends no vitals for a member who is not in your zone, so the row shows the name and the zone's compact name in parentheses on the second line (`(SSandOria)`, `PartyRowVitals.ZoneName`) instead of the HP/MP numbers and gauges (retail capture, Windower 2026-09-29: "Cybin" / "(SSandOria)"); the leader ball still shows and the opt-in TP is not drawn. The text is `ROM/165/85` (`DMsgCategory.ZoneNamesCompact`, indexed by zone id like ROM/165/84: 230 `SSandOria`, 231 `NSandOria`, 232 `PSandOria`, 233 `ChatdOrag`, 234 `BastokMine`, 235 `BastokMark`, 236 `PortBastok`, 244 `UpJeuno`, 246 `PortJeuno`; no spaces or punctuation; not ROM/165/83, which holds the display abbreviations "S.San d'Oria"). "Another zone" is decided by `PartyMember.IsInOtherZone(currentZone)`: a reported ZoneNo that is non-zero **and** differs from your zone. LandSandBoat's S2C 0x0DD / 0x0E2 set ZoneNo only for a member elsewhere (0 = same zone, vitals present), but S2C 0x0C8 lists every member's zone, same-zone ones included, so non-zero alone would mark everyone; comparing against `WorldState.CurrentZoneId` handles both packets. `PartyState.UpsertMember` stores a 0x0DD/0x0E2 ZoneNo as given (0 clears it, so a returning member's gauges come back) and skips the zeroed HP/MP/TP/percent fields while the member is elsewhere (the last real vitals are kept); a 0x0C8 ZoneNo only overwrites when non-zero. The party window and the alliance windows share the rule; an alliance row (16 px, no second line) shows the zone where its gauge would be, right-aligned to the HP number's edge. Evidence: LandSandBoat `0x0dd_group_list.cpp` and `0x0c8_group_tbl.cpp`, the retail capture above and the issue text. **Unverified against retail:** the zone text's exact position and colour (right-aligned, as retail, at the MP number's right edge, row x + 96, 10 px below the name, default white `fontshp` at 7/8; confirmed right-aligned in-game 2026-10-03), and the alliance placement (right edge at the HP number's, row x + 87, 4 px below the row top). Party vitals: member HP/MP/TP changes arrive as S2C 0x0DF and now update `PartyState` (previously only 0x0DD at roster changes, so members froze), roster tables (0x0C8) no longer zero stored vitals, and the local player's row reads its own live vitals. Verified offscreen on D3D11 (`StockUiRendererTests`); the depleted-gauge look was accepted in-game.

## Menu input (chunk 4)

- **Chunk 4: Menu input.** `StockUiMenuController` (Core `Ui/`, owned by `PlayerActionService.Menus`) keeps a stack of open DAT menus and is fed each locomotion tick: `OpenMenu` (`-`/`M`, pad `X`/Start) opens the main "Commands" menu and, pressed again, turns its page (retail; only `Cancel` closes); the new `MenuUp/Down/Left/Right` actions (arrows, keypad 8/2/4/6, d-pad) move the cursor along each button's authored navigation links with key repeat (0.4 s, then every 90 ms); `Confirm` activates and `Cancel` closes the top window. The menu bindings share their keys with the camera and party-targeting actions, so `InputProfile.TryGetAction` takes a menu context (`InputState.MenuContext`): in a menu the shared keys navigate and the camera keys pause, while WASD and the left stick keep moving the character, as in retail (confirmed in-game 2026-09-26). Left/right on a list whose links point back at the button flip the main menu's pages (`menuwind` ↔ `socialme`, keeping the row; the page arrows, buttons 13/14, draw only on paged menus); the cursor position of every menu and the last page are remembered. The DAT carries no meaning for the buttons, so `StockUiMenuEntries` maps them (labels read from their `windowps` sprites): page 1 Status, Equipment, Magic, Items, Synthesis, Abilities, Party, Trade, Search, Linkshell, Region Info, Map; page 2 Missions, Quests, Key Items, View House, Bazaar, Macros (opens `mcrmenu`, [macros.md](macros.md#windows-stock-ui-tier-2)), Config, Help Desk, Current Time, Communication, Shut Down, Log Out. Config opens the `configwi` list (Gameplay, Chat Filters, Font Colors, Windows, Log, Misc. 1-4, Effects, Mouse/Cam., Global, Gamepad); Windows opens the `conf5m` list (Shared / Window 1 / Window 2), which replaces the config list in its corner, and Shared opens `conf5win` ("Window Settings (Shared)") at the left, as a retail capture shows: its eight Window Type digits (`keytops3` sprites) select the window skin (ROM/0/14-21), the skin in effect underlined with retail's red bar, applied live by reloading the UI resources and persisted in the layout (`StockUiLayout.WindowSkin`, also `/uilayout skin <1-8>`). Log Out / Shut Down ask "Log out?" / "Shut down?" through `PromptYesNoAsync` (the `comyn` window with client-drawn text, `yesno` without one; cancel = No, default No) and then send the 0x0E7 logout request. Current Time posts the Vana'diel date; entries whose window does not exist yet post a notice to the log (`NoticePosted`, shown in the stock log and by `ChatViewModel`). Drawing (`StockUiMenuWindow`, from `StockUiHud`): the root menu takes the layout's `menu` placement and sub-menus keep their authored place relative to it (they follow a moved main menu rather than taking overrides); a window whose authored rectangle a later window covers is hidden (a sub-menu opened in the same corner replaces its parent, as retail); the cursor is the frame's kind-6 element group (`anc_s`, the six-frame gold arrow authored 32 px to the left of its origin, not the `yubi` hand, which is the mouse pointer), drawn at the selected button's origin plus the frame's and button's cursor offsets and animated with the target cursor's 67 ms ping-pong; the selected entry is tinted orange, glyphs (light, peak FFC05C in a retail capture; key-cap digits included) and capsule (deeper: (127, 133, 186) becomes (133, 87, 48)); the darkening shadows keep their colour; the alternate (kind 4) images some buttons carry (Synthesis, Party, Gamepad) are not the selected look and are not drawn until their meaning is known. The DAT's navigation link bytes are up, down, right, left (the first reading had left/right swapped; caught in-game on the three-column settings rows). Verified offscreen on D3D11 (`RendersOpenMainMenuWithCursor`, `RendersWindowSettingsPage`): cursor beside the entry, title band, page arrows, prompt text, highlighted digit and red bar.
  - Still open: help text (`helpwind` at the top of the screen) and window titles are not drawn yet (the string tables they need are decoded, see [Menu string tables](#menu-string-tables-19)); the windows behind Status, Magic, Map and the rest of the entries (client-composed content) are later chunks (Items and Equipment: [below](#items-and-equipment-windows-351-352)); the config pages beyond Window Type are chunk 4c; mouse input is below ([#22](https://github.com/jimmy58663/GordianXI/issues/22)).
  - Menu labels are pre-rendered sprites (`windowps` images referenced by each button's shape references); a button's second shape reference (kind 4) is its alternate/highlighted image; frames carry the cursor group reference (kind 6: `anc_s` on list menus, `anc_equi`/`anc_item`/`anc_shop` on grids; the chat input line `inline` names `yubi`).

## Menu string tables ([#19](https://github.com/jimmy58663/GordianXI/issues/19))

The config rows table feeds the list pages (`ConfigRowText`) and the help table the Items and Equipment windows' help bar (`DMsgCategory.MenuHelp`, `MenuHelpText`, #351); the titles table is not read yet. The tables were found (2026-09-28) by searching every ROM DAT for known help strings (plain and XOR 0xFF), then checked against the menu DAT.

- **Where the text lives.** Three `d_msg` tables in ROM/165, XOR 0xFF, variable-stride layout (`tsize` > 0, 8-byte offset/length pairs), one string per record. `DMsgStringTable` already parses them. Indexes are the raw ids from the menu records, starting at 0; `-1` means none.

  | Table | English | Japanese | Records | Indexed by |
  |---|---|---|---|---|
  | Help text (`helpwind`) | 55651 = ROM/165/75 | 55531 = ROM/165/59 | 1099 | `HelpTextId` on frames and buttons |
  | Window titles | 55652 = ROM/165/76 | 55532 = ROM/165/60 | 201 | `TitleTextId` (frames; the main menu's buttons carry the title of the window they open) |
  | Config rows | 55650 = ROM/165/74 | 55530 = ROM/165/58 | 206 | nothing in the DAT; the client picks rows by index |

  The Japanese table is 120 file ids below the English one. The rest of ROM/165/69-87 is the English set of other client strings (lobby errors 70, lobby status 71, party and system messages 72-73, regions, weather, days, directions, moon phases, zone names, job names); ROM/165/53-68 is the Japanese set.

## Text boxes: one wrap and clip for every window (round 4, 2026-10-19)

- **The question (the maintainer, round 4):** is there a central window definition with a width and height that controls word wrap and text bounds? Before this change, no: the DAT frames give each window its size, but every window wrapped its own text, with five helpers (`StockUiItemDescription.WrapWords` by a fixed 42 characters, `StockUiMenuWindow.Wrap`, `StockUiTreasureWindow.Wrap`, `StockUiKeyItems.Wrap`, each by measure), and nothing clipped. The 42-character rule put "Lv.7 WAR RDM THF PLD DRK BST BRD RNG SAM" on one line of the Leather Bandana, wider than the window in the log font's capitals (image-17).
- **Now:** `StockUiTextLayout` (Core) is the one layout: text wrapped at spaces to a box's width as the drawing font measures it, the text's own line breaks kept, a word wider than the box broken between characters, cut to the lines the box holds. `StockUiTextBoxes` (App) draws a box's lines at the font's pitch and clips them to the box (`StockUiRenderer.SetClip`), so nothing can run past a frame even if a measure were off. The box is the frame's text area: for the item info windows (`iteminfo`, `item4inf` ... `item12in`, 366 wide) from (48,4) to 8 px before the right edge, `StockUiItemDescription.TextWidth` = 310 px.
- **Windows on it:** the item description pages (`StockUiItemDescription.Pages`: description and job list wrapped with the log font's measure, `StockUiItemDescription.FontMeasure`, set by the HUD) as the Items, Equipment, player check, Equipment Sets editor, Key Items (equipment) and Synthesis windows draw them (`StockUiItemWindow.DrawDescriptionPage`); the NPC shop and guild shop item info (`StockUiMenuWindow.DrawItemInfo`, the menu font at its 14 px pitch); the Treasure Pool item info; the Key Items Examine question and key item description; the wrapping of prompt messages and of the action lists' empty text (laid out by it, drawn centred as before). Not on it, on purpose: the chat log (`StockUiChatLog.Wrap`, per-character advances and timestamps) and the target window's name (`StockUiTargetWindow.WrapName`, retail's own first-break rule, #258).
- **Retail:** the captures show item descriptions wrapped inside the window at spaces over several lines (`Synthesis_History.png`: "A white powder formed by applying / extreme heat to zinc ore."; the video's Apocalypse and Onion Sword III), at the normal font size and never cut mid-glyph; no capture shrinks the text. A job list as long as the Leather Bandana's is not captured, so where retail breaks it is PROVISIONAL (here: at the last job that fits the 310 px).
- *Checked:* `StockUiTextLayoutTests` (measured wrap, line breaks, over-wide words, line caps, the Leather Bandana's job list against a wide-capitals measure) and offscreen on D3D11 (`StockUiTextBoxRenderTests`: the bandana's description with the retail log font, nothing drawn right of the window; `GORDIAN_UI_DUMP` writes `gpu_text_box_bandana.png`).

## Menu mouse input and pointer ([#22](https://github.com/jimmy58663/GordianXI/issues/22))

- **Mouse on menus (2026-09-28, tested in-game).** The HUD publishes where it drew each visible open menu every frame (`StockUiMenuController.SetScreenPlacements`, `StockUiMenuPlacement` = menu, screen origin, scale; windows hidden behind a later one are left out) and `ViewportWindow` offers each mouse event to the stock UI before the input bus: the unlocked UI's drag first (left button), then the menus. Hit-testing uses each DAT button's rectangle (`X`, `Y`, `Width`, `Height` from the frame origin, times the scale), topmost window first; only buttons the cursor can reach take the pointer (a navigation link, list rows only while they show an entry), plus a paged menu's page arrows (buttons outside the frame, drawn only on the main menu). Behaviour: hovering an entry of the window taking input moves the cursor there; a left press on an entry selects and activates it as Confirm does; on an entry of a parent window still on screen it first closes the windows opened from it; while a yes/no prompt is up only its own buttons answer; a page arrow turns the page; a slider takes the value under the pointer (the bar's share, snapped to the setting's step) and follows the pointer until release; a press on a window's body or title is swallowed without selecting. A right press over a menu cancels (closes the top window) as the Cancel key does; elsewhere it is still camera look. The wheel over a scrolling list (Chat Filters) scrolls it an entry a notch without wrapping and is swallowed over any other menu (it does not zoom the camera). Presses outside every menu stay game input, and a release is the menus' whenever its press was.
- **Pointer (retail capture, 2026-09-28):** retail's pointer over the game is a small yellow arrow with a dark outline; over a clickable menu entry it becomes a grey ring over the arrow's tip, the rest of the arrow showing below right. The arrow is a Windows cursor in the client's `FFXiResource.dll` (cursor group 102/105: cursor 1 is the 32 x 32 8-bit arrow, hotspot (19, 19); cursor 2 is a blank 1-bit cursor, which suggests the client hides the system cursor over entries and draws the ring and arrow itself); the ring is in none of the 78 UI DAT textures, and a scan of every ROM DAT for cursor-like names found nothing. Neither is copied: `StockUiPointerArt` (App) draws GordianXI's own look-alikes in code (the arrow from a polygon, amber gradient and dark outline; the ring from two circles), a deliberate exception to legacy parity (the maintainer chose look-alikes over reading the DLL at runtime). The arrow is the viewport's system cursor, so it never lags a frame: on Windows an `HCURSOR` made from the bitmap (`Win32ChildWindowHelper.CreateCursorFromRgba`, per-pixel alpha) that the child window sets on `WM_SETCURSOR`; elsewhere an Avalonia bitmap cursor. Over a clickable entry (`StockUiMenuController.IsOverEntry` at `PlayerActionService.UiPointer`) the system cursor is hidden (`StockUiHud.PointerDrawn`) and the HUD draws the arrow and ring over everything (`StockUiMenuWindow.DrawHoverPointer`, one screen pixel per image pixel like the system cursor). The child window asks for `WM_MOUSELEAVE` (`TrackMouseEvent`) and elsewhere `PointerExited` clears the pointer, so the hover pointer is not left at the edge. (A first pass drew the `yubi` hand; retail PC does not show it over the game.)
- Not yet compared with retail: whether retail activates on press or on release, whether right-click cancels anywhere or only over a window, hover over a parent window (ignored here), the retail "Mouse Control Type 1/2" setting (Mouse/Cam. page; stored, not applied), and the pointer while the camera turns. Verified by `StockUiMenuControllerTests` (`Mouse_*`) and offscreen on D3D11 (`RendersOpenMainMenuWithCursor` draws the hover pointer).

## Movable stock UI (chunk 4b)

- **Chunk 4b: Movable stock UI (opt-in, 2026-09-27).** `/uilayout unlock` (and `lock`) sets `StockUiLayout.Unlocked`, saved with the layout so a player who opted in stays unlocked across launches (legacy parity by default: retail cannot drag its stock windows, and a fresh layout is locked); `StockUiDragController` (Core `Ui/`, `PlayerActionService.UiDrag`) reads the flag from the layout the HUD hands it each frame. While unlocked a hint line and a "Default positions" button sit at the top of the screen; the button (a registered region with the `button:` prefix, clicked rather than dragged) calls `StockUiLayout.ResetPositions`, which drops every window's position and anchor override and keeps scales, hidden flags, skin and options (`/uilayout reset positions` does the same; plain `/uilayout reset` still restores everything and locks). The HUD registers each persistent window's screen rectangle as it draws it (`log` = Window 1 and Window 2 with their title bands, `chat`, `party`, `alliance1`/`alliance2`, `target`, `status`, `menu` = the root menu only) and `StockUiDragOverlay` (App) outlines them (translucent white; pale yellow under the pointer, orange while dragged) with the window id in `fontshp`; windows with nothing to show (no target, no status effects, no alliance, closed menu or input line) are drawn as empty frames with a faint blue fill and labelled "(empty)" so they can still be placed. A left press over a window starts a drag (the press is not game input; right-click camera look still works), the window follows the pointer clamped to the screen, and only the release writes the layout, through `StockUiLayout.MoveTo` (re-anchored to the nearest screen corner, saved to the character's layout file); while dragged the HUD substitutes the transient position and treats the window as moved (the target window leaves the party window, the input line leaves Window 1). The log windows keep the retail arrangement's width wherever they are: Window 1 stretches from its authored left edge to 2 px short of the party window's retail place (or 16 px from the screen's right edge when the party window is hidden), the Window Width sliders then take their share, and a moved log or input line is clamped to stay on screen at that width (in-game 2026-09-27: a dragged log first shrank to its authored 366 px). Esc locks the UI (once no menu is open for it to cancel). Runtime-placed windows (sub-menus, prompts) are never registered: they follow their parent. The status icon region is the icon slots in use (the "buff" frame is only a strip), all slots when empty. The chat input line is now separately placeable: with a `chat` override it takes that placement at its authored width and Window 1 shows all its rows; otherwise it stays over the bottom of Window 1 as retail. Mouse positions reach the controller by two routes, both wired in `ViewportWindow`: on Windows the subclassed native child window's raw Win32 messages (rendering-surface pixels; a button message carries no position, so the move that precedes it is kept), elsewhere Avalonia's window-level pointer events (the position over the viewport control times the render scaling). The child is a `static` class HWND, which reports itself transparent to mouse hit-testing, so until 2026-09-27 every mouse message over the viewport fell through to Avalonia's native-host holder window and was swallowed: no click, hover or right-drag camera look ever arrived by either route (confirmed in-game: no press line in the log). `Win32ChildWindowHelper` now answers `WM_NCHITTEST` with `HTCLIENT` and captures the mouse while a button is held, so the raw route is the one in use. Every left press while unlocked writes an Info line to the log (`Stock UI unlocked press (avalonia|raw) at (x, y) hit <id>; N regions; viewport w x h at scale s`) so a drag that does not start can be traced. Hidden windows are not shown while unlocked (`/uilayout <window> show` first). Verified offscreen on D3D11 (`RendersUnlockedOverlayOutlinesAndPlaceholders`) and by `StockUiDragControllerTests` / `UiLayoutCommandTests`.

Built-in Gordian HUD pieces use this Tier 2 renderer by default for retail parity, and Gordian addons get it too (`gordian.ui`, [post-mvp.md](../design/post-mvp.md)). Comparison and reasons: [reference/dependencies.md](../reference/dependencies.md#hud-and-addon-ui-imgui-and-stock-ui-sprites).
- [x] **Stock UI visibility API (`StockUiVisibilityState`, [#29](https://github.com/jimmy58663/GordianXI/issues/29)).** Run-time hiding of stock HUD elements so an addon or ImGui replacement can take one's place without overlap. It lives in Core (`Gordian.Core.Ui`) and each session has one (`PlayerActionService.UiVisibility`), so the App's HUD and the Phase 6 addon runtime share it without referencing each other.
  - **Elements (`StockUiElement` flags):** `TargetBar` (target window), `Vitals` (the party window while solo, "ptw0": the stock client shows the player's own vitals there), `Party` (the party window in a party, "ptw1".."ptw6"), `Alliance` ("raid1", "raid2"), `Buffs` (status icons), `Menus` (main menu tree, event choices, command menu, shop, home point, check window, and the action help bar), `Chat` (log windows and the chat input line), `NamePlates`, `TargetCursor` (target and sub-target cursors), `All`. In a party, the party window also lists the other members, so `Vitals` alone leaves it up; hide `Party` too.
  - **Owners:** each caller hides under its own name (`Hide`, `Show`, `Set`, `Release`); an element is hidden while any owner hides it, so one addon showing an element never undoes another's hide, and releasing an owner (an addon unloading) drops all its hides. Not saved: owners apply theirs when they start. Writes lock; the render thread reads the combined flags lock-free.
  - **HUD:** `StockUiHud` reads the flags once a frame and treats a hidden element's window exactly like a `/uilayout <window> hide` (`ResolveWindow` marks its placement hidden), so the dependent layout follows: with the party window hidden the target window keeps its own place and the log stretches as when the party window is hidden by layout. Name plates, cursors and the help bar are skipped directly. The persistent per-window `/uilayout` hides are unchanged; a window is hidden when either says so.
  - **`/stockui [hide | show <element ...|all>] | reset`:** the player's own hides (owner `user`), until the client restarts; with no argument it lists what is hidden and by whom. `show` reports elements an addon still hides. For a clean screen: `/stockui hide all`.
  - **Hidden elements take no input (round 2 of the #30/#29 test).** Hiding is for letting a replacement draw and drive the element, so a hidden stock element must not fight it for the keys:
    - *Menus hidden:* the stock menus do not open and do not read input. The menu key (`OpenMenu`) does not open the main menu; Confirm on a target opens no command menu (`OpenTargetCommandMenu` returns false), though talking to an NPC still works; and the input does not switch to menu context. Confirm, Cancel, the arrows and the menu key therefore keep their gameplay meanings (targeting, camera, Cancel clearing the target), which a replacement can read from `InputState`. Mouse clicks hit no hidden menu, because the HUD registers no menu placements. A menu that was already open, or that the server opens while hidden (event choices, shop, home point, check), stays in the menu model but takes no input. A replacement drives it through the model; with no replacement, `/stockui show menus` (or the restore below) shows it again and gives it the keys back. An event choice therefore waits until then.
    - *Chat hidden:* the chat line does not open: neither Enter, the chat key (`OpenChat`), nor typed text. An open input line, a selected log window and the full-screen log are let go at once (the window cancels the line on the next key, the input tick on the next frame), and keypad + does not select the log. The keys go to the game instead.
  - **Getting the stock UI back** when nothing replaces a hidden chat, so `/stockui show chat` cannot be typed in-game:
    - **Ctrl+Shift+F12** in the viewport window drops every hide for the character on screen, the player's and any addon's (`StockUiVisibilityState.ReleaseAll`; an addon re-applies its hides when it next starts). A notice confirms it in the main window's chat tab.
    - The main window's **Command Console** tab runs slash commands for its selected character without the in-game chat line, so `/stockui reset` or `/stockui show chat` work there. The console follows the character of whichever viewport window is active (`MainWindowViewModel.FollowViewportCharacter` and `AttachViewportFocus`, on `ViewportWindowManager.WindowFocus`). It switches to the main window's character when that window switches (Ctrl+Tab, a switcher click), and to a pop-out's character when the pop-out gets the focus or switches. A character picked by hand in the console holds while the focus is outside the viewport windows (for example while using the console) and until a viewport window is focused again or switches character. Round 4: focusing a pop-out had left the console on the main window's character. Round 3 of the in-game test: with two characters logged in, the console stayed on the first registered one, so `/stockui show chat` reported success for that character while the chat of the one on screen stayed hidden (`ConsoleStockUiRestoreTests`).
    - Hides are never saved, so a restart also clears them.
  - [ ] **Addons respect cutscenes:** addon overlays (minimap, party frames, any ImGui window) are not drawn while an event hides the HUD (`EventDialogController.IsCutsceneHud`, the event message mode), as the stock windows are. Retail's minimap is itself an addon (Windower) that stays up through intros, so an addon opts in through the suppression API; the default for every addon is hidden during a cutscene (maintainer's requirement, 2026-10-01).
