# Stock DAT 2D UI

> The Tier 2 stock UI: Section 0x30/0x31 decoding, the sprite renderer and layout model, HUD windows, menus and config pages (Phase 5E Tier 2), plus Tier 3 ImGui overlays. Status and open work: [ROADMAP.md](../../ROADMAP.md) and GitHub Issues.

## Data layer (chunk 1)

- **Chunk 1: UI data layer.** `UiElementGroupDecoder` (Section 0x31: texture list, images of 61-byte parts = destination quad TL/TR/BL/BR, source rect, flags, per-corner RGBA colours in the 0x80 half-scale convention, sampled texture id), `UiMenuDecoder` (Section 0x30: frame with 2-bit screen anchor, buttons with 4-way nav links, 20-byte shape references to group images, help/title text ids) and `UiResourceLibrary` (English menu DAT 39542 = ROM/119/51, base menu DAT 1 = ROM/0/1 for fonts it omits, window skins 14-21 = ROM/0/14-21 overriding `newtex`/`hfr1`/`corner`/`vfr1`; textures decode lazily). Every group and menu in the retail DATs decodes to within its section padding; 3625 of 3630 shape references resolve (the rest are lobby-only); menus are authored in the 512 x 448 PS2 layout; UI textures wrap (window backgrounds tile `newtex`); menu labels are pre-rendered sprites (`windowps`), and `fontshp` glyphs run from ASCII 0x20. A software composite of the log, party, target and main-menu windows matches the retail look.

## Renderer and layout model (chunk 2)

- **Chunk 2: Tier 2 sprite renderer & layout model.** `StockUiRenderer` draws element-group images and text as batched screen-space quads after the 3D pass (`RenderTier2_StockUi`): per-corner vertex colours doubled from the 0x80 half scale, texture alpha normalized on upload (DXT3 UI sheets peak at 0x88, DXT1 at 0xFF; both mean opaque), bilinear wrap sampling. Window backgrounds fade to half brightness and half opacity toward the bottom through their authored corner colours (0x7F top, 0x40 bottom), which is the retail translucency. `StockUiLayout` (Core) resolves every persistent window from its authored position and anchor corner plus an optional per-window override (anchor, position, scale, hidden), clamped on screen; keys are logical window ids (`StockUiWindowIds`) because windows swap layouts at runtime (party `ptw1`..`ptw6` by member count, log `log1`..`log8` by line count). Default scale 1 = the retail PC layout (one screen pixel per layout pixel). `StockUiLayoutStore` shares one layout per character (`ui_layouts/<name>.json`, saved on change) between the HUD and `/uilayout [scale n | reset]` / `/uilayout <window> <hide|show|reset|scale n|move x y [anchor]>`; `MoveTo` (for chunk 4b) re-anchors to the nearest corner. `UiFont` measures and draws `fontshp` glyphs. Compared against Windower captures (2026-09-25; retail draws the UI at one screen pixel per layout pixel at 2560 x 1440): part corner colours are stored bottom row first, so windows are translucent at the top; the attributes' second byte is the part blend mode (2 = darken, used by text shadows, the band behind window titles and separators; 1 = add); the client draws its own window border (the skin's `hfr1` strip along the top and bottom edges, added at ~85% so the bottom line reads lavender over the navy, fading over 16 px at the ends). The party window uses `ptw0` (titled Solo) outside a party; the log window stretches right to meet the party window (2 px gap) unless moved. Party rows (`StockUiPartyWindow`) are composed by the client, not the DAT: name, HP number (hpcol colours by HP%) and MP number in `fontshp` at 7/8 size (the glyphs carry their own dark outline; the client adds no shadow) (names that do not fit before a four-digit HP number keep their longest fitting prefix plus "..", as retail shows "Tarudrake" as "Tarudra.."), the HP gauge (5 x 5 knob + strip middle stretched to 64 px) and MP gauge (unstretched strip) from the `gauge` texture tinted by measured fills, and the party-leader ball; positions within a pixel of the capture. Opt-in (not retail): party TP under the name (`/uilayout tp on`). Party vitals: member HP/MP/TP changes arrive as S2C 0x0DF and now update `PartyState` (previously only 0x0DD at roster changes, so members froze), roster tables (0x0C8) no longer zero stored vitals, and the local player's row reads its own live vitals. Verified offscreen on D3D11 (`StockUiRendererTests`); the depleted-gauge look was accepted in-game.

## Live HUD (chunk 3)

- *Target window:* `targetwi` shown while something is targeted, stacked on the party window with a 2 px gap unless moved (its authored y fits only a six-member party); name in fontshp 7/8 coloured by claim (unclaimed monster pale yellow, claimed by you/party red, sampled from Windower; claimed by others purple, retail convention not yet captured; players/NPCs white); HP gauge as the party window's at (28, 28). Depleted gauge share is the captured light lavender (party window too).
- *Status icons:* `StatusIconLibrary` reads the status resource DAT (file id 87, ROM/119/57: 640 records of 0x1800 bytes in status-id order, icon at +0x280 like item icons); `LocalPlayerState.GetStatusEffectIds` decodes the 0x037 slots (low byte + 2 high bits, 0xFF empty); icons draw 24 x 24 on the `buff` menu grid (frame (142, 48), 26 px pitch, nine per row), matching the capture.
- *Target cursor:* the "anc_s" group (ROM/0/1 `anc` texture; the same diamond-and-arrowhead cursor as the menus, authored pointing right) turned to point down, drawn at UI scale with its tip at the skeleton's overhead point, projected from the entity pass (`EntityRenderer.TargetAnchor`). That point is skeleton reference 2, a straight offset up from the root joint authored per skeleton (Goblin 1.8, Island Rarab 1.7, Raven 2.8, Marine Dhalmel 6.05; Hume 2.0, Tarutaru 1.3, Galka 2.6 yalms), fixed per model so the cursor does not bounce with the animation (it followed the live pose until a bird's wing beat showed that). Windower screenshots (Raven, Marine Dhalmel, Island Rarab, 2026-09-29) show retail centring the name plate there (the Dhalmel's head top, well above the small Rarab) with the cursor a short gap above the name; the tip now sits above the target's name plate ([Name plates](#name-plates-28)), or at the point itself when the target has no plate. A skeleton without the reference falls back to its highest idle joint plus 0.6 yalms; it shades through the six frames and back at ~67 ms a step (0.8 s cycle), measured from a retail capture.
- *Target selection flash:* a newly selected target's model brightens in three triangular pulses of ~0.72 s (`TargetFlash`, light added before the texture modulate, peak +0.5, so the colour roughly doubles as in the capture); selecting another target restarts it there and cuts the old one short.
- *Lock-on:* while locked on, the "targetlo" overlay (windowps image 212: red corner brackets, "Locked" between two arrow key-tops, side glow bars from "colorbal") draws over the target window.
- *Alliance windows:* "raid1"/"raid2" (authored at 48 and 150, 100 tall, 16-pixel rows, directly above the target window's slot so they do not move with it); rows are name, HP number and HP gauge at the party rows' offsets, no MP (measured from 1:1 retail alliance captures). Your own party stays in the Party window; the other parties fill raid1 then raid2 by party number (0x0C8/0x0DD PartyNo, bits 0-1). Party, target and each alliance window are separately placeable (`party`, `target`, `alliance1`, `alliance2`). Leader balls now come from "colorbal" (the captures' greenish yellow; the alliance leader shows a cream-white ball with the yellow one beside it, AllianceLeaderFlg bit 3). The group table (0x0C8) now also drops members it no longer lists.
- *Party member status icons* (opt-in, not in the legacy client): `/uilayout buffs <on|off|left|right>`, 16 x 16 icons in a line beside each party row, first nearest the window; other members from S2C 0x076 (now stored on `PartyMember.StatusEffectIds`), your own row from your live status.
- *Idle step fix:* S2C 0x037 no longer copies the movement speed stat into the local entity's current Speed (a standing player took a step on every status update, ~3 s apart).
- [ ] *Expiring status icons blink:* needs status durations (S2C 0x063 status-icon packet) wired into `LocalPlayerState`.
- Claimed-by-others target names are pink (240, 122, 180 from an alliance capture of Tiamat); confirm against a capture where the claim is known to be another group's.

## Menu input (chunk 4)

- **Chunk 4: Menu input.** `StockUiMenuController` (Core `Ui/`, owned by `PlayerActionService.Menus`) keeps a stack of open DAT menus and is fed each locomotion tick: `OpenMenu` (`-`/`M`, pad `X`/Start) opens the main "Commands" menu and, pressed again, turns its page (retail; only `Cancel` closes); the new `MenuUp/Down/Left/Right` actions (arrows, keypad 8/2/4/6, d-pad) move the cursor along each button's authored navigation links with key repeat (0.4 s, then every 90 ms); `Confirm` activates and `Cancel` closes the top window. The menu bindings share their keys with the camera and party-targeting actions, so `InputProfile.TryGetAction` takes a menu context (`InputState.MenuContext`): in a menu the shared keys navigate and the camera keys pause, while WASD and the left stick keep moving the character, as in retail (confirmed in-game 2026-09-26). Left/right on a list whose links point back at the button flip the main menu's pages (`menuwind` ↔ `socialme`, keeping the row; the page arrows, buttons 13/14, draw only on paged menus); the cursor position of every menu and the last page are remembered. The DAT carries no meaning for the buttons, so `StockUiMenuEntries` maps them (labels read from their `windowps` sprites): page 1 Status, Equipment, Magic, Items, Synthesis, Abilities, Party, Trade, Search, Linkshell, Region Info, Map; page 2 Missions, Quests, Key Items, View House, Bazaar, Macros, Config, Help Desk, Current Time, Communication, Shut Down, Log Out. Config opens the `configwi` list (Gameplay, Chat Filters, Font Colors, Windows, Log, Misc. 1-4, Effects, Mouse/Cam., Global, Gamepad); Windows opens the `conf5m` list (Shared / Window 1 / Window 2), which replaces the config list in its corner, and Shared opens `conf5win` ("Window Settings (Shared)") at the left, as a retail capture shows: its eight Window Type digits (`keytops3` sprites) select the window skin (ROM/0/14-21), the skin in effect underlined with retail's red bar, applied live by reloading the UI resources and persisted in the layout (`StockUiLayout.WindowSkin`, also `/uilayout skin <1-8>`). Log Out / Shut Down ask "Log out?" / "Shut down?" through `PromptYesNoAsync` (the `comyn` window with client-drawn text, `yesno` without one; cancel = No, default No) and then send the 0x0E7 logout request. Current Time posts the Vana'diel date; entries whose window does not exist yet post a notice to the log (`NoticePosted`, shown in the stock log and by `ChatViewModel`). Drawing (`StockUiMenuWindow`, from `StockUiHud`): the root menu takes the layout's `menu` placement and sub-menus keep their authored place relative to it (they follow a moved main menu rather than taking overrides); a window whose authored rectangle a later window covers is hidden (a sub-menu opened in the same corner replaces its parent, as retail); the cursor is the frame's kind-6 element group (`anc_s`, the six-frame gold arrow authored 32 px to the left of its origin, not the `yubi` hand, which is the mouse pointer), drawn at the selected button's origin plus the frame's and button's cursor offsets and animated with the target cursor's 67 ms ping-pong; the selected entry is tinted orange, glyphs (light, peak FFC05C in a retail capture; key-cap digits included) and capsule (deeper: (127, 133, 186) becomes (133, 87, 48)); the darkening shadows keep their colour; the alternate (kind 4) images some buttons carry (Synthesis, Party, Gamepad) are not the selected look and are not drawn until their meaning is known. The DAT's navigation link bytes are up, down, right, left (the first reading had left/right swapped; caught in-game on the three-column settings rows). Verified offscreen on D3D11 (`RendersOpenMainMenuWithCursor`, `RendersWindowSettingsPage`): cursor beside the entry, title band, page arrows, prompt text, highlighted digit and red bar.
  - Still open: help text (`helpwind` at the top of the screen) and window titles are not drawn yet (the string tables they need are decoded, see [Menu string tables](#menu-string-tables-19)); the windows behind Status, Equipment, Magic, Items, Map and the rest of the entries (client-composed content) are later chunks; the config pages beyond Window Type are chunk 4c; mouse input is below ([#22](https://github.com/jimmy58663/GordianXI/issues/22)).
  - Menu labels are pre-rendered sprites (`windowps` images referenced by each button's shape references); a button's second shape reference (kind 4) is its alternate/highlighted image; frames carry the cursor group reference (kind 6: `anc_s` on list menus, `anc_equi`/`anc_item`/`anc_shop` on grids; the chat input line `inline` names `yubi`).

## Menu string tables ([#19](https://github.com/jimmy58663/GordianXI/issues/19))

Research only (2026-09-28), nothing reads these tables yet. Found by searching every ROM DAT for known help strings (plain and XOR 0xFF), then checked against the menu DAT.

- **Where the text lives.** Three `d_msg` tables in ROM/165, XOR 0xFF, variable-stride layout (`tsize` > 0, 8-byte offset/length pairs), one string per record. `DMsgStringTable` already parses them. Indexes are the raw ids from the menu records, starting at 0; `-1` means none.

  | Table | English | Japanese | Records | Indexed by |
  |---|---|---|---|---|
  | Help text (`helpwind`) | 55651 = ROM/165/75 | 55531 = ROM/165/59 | 1099 | `HelpTextId` on frames and buttons |
  | Window titles | 55652 = ROM/165/76 | 55532 = ROM/165/60 | 201 | `TitleTextId` (frames; the main menu's buttons carry the title of the window they open) |
  | Config rows | 55650 = ROM/165/74 | 55530 = ROM/165/58 | 206 | nothing in the DAT; the client picks rows by index |

  The Japanese table is 120 file ids below the English one. The rest of ROM/165/69-87 is the English set of other client strings (lobby errors 70, lobby status 71, party and system messages 72-73, regions, weather, days, directions, moon phases, zone names, job names); ROM/165/53-68 is the Japanese set.
- **Check.** Every help and title id in the English menu DAT (39542, all 404 menus) is in range and resolves to non-empty text: 676 distinct help ids (up to 1098), 132 title ids (up to 198). Samples: main menu Status = help 321 "View status." / title 81 "Status"; `menuwind` Synthesis = help 816 / title 170; `chatctrl` = help 595 "Set your default chat mode." / title 129 "Chat"; `conftxtc`/`textcol1`/`textcol3` = title 55 "Font Colors", help 488 "Select a text category.", 489 "Set RGB color values."; `fxfilter` = help 599 / title 128 "Filter"; `conf11l`/`conf11s`/`conf11m` = title 175 "Log Settings", help 901-907; `playermo` Request = help 954.
- **ROM/97 is the legacy set, not the current one.** xi-tools points at ROM/97; it holds `XISTRING` tables (magic `XISTRING`, u32 file size / count / index size / data size at 0x20, index at 0x38 of 12-byte entries: u32 offset, u16 length, u16 flags where bit 0 marks format codes, 4 unused bytes, then NUL-terminated CP932 strings). English help is ROM/97/42 (file id 54, 653 records) and titles ROM/97/41 (53, 143 records); Japanese ROM/97/24 and 97/23. They are an older snapshot: the titles are a prefix of ROM/165/76, the help table has 31 older wordings ("Dismount your chocobo." vs "Dismount."), and ids above 652 / 142, which today's menus use, are missing. Use ROM/165.
- **Config row table (ROM/165/74), by index.** 0-10 channel names (Say, Shout, Tell, Party, Linkshell, Linkshell 2, Assist J, Assist E, Unity, Emotes, Messages from alter egos); 11-32 and 171-182 battle message categories (on/by you, NPCs, party, allies, others, foes); 33-35 System Lv. 1-3; 36-47 long channel descriptions ("Immediate vicinity ("Say")"...), 196 Yell; 48-62 effect and system categories (HP/MP you recover... Basic system messages); 63-72, 197 and 204-205 the Font Colors rows ("Player: Color of "say" text"...); 73-88 Font Colors sample lines ("Player recovers 10 HP."...); 89-142 key and gamepad assignment names (Move Up... Hide/Show Window); 143 the key-reset prompt; 144 Lot results; 145-152 list headings; 153-170 Effects filter rows (All effects during battle, You → you ... Screen shaking); 183-201 assorted prompts; 192-195 spam and emote filters and Yell; 202-203 Battle Messages / Calls for help. The 55 Chat Filters labels that `StockUiConfigPages.ChatFilters` types in (from retail captures) all appear here word for word. The groupings are read from the text; which rows each page shows, and in what order, still needs retail captures (Log page categories, Font Colors list, Effects list).
- **Text.** Plain CP932 with no control, glyph (0xEF) or auto-translate (0xFD) codes in any of the three English tables; the only byte below 0x20 is a newline (0x0A) in three help lines (69, 71, 74, e.g. "Stop tracking current target / and proceed with wide area scan?"). The Effects rows use CP932 0x81A8 (→) and the list headings 0x816B/0x816C (〔〕).
- **Not yet decided:** how `helpwind` lays out long lines (wrap width, one or two lines) and when retail shows it (on cursor move, frame help vs button help precedence). Check against a capture when it is wired.

## Menu mouse input and pointer ([#22](https://github.com/jimmy58663/GordianXI/issues/22))

- **Mouse on menus (2026-09-28, tested in-game).** The HUD publishes where it drew each visible open menu every frame (`StockUiMenuController.SetScreenPlacements`, `StockUiMenuPlacement` = menu, screen origin, scale; windows hidden behind a later one are left out) and `ViewportWindow` offers each mouse event to the stock UI before the input bus: the unlocked UI's drag first (left button), then the menus. Hit-testing uses each DAT button's rectangle (`X`, `Y`, `Width`, `Height` from the frame origin, times the scale), topmost window first; only buttons the cursor can reach take the pointer (a navigation link, list rows only while they show an entry), plus a paged menu's page arrows (buttons outside the frame, drawn only on the main menu). Behaviour: hovering an entry of the window taking input moves the cursor there; a left press on an entry selects and activates it as Confirm does; on an entry of a parent window still on screen it first closes the windows opened from it; while a yes/no prompt is up only its own buttons answer; a page arrow turns the page; a slider takes the value under the pointer (the bar's share, snapped to the setting's step) and follows the pointer until release; a press on a window's body or title is swallowed without selecting. A right press over a menu cancels (closes the top window) as the Cancel key does; elsewhere it is still camera look. The wheel over a scrolling list (Chat Filters) scrolls it an entry a notch without wrapping and is swallowed over any other menu (it does not zoom the camera). Presses outside every menu stay game input, and a release is the menus' whenever its press was.
- **Pointer (retail capture, 2026-09-28):** retail's pointer over the game is a small yellow arrow with a dark outline; over a clickable menu entry it becomes a grey ring over the arrow's tip, the rest of the arrow showing below right. The arrow is a Windows cursor in the client's `FFXiResource.dll` (cursor group 102/105: cursor 1 is the 32 x 32 8-bit arrow, hotspot (19, 19); cursor 2 is a blank 1-bit cursor, which suggests the client hides the system cursor over entries and draws the ring and arrow itself); the ring is in none of the 78 UI DAT textures, and a scan of every ROM DAT for cursor-like names found nothing. Neither is copied: `StockUiPointerArt` (App) draws GordianXI's own look-alikes in code (the arrow from a polygon, amber gradient and dark outline; the ring from two circles), a deliberate exception to legacy parity (the maintainer chose look-alikes over reading the DLL at runtime). The arrow is the viewport's system cursor, so it never lags a frame: on Windows an `HCURSOR` made from the bitmap (`Win32ChildWindowHelper.CreateCursorFromRgba`, per-pixel alpha) that the child window sets on `WM_SETCURSOR`; elsewhere an Avalonia bitmap cursor. Over a clickable entry (`StockUiMenuController.IsOverEntry` at `PlayerActionService.UiPointer`) the system cursor is hidden (`StockUiHud.PointerDrawn`) and the HUD draws the arrow and ring over everything (`StockUiMenuWindow.DrawHoverPointer`, one screen pixel per image pixel like the system cursor). The child window asks for `WM_MOUSELEAVE` (`TrackMouseEvent`) and elsewhere `PointerExited` clears the pointer, so the hover pointer is not left at the edge. (A first pass drew the `yubi` hand; retail PC does not show it over the game.)
- Not yet compared with retail: whether retail activates on press or on release, whether right-click cancels anywhere or only over a window, hover over a parent window (ignored here), the retail "Mouse Control Type 1/2" setting (Mouse/Cam. page; stored, not applied), and the pointer while the camera turns. Verified by `StockUiMenuControllerTests` (`Mouse_*`) and offscreen on D3D11 (`RendersOpenMainMenuWithCursor` draws the hover pointer).

## Config pages and settings (chunk 4c)

- **Chunk 4c: Config pages and settings (2026-09-26, tested in-game).** Every page the `configwi` list opens is navigable and live: Gameplay (`conf2win`), Chat Filters (`cfilter`), Windows -> Shared (`conf5win`) / Window 1 (`conf5w1`) / Window 2 (`conf5w2`), Misc. (`conf3win`), Misc. 2 (`conf6win`), Misc. 3 (`conf12wi`), Misc. 4 (`conf13wi`), Mouse/Cam. (`conf7`) and Global (`conf4`). The DAT gives the buttons no meaning, so each page's label sprites were composited and read first (`GORDIAN_UI_DUMP_MENUS`, see the working notes) and `StockUiConfigPages` (Core `Ui/`) describes every row: option rows (one button per value; the value in effect gets retail's red bar, confirm selects) and slider rows (the 192 x 16 button is an invisible hit region over a bar authored in the frame art; left/right move the value by its step, and the client fills the bar with rows 1-6 of the `gauge` strip drawn opaque and tinted light blue, 12 px tall inside the 16-px bar, as a retail capture shows (`framesus` #103 is the same strip tinted (64, 96, 127); the capture reads a little more lavender, tint (0x68, 0x60, 0x84)); `conf5w1`/`conf5w2` bake an orange sample fill (gauge texels 48,16) into their first bar, which is skipped when drawing). Values live in `StockUiSettings` (one integer per `StockUiSettingKey`, retail defaults where known), saved per character in `ui_settings/<name>.json` by `StockUiSettingsStore`; Window Type and Party Icon Display stay on `StockUiLayout` (routed through the controller's delegates). Consumers wired so far: Window 1 "Maximum lines displayed" picks the log frame `log1`..`log8` (22 px + 16 per line, `logwindo` = `log8`), Misc. 3 "Party Icon Display" = `/uilayout buffs`, Mouse/Cam. third-person axes set the session input profile's mouse inversion (only once chosen), Window Type as before. The rest (volumes, gamma, shadows, weather, clipping plane, footsteps, timestamps, multi-window Vertical/Horizontal/OFF, key assignment, macro palette, term filter, auto-disconnect...) are stored and shown, to be read by their subsystems as they appear. Server-side settings go through the new `ConfigPacketModule`, opcodes confirmed against LandSandBoat's `packets/c2s/0x0dc_config.h` / `0x0db_config_language.h` / `s2c/0x0b4_config.h` and XiPackets: S2C 0x0B4 (SAVE_CONF flag word, two chat-filter words, PvP flag, area code, party languages) is kept in `PlayerConfigState`; C2S 0x0DC sets or clears one flag (Gameplay "Auto-target" = `AutoTargetOff`, Misc. "Character Information: Hide" = `Anonymity`); C2S 0x0DB kind 0 carries both chat-filter words and must echo the server's flag word (LSB copies the whole word, so a zero would clear /invite, /away, /anon and auto-target); kind 1 carries the party-search languages. The Chat Filters list is retail's one continuous list of 55 entries (all four screens captured, 2026-09-26) scrolled through the DAT's 14 invisible `hfr1` row buttons: the last row links down to 26 and the first up to 16, which scrolls the list by one entry with the cursor held on the edge row, wrapping at the ends; the rows slide smoothly (`ScrollFrom` -> `FirstRow` over 0.12 s, clipped with the renderer's new per-batch scissor) and a 6 px scrollbar straddles the window's right edge below the title band (translucent gauge strip track, pale pink-white thumb sized and placed by the visible and first-entry shares, as the captures show). Each row draws a state ball at its origin (`framesus` #88 "ON" = filtered, #89 "OFF"; #83 is a green "Hold" state one capture shows on Party, meaning and wire mapping not decoded, and Tell's OFF carried a music-note icon, likely the tell sound, not drawn) and the text 34 px in; confirm toggles ON/OFF. Tell, Party, Linkshell, Linkshell 2 and Unity have no server bit (LSB's words carry none), so they toggle a client-only mask (`StockUiSettingKey.ClientChatFilters`, persisted) for the chat window to apply; the three "System Lv." rows stack on the flag word's 2-bit SysMesFilterLevel (Lv. N on = level N, off = N - 1), sent as a kind-0 0x0DB with the level replaced in the echoed word. Verified offscreen on D3D11 (`RendersConfigPagesWithSlidersAndFilterRows`) and by controller/packet tests.
  - Still open: Font Colors (`conftxtc` -> `textcol1` rows + `textcol3` RGB sliders), Log (`conf11l` -> `conf11s` rows -> `conf11m` Window 1/2/Default) and Effects (`fxfilter` rows) are list pages not built yet (their row text is in the config row table, see [Menu string tables](#menu-string-tables-19)); Gamepad opens the key-assignment editor (`keypad`/`k1assign`). Retail defaults not yet confirmed against a capture: Multi-window (default OFF), DamageDisplay (Both), volumes, gamma. the Chat Filters "Hold" state and the tell-sound note. Menu-window opacity: retail's config pages are opaque below the title band (in-game comparison 2026-09-26: nothing shows through the body, only the band lets the HUD through) although the DAT authors the same 0x40 -> 0x7F alpha gradient as the translucent HUD windows; `StockUiMenuWindow` therefore has `DrawMenu` redraw the body below 20 px opaque with the authored colour gradient (`opaqueBody`), and the mechanism retail uses is undecoded (the top and bottom body colours, (19, 13, 39) -> (37, 36, 89), read a little darker than the texel x 0.5 -> 1.0). "Chat Language Filter" (Global) is stored client-side only; whether it maps to SAVE_CONF's 2-bit Language field is unconfirmed.

## Chat and log windows (chunk 5)

- **Chunk 5: Chat/log window (2026-09-27, tested in-game; calibrated against retail captures).** `StockUiChat` (Core `Ui/`, one per session as `CharacterSession.Chat`) fills the log from S2C chat (0x017), system messages, linkshell messages, party invites, combat lines (`CombatLogFormatter`) and menu notices, and sends what is typed through `PlayerActionService.ExecuteCommandAsync` (the console's dispatcher), the chat mode's channel being the default for plain text. The server does not echo your own chat, so the client logs it. Line formats (retail): `Name : text` (say, shout, yell, assist), `Name>> text` (tell in), `>>Name : text` (tell out), `(Name) text` (party), `<Name> text` (linkshell), `[2]<Name> text` (linkshell 2), `{Name} text` (Unity); emotes and system text as sent. The config menu's client-only chat filters (Tell, Party, Linkshell, Linkshell 2, Unity) drop those channels here.
  - *Retail reference:* a 1:1 retail capture (2026-09-27, 2560 x 1440, Bibiki Bay, two log windows side by side, input line open) gives the layout below. Measured values: a 94-character line spans 752 px (8-px cells), rows 16 px apart; both windows' top border at the same y and bottom border 147 px below it; the input line's borders 19 px apart at the bottom of Window 1; titles end 45 px from the window's right edge.
  - *Log font (`StockUiLogFont`, App):* the `moji` texture (1024 x 2048, "font    moji" in the English menu DAT ROM/119/51, also ROM/0/1, ROM/91/15, ROM/118/111, ROM/176/75, ROM/178/14; found by scanning every ROM folder for font-named textures): 16 x 16 cells, 64 to a row, printable ASCII at cell `code - 0x20`, then kana, Greek, Cyrillic, Latin-1 and symbols (the rest of the character set is there for later). Alpha is a 1-bit mask; the colour channels carry the glyph's shading and dark edge. Spacing is proportional: each cell is drawn at the pen and the pen moves to 2 px past the glyph's rightmost ink; a space is 7 px, and every digit takes the widest digit's advance so timestamps line up (retail spaces "1234567890" evenly) (fitted to a retail capture of every keyboard character, 2026-09-27: "Tarudrake" 77 px, within about a pixel per glyph). Retail draws a dark outline round the text; the client copies the ASCII cells into its own atlas with a 1-px dark dilation (~80%) under each glyph, so a channel tint keeps the outline dark, drawn through `StockUiRenderer.DrawTextureRegion`. (A first pass used MS Gothic from the system, which drew `\` as a yen sign.)

## Movable stock UI (chunk 4b)

- **Chunk 4b: Movable stock UI (opt-in, 2026-09-27).** `/uilayout unlock` (and `lock`) sets `StockUiLayout.Unlocked`, saved with the layout so a player who opted in stays unlocked across launches (legacy parity by default: retail cannot drag its stock windows, and a fresh layout is locked); `StockUiDragController` (Core `Ui/`, `PlayerActionService.UiDrag`) reads the flag from the layout the HUD hands it each frame. While unlocked a hint line and a "Default positions" button sit at the top of the screen; the button (a registered region with the `button:` prefix, clicked rather than dragged) calls `StockUiLayout.ResetPositions`, which drops every window's position and anchor override and keeps scales, hidden flags, skin and options (`/uilayout reset positions` does the same; plain `/uilayout reset` still restores everything and locks). The HUD registers each persistent window's screen rectangle as it draws it (`log` = Window 1 and Window 2 with their title bands, `chat`, `party`, `alliance1`/`alliance2`, `target`, `status`, `menu` = the root menu only) and `StockUiDragOverlay` (App) outlines them (translucent white; pale yellow under the pointer, orange while dragged) with the window id in `fontshp`; windows with nothing to show (no target, no status effects, no alliance, closed menu or input line) are drawn as empty frames with a faint blue fill and labelled "(empty)" so they can still be placed. A left press over a window starts a drag (the press is not game input; right-click camera look still works), the window follows the pointer clamped to the screen, and only the release writes the layout, through `StockUiLayout.MoveTo` (re-anchored to the nearest screen corner, saved to the character's layout file); while dragged the HUD substitutes the transient position and treats the window as moved (the target window leaves the party window, the input line leaves Window 1). The log windows keep the retail arrangement's width wherever they are: Window 1 stretches from its authored left edge to 2 px short of the party window's retail place (or 16 px from the screen's right edge when the party window is hidden), the Window Width sliders then take their share, and a moved log or input line is clamped to stay on screen at that width (in-game 2026-09-27: a dragged log first shrank to its authored 366 px). Esc locks the UI (once no menu is open for it to cancel). Runtime-placed windows (sub-menus, prompts) are never registered: they follow their parent. The status icon region is the icon slots in use (the "buff" frame is only a strip), all slots when empty. The chat input line is now separately placeable: with a `chat` override it takes that placement at its authored width and Window 1 shows all its rows; otherwise it stays over the bottom of Window 1 as retail. Mouse positions reach the controller by two routes, both wired in `ViewportWindow`: on Windows the subclassed native child window's raw Win32 messages (rendering-surface pixels; a button message carries no position, so the move that precedes it is kept), elsewhere Avalonia's window-level pointer events (the position over the viewport control times the render scaling). The child is a `static` class HWND, which reports itself transparent to mouse hit-testing, so until 2026-09-27 every mouse message over the viewport fell through to Avalonia's native-host holder window and was swallowed: no click, hover or right-drag camera look ever arrived by either route (confirmed in-game: no press line in the log). `Win32ChildWindowHelper` now answers `WM_NCHITTEST` with `HTCLIENT` and captures the mouse while a button is held, so the raw route is the one in use. Every left press while unlocked writes an Info line to the log (`Stock UI unlocked press (avalonia|raw) at (x, y) hit <id>; N regions; viewport w x h at scale s`) so a drag that does not start can be traced. Hidden windows are not shown while unlocked (`/uilayout <window> show` first). Verified offscreen on D3D11 (`RendersUnlockedOverlayOutlinesAndPlaceholders`) and by `StockUiDragControllerTests` / `UiLayoutCommandTests`.

## Dialog text (chunk 6)

- **Chunk 6: Dialog text (2026-09-28, awaiting the in-game test).** NPC talk, event choice menus and zone messages. Retail compiles every NPC's scripts into a per-zone event DAT and runs them in a byte-code VM; the text they print lives in a per-zone dialog table. Both are now decoded and a talk subset of the VM runs them (formats and opcode notes from XiEvents, clean-room C# in `Gordian.Core.Events` and `Resources/Events`, `Resources/Tables`).
  - *Zone files (`ZoneDialogTable.GetFileId`, `ZoneEventScript.GetFileId`):* zone z's English dialog table is file id 6420 + z (Japanese 6120 + z), its event scripts 5820 + z; zones 256-299 continue at 85591 / 85291 / 84991 + (z - 256) (the zone entity list, 6720 + z, continues at 86491 + (z - 256)). Every ROM path in XiEvents' zone list resolves to those ids in the retail file table (2026-09-28); zone 256 (Western Adoulin) is ROM9/5/53 (events), ROM9/5/101 (dialog), ROM9/5/77 (Japanese dialog), ROM9/6/45 (entities). The earlier 256-299 formulas were 256 ids low (#71). Southern San d'Oria: ROM/25/39 (16,941 messages) and ROM/21/39 (502 blocks, 4,819 events).
  - *Dialog table (`ZoneDialogTable`):* first dword `0x10000000 | (size - 4)` in the clear, everything after XOR 0x80; a dword offset table (count = first offset / 4, offsets from byte 4) then control-coded strings. Message ids are LandSandBoat's `IDs.lua` text ids (24 = "Home point set!", 6439 = "Obtained: <item>.", 7239 = "You accept the mission." in that zone).
  - *Message codes (`EventMessageDecoder`):* 0x07 line break, 0x0B starts the choice list, 0x0A n number parameter n, 0x0C n `[a/b/c]` picks by parameter n, 0x08/0x09 player/NPC name, 0x19 n / 0x7F 0x93 another entity, 0x1F c colour, 0x01 len type ... a named thing (type '#' item, '3' key item, '8' zone; sub-blocks of (length ^ 0x80) value bytes ^ 0x80 and a closing byte; the first value is the index of the parameter holding the id), 0x7F 0x31 0x00 the prompt (the event waits for Confirm), other 0x7F codes two bytes (0x34-36/80/84/86/8C/92 three, 0x38 four, per the retail query handler), 0xEF n icon, 0xFD...0xFD auto-translate, the rest Shift-JIS. Sub-block values are read from the number parameters (a packet's num[], an event's zone work values from slot 2); which array an event's text really reads is unconfirmed.
  - *Event scripts (`ZoneEventScript`):* block count and sizes, then per actor (server id; 0x7FFFFFF0 = the player's block, 0x7FFFFFFF = zone events): event count, ushort offsets, ushort event ids (0xFFFE answers any id), immediate data dwords, byte code. `EventOpcodeTable` holds every opcode's length (sub-case byte for the variable ones). *Corpus walk (2026-09-28, #73, `EventOpcodeCorpusTests`):* each event entry of every retail zone with an event DAT (296 zones, 209,144 entries) is stepped from its start by the table and must land exactly on the next offset (or the end of the block's code); 99.29% do (98.27% before #73; xi-tools' `docs/events/typed_opcodes.md` lengths reach 99.30%). The misses hold inline data (strings after `1F 17`, sub-case 0x80 records). Corrections from that walk, checked against XiEvents' pseudo code where it has the opcode: 0x5F subs 2-7 = 6/16/16/18/18/14, 0x7E (CodeCHOCOBO) subs 0/1/2/4/5/8 = 6, 3 = 16, 6 = 18, 7 = 8, 0xB4 sub 0x14 = 12 / 0x15 = 2, 0xB6 subs 0x14/0x15 = 6, 0xC4 = 12, 0x75 sub 2 = 2, 0x60 subs 0/1 = 4, 2 = 6, else 2, 0xBF subs 0x20/0x40 = 10, 0x72 subs 0/1 = 4/6, 0xA6 subs 1/2 = 2/4, 0x9D subs 7/8/0x0C/0x0D/0x0F/0x10 = 6/23/8/10/10/10, 0xD4 subs 0/2 = 8.
  - *VM (`EventVm`, host `IEventVmHost`):* runs one entity's part of an event (see *Entities and request stacks* below): control flow (0x00/0x01/0x02/0x1A/0x1B), work arithmetic and bit fields (0x03-0x15, 0x19, 0x3C-0x41, 0x57), messages (0x1D entity, 0x2B named actor, 0x48/0x49 no speaker, 0xB0), waits (0x1C, 0x6F, 0x58), the prompt wait 0x23, queries (0x24 with 0x25/0x7F; 0xD4 sub-cases 0/2 are the same query with the zone map behind it, not drawn yet), the 0x43 update handshake and the 0x47 position update (0x05C mode 1, a same-zone warp), the scripts' tables (0x9D: runs of 16-bit work references inside the byte code, read/written by index, shared through 64 zone-wide pointer slots, or jumped through), event position (0x36/0x37), control lock 0x20, entity test 0x44, facts 0x83/0x9C/0xBE and the ends 0x21/0x26; everything else (camera, motion, schedulers, look-at, strings) is stepped over by length, so cutscenes play as their text. Operands: bit 15 = immediate data, 0-79 locals, 4096+ the zone's shared work values (`EventWorkZone`: the server's 0x034 parameters land in slots 2-9, a choice in slot 0 (0-based; 254 cancelled), slot 1 is the 0x05B EndPara), 5888+ the 1700 block, 0x7F00+ entity facts. Message parameter n is slot 2 + n, then the 1700 block from n = 8 (`GetMessageParameter`: the home point script writes its lists there and names parameter 33 for the zone). Waits count 60 Hz frames: every opcode of a tick sees the same frame delay (the 60 Hz frames since the last tick), which 0x1C/0x6F subtract and 0x57 adds to its work value (XiEvents' `GetFrameDelay`); 0x6F starts a 16-frame sleep only when no wait is running. A tick runs up to two million opcodes (the home point script walks its tables in long loops). An event runs until an end opcode (0x00, 0x21, 0x1B with an empty stack, 0x26) or the end of its block's code, not to the next event's offset: actor blocks share code, and 18,948 jumps and calls in the retail corpus land past their event's next offset (e.g. Northern San d'Oria actor 0x010E7017, event 4865, is one call to offset 176 in a range ending at 156; #72). 0x72 (CodeGETWEATER) is stepped over: retail's sub 1 writes the weather forecast from file 7033/7037 into zone work values 2-4, which is not decoded yet.

  - *Entities and request stacks (`EventScene`, [#85](https://github.com/jimmy58663/GordianXI/issues/85)):* an event is played by several entities at once, as in retail (XiEvents "Event VM Functions.md": InitEvent2, XiEventInit, EventIdle; "Event VM Structures.md": `reqstack_t`). ## Name plates ([#28](https://github.com/jimmy58663/GordianXI/issues/28))

- **Done 2026-09-29, tested in-game over three rounds the same day (size, pearl colour, the pearl vanishing while running, glyph box edges, then depth-tested occlusion).** Every entity the entity pass draws records its overhead point (`EntityRenderer.OverheadAnchors`: skeleton reference 2, as for the target cursor below, or the top of the bounds for an unskinned model); the viewport projects them (`NamePlateAnchor`: screen point, view depth, pixels per yalm = projection M22 x height / 2 / depth) and `StockUiNamePlates` draws them first in the stock UI pass, far to near. Each plate is a flat card at its entity's depth, tested against the scene's depth buffer (test on, write off; `StockUiRenderer.Depth`, the vertex carries clip z / w): walls and models in front cut it pixel by pixel, as retail does (a wall edge crossing the A.M.A.N. Liaison's name in a retail capture, 2026-09-29). The depth is taken 0.5 yalms toward the camera from the overhead point so the entity's own head does not cut its name. A first version hid whole plates by a camera-to-head raycast against the collision mesh; retail clips per pixel, so it was replaced. Other UI and the target cursor are drawn with the depth test off.
  - *Font and size:* the ordinary `fontshp` glyphs (their own outline; bilinear), centred on the overhead point, sized in the world: targeting does not change a plate's size, distance does (Windower captures, 2026-09-29). One font pixel is 0.0128 yalms (the local player's 24 px cap height at 2560 x 1440 against the ~9 px source glyph, assuming the default 6-yalm camera at 60 degrees) made 10% larger by the maintainer's choice after the first in-game test (`YalmsPerFontPixel`), clamped to 1-4 screen pixels per font pixel (provisional) and skipped nearer than 1 yalm (first person). Opt-in: `/uilayout names <n|default>` multiplies the size (0.5-3, `StockUiLayout.NamePlateScale`, saved with the layout). Glyphs and icons are drawn with half a texel trimmed from each edge (`StockUiRenderer.TexelInset`, the quad trimmed by the same share), because bilinear scaling otherwise samples the neighbouring atlas cells and draws faint box edges around them (in-game 2026-09-29; retail shows a few such lines too). The letter spacing is the font's own advance; the captures suggest a wider gap (about 15-17 px between neighbouring fills at the 24 px size), still to be measured.
  - *Colours (`NamePlateStyle.Color`, the `ncol` group's image corner colours):* #0 white player (the local player too, even in a party), #1 pale cyan own party members other than you, trusts included (alliance members stay white), #2 lavender seeking party, #3 dark blue anonymous, #4 pale green NPC, #5 pale yellow unclaimed monster, #6 red claimed by you / your party or alliance (probable), #7 purple claimed by others (probable), #8 orange called for help (XiPackets: YellFlag turns the name orange; the index is probable).
  - *Icon (`NamePlateStyle.Icon`, one, drawn left of the name 2 font px away at the glyph size):* `fontshp` 110-145 draw 32 x 32 cells of `ustatsHD` at 16 x 16: 110 PlayOnline, 111 link dead, 112 away, 113 seeking party, 114 linkshell pearl (tinted with the linkshell colour: the 0x00D / 0x037 r, g, b bytes used as they are as a half-scale UI colour, so 0xFF about doubles the mid-grey art; halving them came out at less than half retail's brightness, sampled 2.1-2.6x darker in the first in-game test; LandSandBoat sends each 4-bit channel as (c << 4) + 15), 115 trial, 118 GM, 124 bazaar, 125 auto party, 129 new player "?", 130 mentor "M", 140 seeking a master party, 145 the A.M.A.N. Liaison's "i". XiPackets says only that the pearl gives way to every other icon; the order used among the rest is provisional (GM, link dead, PlayOnline, away, seeking, bazaar, new player, mentor, trial, info, linkshell). GM level 4-7 shows the GM icon unless the GM hides it, 3 the PlayOnline icon, 1-2 the trial arrow.
