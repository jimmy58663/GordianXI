# Retail Login (Direct, POL-Bypassing)

> How GordianXI logs in to Square Enix's retail servers without `pol.exe`. It is written from the derived spec alone ([retail-login-spec.md](retail-login-spec.md) v2.1.25, clean-room policy in [retail-login-research.md](retail-login-research.md)). Status: the stages run in order (`RetailLoginClient`), the retail lobby sits behind the character select screen and the map session starts with the retail key. Everything is unit-tested against the spec's vectors and loopback fakes. Live (2026-11-11): both version checks and the PlayOnline (Core) login succeed; the Square Enix login and the PML pages succeed with the v2.1.21 password key; the lobby accepted `0x26` once the FFXI key request followed spec v2.1.23 section 4.3.5, and character select works. The first map login (2026-11-11) got an answer to its `0x00A`, but the server kept resending its first datagram and sent `0x00B` Logout after 1.4 s; a second, whose map key had a zero byte, got no answer at all. Spec v2.1.24 explains both: the `0x00A` ticket hashes the key cut at its first zero byte (as the cipher does), and retail answers the server's first datagram with `0x011` alone, sends `0x00C` in a later datagram, and copies the server's header `State` bytes. All three are built (`RetailMapProtocol`). The next run got the server's first datagram but nothing more: our `0x011` went out with Ack 0 (the ack was written only after the datagram's handlers ran) and we sent `0x015` every 250 ms while loading, which retail does not. The ack is now set before a first datagram is parsed, and retail sends no `0x015` before `0x008`. The run after that (2026-11-11 21:48) sent the `0x011` exactly as retail does and still got no answer; the only header fields left that differed were `+0x04` and `State` word 2, which spec v2.1.25 identifies as the send time's milliseconds and our public IPv4 address (both now written). With them the map login works (2026-11-12): the character is in the world and plays. Crossing a zone line does not: the server answered our `0x05E` (`z372` in zone 115, laid out as XiPackets gives it) with two small datagrams and then `0x00B` state 1 (Logout, no address) 1.3 s later, instead of state 2 with the next map server. Not yet explained. The datagram framing (leading `0x01`, bit count, MD5 over both) already matched retail (test vector 19). The map session logs its first 20 datagrams each way (headers, and sub-packets both ways), and again from each zone-line request.

## Pieces (`src/Gordian.Core/Network/Retail`)

| 1, 7. POLP version checks (`pt008.pol.com:54000` Viewer, `pc001W2U.pol.com:53001` FFXI) | `PolpPackets`, `PolpVersionChecker`, `PatchConfigFile` | Built. Type 7 request and Type 8 response. The header checksum is the first 4 bytes of MD5 over the frame from the `POLP` magic to its end (spec v2.1.20; the CRC-32 of earlier spec versions made both servers close without replying). The request matches capture #8's byte for byte. The version string is the product id (`1000` Viewer, `0001` FFXI) and the highest version tag in that product's `patch.cfg`; `patch.ver` is encrypted and not read. An outdated install still gets status 1: the reply's current version differs from the installed one, which stops the login with "update it in PlayOnline Viewer". Both checks run in retail's order: the Viewer's first, FFXI's after the PML pages. |
| 2, 3. Core IRC: gatekeeper `ci000.pol.com:51240`, session host `:51241`-`:51247` | `PolCoreProtocol`, `PolCoreSession`, `PolCoreToken`, `PolRsaKeyExchange`, `PolIdEncoding`, `PolClientMeta` | Built. The gatekeeper's and the session host's 44-character tokens share one 25-byte layout (server time, client address, redirect host and port, client port). The redirect can name any port, 51240 included. Ephemeral RSA (e = 65535) with a 255-bit modulus, as in every captured key pair (128-bit primes with top byte 0x80-0x8F): `USER` carries the modulus N little-endian as a 43-character body followed by the 4-character line checksum, the server returns C big-endian (its line has the same body and checksum), and K8 is the last 8 bytes of the PKCS#1 v1.5 block reversed. Encrypted `NICK` (86 bytes, no tabs): the encoded POL ID, the password response MD5(greeting token body + POL password), the client metadata body computed from the POL ID, and its checksum suffix. Every token line ends in that line checksum (`PolHashes.LineSuffix`, spec section 5.10): the little-endian 32-bit word sum of the line from its first byte, a 1-3-byte tail counted with the zero bytes in front, bits 31..8 as four 6-bit slices plus 0x3F. The session builds it for `USER` and `NICK` and logs a warning when a server line's suffix does not match. The routing token (the client's port and address) comes from the greeting; the `001` payload carries nothing the client uses. The connection stays open and the session answers the server's `PING`s. |
| 4. Square Enix account (`pp000.pol.com:51220`, `0x04/0x07`) | `PolPresencePackets`, `PolPresenceClient.AuthenticateAsync` | Built. Password or password + one-time code; the reply's header names the assigned `:51220` server (last octet first), and the 8 payload bytes it announces never come. The password is never sent: the payload carries SHA-1(lowercase hex of the password key + the server minute), where the password key is SHA-1(lowercase hex SHA-1(password) + `playonline`) (spec v2.1.21 section 5.4, test vectors 3 and 17). Without the `playonline` step (spec before v2.1.21) the server refused a valid account with status `0x6F`. Status `0x6F` covers at least a wrong ID and a wrong password digest; any non-zero status is reported as the ID, password or one-time code being rejected. Every request header carries 12 zero bytes and MD5(POL ID + POL password + LE32(challenge seed)). |
| 5, 6, 10. Session keys (assigned `:51220`, `0x04/0x05`) | `PolPresenceClient.RequestSessionKeyAsync` | Built (spec v2.1.23 section 4.3.5, test vector 18). `Viewer` sends `00 00 00 00 E8 03 05 00 00 01` at `+0x10` with a zero `+0x20` word (not the PML key; retail asks for it, its use is unknown). `Lobby` sends `00 00 00 01 01 00 05 00 00 01` with the `+0x20` word set to the session keystream at that position (`KeystreamWordFor`), so it is zero on the wire. Up to v2.1.22 the spec gave a layout that asked for the Viewer's kind of key, and the lobby refused the AuthCode with 3301. The section 4.3.7 requests and the third key are not sent. The hello sends zeros after the routing token. |
| 7. PML pages (`wh000.pol.com:51304`) | `PolPmlClient`, `PolHashes.PmlUserName`, `PmlDigestResponse` | Built. The spec's two requests on one keep-alive connection: `/pml/main/index.pml` (unauthenticated with the spec's `If-Modified-Since` date, then again answering the 401 digest challenge) and `/pml/game/ff11/index.pml?SC=0&PF=WIN` with the same nonce. Headers in retail's order; `X-POL-VIEWER-VERSION` is `Ver.` + the Viewer's `version.dat`; `X-PlayOnline-Want-Hello` is POL Base64 of LE32(t) twice. Digest: userName is the client's `a.b.c.d:port` (from the routing token) in POL Base64, the password is POL Base64 of K8, and the response is MD5(HA1:HA2:nonce). The bodies are not rendered; `$playbutton_enable` = 0 on the FFXI page stops the login with its `$status` (maintenance). The `<define>` syntax is not in the spec, so the flags are read leniently. |
| 8, 9, 11-13. Lobby `ffxi00.pol.com:54001` | `LobbySession` + `PolLobbyHandoff`, `LobbyClientPackets`, `LobbyKeyModifier`, `PolAuthCode`, `ClientFileChecksum` | Built ([packets.md](packets.md#retail-lobby-ffxi00polcom54001)). The lobby is the one LandSandBoat uses (`LobbySession`, [session-and-packets.md](session-and-packets.md#lobby-session-35)): the legacy client talks to both the same way, and only the part pol.exe or xiloader plays differs. `PolLobbyHandoff` is pol.exe's: the lobby key from `:51220` once the connection is open, the AuthCode, the packet MD5 left in the header, no data channel, and the map key. The session runs `0x26` -> `0x05`, `0x1F` -> `0x20`, `0x24` -> `0x23`, then name check, creation, deletion, rename and `0x07` -> `0x0B` on demand. `0x26` carries the AuthCode token (MD5 of the lobby key, the greeting's server time and K8, encrypted with a fixed-key block cipher). `0x07`'s selection digest includes `ClientFileChecksum` of the install's FFXiMain.dll. A refusal (`0x04`) keeps the connection, so the screen shows the message (3307: the character is still logged in) and the player can retry; the retry takes the next modifier. |
| Map server | `RetailMapPackets.MapKey` / `MapRawKey` / `BuildFirstDatagram`, `SessionNetworkManager.LoginDatagramBuilder` | The map key is SessionHash(the `0x07` modifier + 4); the ticket's `BlowfishKey` is `MapRawKey`, the 20-byte key `LegacyBlowfishCryptoSuite` MD5s, so LandSandBoat's map session runs unchanged. The first datagram (136 bytes, unencrypted) carries `Ticket` = MD5(15 zero bytes + map key cut at its first zero byte, spec v2.1.24), built by the ticket's `LoginDatagramBuilder` in place of LandSandBoat's. A zone change adds 2 to the key's counter (`AdvanceZoneKey`), and the next first datagram's ticket uses the moved key (not verified: the spec does not show a post-zone `0x00A`). The search server is the one `0x0B` names. `RetailMapProtocol` (set from the ticket) answers the first `0x00A` with `0x011` only and sends `0x00C` 1 s later (`LifecyclePacketModule.RetailGameOkDelay`; retail waits about 2 s, for zone loading), and puts the server's last header `State` bytes (`+0x0C..+0x1B`) in ours with word 0's low byte 0x01 and word 2 (`+0x14`) set to our public IPv4 address in network byte order (the routing token's address bytes reversed, `RetailMapPackets.ClientAddressFromRoutingToken`); header `+0x04` is the send time's milliseconds and `+0x08` its seconds (`RetailMapPackets.WriteHeader`, spec v2.1.25 section 4.6.3). |
| All stages | `RetailLoginClient`, `RetailAccountSession` | Built. `LoginAsync` reads the install's `patch.cfg` version and FFXiMain.dll checksum, and the Viewer install's `patch.cfg` and `version.dat` (from the registry's `1000` value, else `PlayOnlineViewer` beside the FFXI folder; a login without a Viewer install stops), then runs every stage in retail's order so the traffic matches a retail login: the Viewer version check, the Core session, the Square Enix login, the Viewer's service-1 key request, the PML pages and the FFXI version check. An outdated install stops with "update it in PlayOnline Viewer"; a version reply that cannot be read, a failed service-1 key and failed PML pages only warn, and the raw version reply is logged. A connection that closes or times out names its stage (version check, PlayOnline login, Square Enix login, FFXI lobby). A Core session timeout also names the step it was waiting at and the types of the lines that came back after `NICK` (numerics and commands only, never their contents), so a silent rejection of `NICK` shows as "waiting for the welcome after NICK". `RetailAccountSession` keeps the Core session (and its `PING` answers) open while the game runs; each `OpenLobbyAsync` fetches a fresh lobby key, so a Log Out returns to character select on the same session. |

Shared primitives:

- **`PolBase32`**: the permuted 5-bit alphabet `N43OVHBJ1Y2C0WSXED5QFILRZMUTAPGK`, MSB-first. It encodes the Core IRC tokens and the `001` payload.
- **`PolCoreBase64`**: polcore's 6-bit alphabet, MSB-first, for the RSA tokens, the `NICK` metadata and the PML digest.
- **`PolStreamCipher`**: Blowfish rounds in 64-bit OFB, with the session's own key setup. A 4096-byte buffer is grown from K8 by digests of all that came before: the first is MD5, the rest are MD5 from a zero starting state (`ZeroStateMd5`). P and S load from it (P at a 1-byte stride), P is XORed with its first words, and P and S are refilled by encrypting the zero block without chaining. The IV is the first 8 bytes of N. The CRLF rule applies to every frame. `Fork` gives the keepalive its own keystream state.
- **`PolHashes`**: the Core IRC line checksum, the `:51220` additive checksum, the POL password MD5, the Square Enix password key and its time-bound SHA-1, the challenge MD5, the lobby session hash and the PML digest.

The constants from pol.exe research (the three alphabets, the AuthCode key and its cipher's numbers, the POL ID token's numbers) come from the spec, under the maintainer's standing approval of 2026-11-08 to commit its pol.exe-derived constants (AGENTS.md prohibition 10). Capture values that identify the research accounts (their POL IDs, POL password hashes, and the `NICK` metadata bodies, which are derived from the POL ID) are redacted from the spec; GordianXI's code reproduced those capture vectors locally before they were removed.

## Launch (`MainWindowViewModel`)

A retail profile without the old bootloader path logs in directly (`LaunchRetailAsync`): the profile's POL ID (upper-cased), POL password, Square Enix ID and password, the 2FA code from its mode, and its game folder (or the registry install). `AccountProfile.GetLaunchProblem` names a missing POL ID, POL password or Square Enix login before anything is sent. Character select opens the retail lobby in the viewport; Auto-Login picks the profile's character by name or slot and selects it. The PlayOnline session ends when the player leaves character select, a lobby return fails, or the game session ends without going back to character select. Profiles that still have a bootloader path keep the old `ProxyStager` launch until this login is proven.
