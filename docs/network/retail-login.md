# Retail Login (Direct, POL-Bypassing)

> How GordianXI logs in to Square Enix's retail servers without `pol.exe`. It is written from the derived spec alone ([retail-login-spec.md](retail-login-spec.md), clean-room policy in [retail-login-research.md](retail-login-research.md)). Status: the protocol pieces are built and unit-tested. The full login is not wired up yet: the spec gaps below block it.

## Pieces (`src/Gordian.Core/Network/Retail`)

| Stage (spec section 2) | Class | Status |
|---|---|---|
| 1, 7. POLP version checks (`pt008.pol.com:54000` Viewer, `pc001W2U.pol.com:53001` FFXI) | `PolpPackets`, `PolpVersionChecker`, `PatchVersionFile` | Built. The Type 7 request, the Type 8 response with its CRC-32 checked, and the `patch.ver` version. Status 1 means up to date. |
| 2, 3. Core IRC: gatekeeper `ci000.pol.com:51240`, session host `:51241`-`:51244` | `PolCoreProtocol`, `PolCoreSession` | Built. Redirect token (server time, port), Diffie-Hellman `300 *` / `USER`, encrypted `NICK`, `001` ticket. The connection stays open for the life of the login. |
| 4. Square Enix account (`pp000.pol.com:51220`, `0x04/0x07`) | `PolPresencePackets`, `PolPresenceClient.AuthenticateAsync` | Built. Password or password + one-time code; the reply names the assigned `:51220` server and the hello echo bytes. |
| 5, 6, 10. Session keys (assigned `:51220`, `0x04/0x05`) | `PolPresenceClient.RequestSessionKeyAsync` | Built. Flags 1000 ask for the PML key and 1 for the lobby key. |
| 7. PML pages (`wh000.pol.com:51304`) | `PolHashes.PmlDigestResponse` | Digest only. The HTTP exchange waits for the digest username. |
| 8, 9, 11-13. Lobby `ffxi00.pol.com:54001` | `RetailLobbyPackets`, `RetailLobbyModifier` | Packets built ([packets.md](packets.md#retail-lobby-ffxi00polcom54001)); the connection and the character select hookup are not. |
| Map server | `RetailLobbyPackets.MapRawKey` | The 20-byte key for `LegacyBlowfishCryptoSuite` (it MD5s it). The rest of the map session is the same as LSB's. |

Shared primitives:

- **`PolBase32`**: the 5-bit alphabet `0-5A-Z`, MSB-first, plus the POL ID's Base36 → 9-character form.
- **`PolStreamCipher`**: standard Blowfish in 64-bit OFB with the MD5 key expansion, IV `52 7E 58 C7 D4 C3 9A 32` and the CRLF rule. Encrypting and decrypting are the same operation; `TransformFrame` is a `reset_iv = 1` frame and `Transform` continues one.
- **`PolDiffieHellman`**: 256-bit, g = 67. The key is the secret's last 8 bytes reversed.
- **`PolHashes`**: CRC-32, the `:51220` additive checksum, the POL password MD5, the time-bound Square Enix SHA-1, the challenge MD5, the lobby session hash and x-MD5-pol.

The DH parameters, the IV and the version strings came from pol.exe research. The maintainer approved committing them on 2026-11-08 (AGENTS.md prohibition 10).

## Verification

`tests/Gordian.Core.Tests/Network/Retail`:

- **Spec vectors:** all seven worked vectors of spec section 5.8 (POL ID, POL password, Square Enix digest, checksum, session hash, map key, PML digest). They were also recomputed independently with Python's `hashlib` before the code was written.
- **Blowfish:** Schneier's published vectors, including the 26-byte variable-key vector.
- **Stream cipher:** checked against the standard key schedule, plus the CRLF rule and continuation.
- **End to end against loopback fakes:** the Core session (gatekeeper, key exchange, `NICK`, `001`, a refusal numeric) and the presence exchanges (account login, redirect echo, lobby key).

None of this has been run against the live servers.

## Open questions (sent to the research side after v1.2.0)

1. **`NICK` client metadata.** Only described as generated by polcore.dll (`TTTTTAIST...`). `PolCoreSession.LoginAsync` takes it as a parameter, and nothing can call it for real until it is specified.
2. **`0x26` reserved block.** +0x38..+0x73 are unspecified and written as zeros. `0x07`'s selection digest repeats the whole block.
3. **`0x0B` layout.** The spec says 76 bytes with the map token at +0x40. XiPackets and LandSandBoat say 72 bytes with the search server's address at +0x40 and port at +0x44.
4. **First map packet.** What the C2S `0x00A` ticket (+0x40) and version (+0x50) hold on retail.
5. **Character management opcodes.** The spec's create `0x14`/`0x15` and delete `0x21`/`0x22` contradict LandSandBoat and XiPackets (delete `0x14`, name check `0x22`, create `0x21`, rename `0x28`).
6. **Lobby key ServiceType.** Section 4.3.5 says 1; the sequence diagram and section 8.2 say 0. `WriteKeyRequestPayload` writes 1.
7. **`0x04/0x05` ClientNonce.** Whether it is free, random or must count. The client starts at a random value and counts up.
8. **PML digest username.** Where the 16-character session username comes from.
9. **Viewer version check.** Where the POL root comes from, and whether the check can be skipped without the Viewer installed (Linux, macOS, a Horizon-only install).
10. **Base32 token lengths.** 41 characters for 24 bytes and 57 for 35 are longer than the bits need (39 and 56). The client decodes the bytes it needs and pads `USER` to 57 with zero characters. It needs a worked `USER` token to confirm.
11. **Keeping the Core session open.** Whether the IRC connection must stay open (and needs keepalives) while the character is in game.

Not yet asked: an OFB keystream vector (an 8-byte key and its first 16 bytes), which would check the key expansion against the research side's values instead of only against standard Blowfish.
