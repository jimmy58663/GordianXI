# Session Handoff & Packet Engine

> Bootloader handoff, direct LandSandBoat login, UDP framing, Blowfish, and the zero-allocation packet registry (Phases 2 and 3). The handoff/proxy rules themselves are in `AGENTS.md`. Status and open work: [ROADMAP.md](../../ROADMAP.md) and GitHub Issues.

## Bootloader handoff and direct login (Phase 2)

- Reverse-engineered `xiloader.exe` and `pol.exe` COM launch mechanisms

## Packet engine (Phase 3)

*Goal: 100% complete coverage of all known LandSandBoat server-to-client (S2C) and client-to-server (C2S) packet definitions with zero-allocation decoders.*

- Full Blowfish cipher suite integration (`LegacyBlowfishCryptoSuite` with MD5 key digest and ECB cipher)
- Incoming & outgoing UDP packet framing (`0x0A` chunking, sequence tracking, checksum verification)
- Session keepalive / ping-pong loop (4Hz `GP_CLI_POS` 0x015 heartbeat & idle timeout prevention)
- **Action requests leave at once (#132 round 2).** The player's action requests (`CombatPacketModule`: C2S 0x01A cast, weapon skill, job ability, attack, ranged, assist and the other 0x01A actions, plus the dig finish) are flushed as soon as they are queued (`SendActionsAtOnce`), with whatever else is queued, instead of waiting up to 250 ms for the next heartbeat tick. A cast logs `COMBAT Sending 0x01A cast: spell <id> on <target>` at Debug, so the time to the S2C 0x028 start (`COMBAT Action 0x028 ... MagicStart`) can be read off the session log. Measured on the maintainer's local LSB on 2026-10-12 while it ran a **Debug build**, the rest of the delay before a chant shows was the server's. Its datagrams arrived in clumps every 1.39-1.50 s (median per 10-minute window; 10th-90th percentile 1.23-1.61 s), and each clump holds one reply per client datagram sent since the last one: 6 at 4 Hz with one session, 12 with two. So the map server handled client datagrams in batches about every 1.4 s, against LandSandBoat's design tick of 400 ms (`map_constants.h` `kLogicUpdateInterval`; `map_engine.cpp` logs "Process main tick has taken ... ms" when it falls behind). A cast therefore waited 0.7 s on average and up to 1.5 s before the server even read it, and start and finish arrived together whenever the cast fit in one batch. Retail, as far as the references show, starts the chant only on the server's 0x028 start (cmd_no 8, cmd_arg `ca??`); no client-side start is documented in XiPackets or LandSandBoat. GordianXI does the same and does not predict the cast: a refused cast would otherwise chant for nothing. **With a Release build of LandSandBoat** (same machine, 20:20-21:05 the same day) the server answers every client datagram on its own: one datagram per arrival, median 0.25 s apart (10th-90th percentile 0.15-0.34 s), following our 4 Hz sends. Press to 0x028 cast start (from `Sending 0x01A cast` to `Action 0x028 ... MagicStart`) was a median of 1 ms, mean 83 ms, 250 ms at most, over 13 casts (5 more were refused and got no start). The 1.4 s batching was the Debug build; the cast delay is gone with the Release server. Remote movement under the Release server is #359.

## Auth handshake (xi_connect)

`LsbLoginClient` logs in over TLS with xiloader's JSON request (command 0x10, username, password, otp, trust token, `version`) and reads `result`, `account_id` and the 16-byte `session_hash` back. Since LSB `08ae16d27d` (the xi_profile service) the session hash is random and also the xi_profile credential (and, since `01e5b447e1`, the source of the map session key: [Map session key](#map-session-key)), and the server also stores a UDP port slot for xi_profile. GordianXI doesn't use xi_profile yet (#364).

**xiloader version negotiation.** LSB's `auth_session` rejects any `version` whose major.minor differs from `SupportedXiloaderVersion` in `src/login/auth_session.h` with a JSON `error_message`: 2.0 after `4d5ef0d385` (Oct 2025), 2.1 after `1d1c2320cc` (Feb 2026), **2.2** after `08ae16d27d` (Sep 2026, the xi_profile service). The message names the version the server wants: "Unsupported xiloader version a.b.c.\nThis server requires version X.Y.x." (since `f660a273e5`, Sep 2026) or "Your xiloader is too old.\nPlease update to version 'X.Y.x'. ..." (before it). `AuthenticateAsync` sends `LsbLoginClient.DefaultXiloaderVersion` (2.2.0) first; on a rejection it parses X.Y (`TryParseRequiredXiloaderVersion`), logs in once more as X.Y.0, and remembers the accepted version per auth server (`host:port`, for the life of the process, `XiloaderVersionFor`) so later logins send it first. Each attempt and the accepted version are logged at Info (`LSB_LOGIN`). Checked against a loopback TLS stand-in (`LsbSessionKeysTests.VersionFallback_*`).

## Lobby session (#35)

`LsbLobbySession` (`src/Gordian.Core/Network/LandSandBoat`) is the character select screen's connection: it opens the xi_data (54230) and xi_view (54001) channels after the xi_connect login and keeps them open until a character is chosen, running one request at a time. `LobbyPackets` builds the requests into caller buffers and parses the replies; `LsbLoginClient.OpenLobbyAsync` / `LoginToLobbyAsync` open one, and the old one-shot `SelectCharacterAsync` (the saved-profile fast path: a profile with a character name or slot) now runs over it unchanged in behaviour. Every packet in both directions still reaches the packet inspector.

Flows (XiPackets `lobby/Protocol.md`; LandSandBoat `src/login/view_session.cpp`, `data_session.cpp`):

| Operation | Wire |
|---|---|
| connect | data 0xFE (hash); view 0x26 → 0x05 (or 0x04, e.g. a version lock); data 0xA1 → data 0x03 and view 0x20 |
| refresh | view 0x1F → data 0x01; data 0xA1 → data 0x03 and view 0x20 (LSB's cached list, updated by its create and delete handlers) |
| worlds | view 0x24 → 0x23 (LSB: one world, 0x20, `main.SERVER_NAME`) |
| create | view 0x22 (name, world) → 0x03 / 0x04 313; view 0x21 → 0x03; refresh |
| delete | view 0x14 → 0x03 (0x04 332 when `login.CHARACTER_DELETION` is off); refresh |
| rename | view 0x28 → 0x03 / 0x04 313; then select under the new name |
| select | view 0x07 → data 0x02; data 0xA2 (base key) → view 0x0B (or 0x04 201 / 208 / 305 / 332); LSB then closes the view channel |

- **Framing.** View packets are read by their u32 size; data channel messages by their first byte (0x01 / 0x02 are 5 bytes, 0x03 is 0x148, an error written to the data socket starts with its size byte 0x24). Each reply has a 10 s timeout.
- **Lost requests.** LSB's view session can drop a request that arrives just as one of its writes completes (`handler_session::do_read` clears the read buffer the request was read into), which happened to the 0x1F after a deletion's OK. A refresh therefore resends 0x1F once when no 0x01 prompt comes within `PromptRetryWait` (1.5 s), waits `AfterDeletePause` (250 ms) after a deletion, and data reads skip a duplicate 0x01 ([character-lobby.md](../design/character-lobby.md#character-deletion-34)).
- **Dropped connections.** LSB closes the view socket instead of answering when 0x21 carries an out-of-range race, size, face or nation, when 0x07's id and name do not match, and when a delete or rename names another account's character. The session then reports `IsConnected = false` and the screen has to log in again.
- **Session key accounting (LSB-specific).** See [Map session key](#map-session-key) below: the key the map server decrypts with depends on the LSB version, so the ticket carries every candidate.
- **Not sent:** the `passwd` fields (an MD5 of PlayOnline's session password, which LSB does not read) and 0x07's `authcode_checksum`; the 0x26 `excode_client` claims every expansion.
## Map session key

The map server decrypts every datagram after the C2S `0x00A` with the 20-byte key LSB stores in `accounts_sessions.session_key` when it handles data `0xA2` (`data_session.cpp`); the map server MD5s it into the Blowfish key (`MapSession::initBlowfish`) and adds 2 to its fifth u32 word on each zone change (`incrementBlowfish`). How LSB builds that key depends on its version, and the client cannot ask which one it is talking to:

| Scheme (`LsbKeyStyle`) | LSB | Bytes 0-15 | Bytes 16-19 |
|---|---|---|---|
| `Counter` | since `393e176732` "Follow the client's lobby key counter instead of guessing it" (Oct 2026) | MD5 of the 16-byte auth `session_hash` (`accounts_profile.session_hash`) | lobby key counter + 3, u32 LE (the client's loader bytes if the counter is 0, with a warning) |
| `HashedLegacy` | `01e5b447e1` "Derive the map session key from the login session" .. `393e176732` (Sep-Oct 2026) | MD5 of the session hash | the loader's bytes, byte 16 raised as below |
| `Legacy` | before `01e5b447e1` | the loader's bytes (xiloader and GordianXI: 16 zeros) | the loader's bytes (`58 E0 5D AD`), byte 16 raised by 6 after a creation in this lobby session, 4 per deletion and per rename, 1 per selection refused with 201; a single-byte add with no carry, reset after zone-in |

**Differs from our earlier doc:** this section used to say LSB raises byte 16 of the 0xA2 key; that is only the `Legacy` / `HashedLegacy` schemes. Current LSB ignores the client's 0xA2 bytes 0-19 apart from the counter-less fallback.

**The lobby key counter** (`LobbyKeyCounter`, LSB `view_session.cpp` `stepsKeyOnRequest` / `stepsKeyOnReply` / `stepsKeyOnError` / `view_session::do_write`) is what the retail client steps and hashes into its key; LSB now follows it per view session:

- +1 when the client sends view request 0x07, 0x14, 0x1F, 0x21, 0x22, 0x24, 0x28 or 0x2B (the server steps when it reads the request; a request it loses is never read, so never counted).
- The 0x05 reply to 0x26 sets the counter to the u32 key at 0x1C of that reply + 1 (LSB sends `0xAD5DE04F`; GordianXI reads it from the reply).
- +1 for each view reply 0x03, 0x0B, 0x20 or 0x23 written through the view session's `do_write`; an error reply 0x04 steps only when the last request was 0x22, 0x24, 0x28 or 0x2B.
- Not counted: data channel messages (0x01, 0x02, the 0x03 id list; `data_session::do_write`), and the 0x0B select reply, which LSB writes straight to the socket and accounts for in the "+3" (one step for 0x0B, two at zone connect).
- 0x26 itself does not step.

`LsbLobbySession` steps it for every view request it sends and every view reply it reads, except 0x1F: LSB can lose a 0x1F (see Lost requests), so that step is counted when its 0x01 account prompt arrives on the data channel, a late duplicate prompt included. The counter is snapshotted when 0xA2 is sent, which is when LSB derives the key. GordianXI's direct select (0x26 → 0x05, data 0xA1 → view 0x20, 0x07) gives `0xAD5DE04F + 3` and a key word of **`0xAD5DE055`**, what the maintainer's connect server logged for it ("key counter AD5DE055", LSB `e27adcc46d`, 2026-10-12). The retail flow (0x1F and 0x24 before 0x07) lands on `0xAD5DE058`, the bytes xiloader always sent: the old fixed key was the retail counter of a plain login. **Beyond LandSandBoat:** that link between the fixed loader key and the counter is not stated in LSB.

**Negotiation.** `LsbLobbySession` hands the ticket all three keys (`KeyCandidates`, newest scheme first, duplicates removed; `BlowfishKey` stays the `Legacy` key) and logs each with the fingerprint LSB's connect server prints: "key value" is FNV-1a (32-bit) of key bytes 0-15, "key counter" is bytes 16-19 (`LsbSessionKeyCandidate.Describe`). The map session starts with `PacketParser.InitializeSessionCrypto(candidates)` (`LegacyBlowfishCryptoSuite.InitializeKeyCandidates`): outbound packets use the first candidate, the server's first datagram is tried with each candidate on a copy, and the one whose MD5 checksum verifies is locked in for the session (zone advances made before the lock carried over). The CRYPTO log line "Map session key negotiated: '<style>'" says which. Trying several keys has no side effect on the server, because the C2S `0x00A` is not encrypted: `MapNetworking::recv_parse` first checks the MD5 of the raw datagram and takes a valid one as a plain 0x00A (both before and after the key change), and only datagrams that fail that check go to `map_decipher_packet`. So nothing the server reads depends on the key until our first encrypted packet, which is sent after the lock. Sending one 0x00A per candidate key is therefore not needed. Sending the counter key itself in 0xA2 would make all three schemes store the same key, but only for a plain select: after a creation, deletion, rename or refusal the old schemes add their increments to byte 16 while the counter scheme overwrites bytes 16-19, so negotiation is needed anyway; 0xA2 keeps carrying the base key the old servers were verified with. Until the first datagram verifies, `SessionNetworkManager` also does not let an undecryptable datagram set the server sequence baseline: in the 2026-10-12 failure the first datagram (Seq 1) failed to decrypt and every retransmission of it was then dropped as a duplicate.

**Evidence and status.** LSB `src/login/data_session.cpp`, `view_session.cpp`, `src/map/map_networking.cpp` at `e27adcc46d`; the maintainer's 2026-10-12 18:26 logs (GordianXI: "Inbound datagram failed Blowfish decryption" for every map datagram; LSB connect server: "key value 96A7172F, key counter AD5DE055"; LSB map server: the plain 0x00A accepted and the character loaded into Davoi). Checked against `FakeLsbLobbyServer` in counter mode (plain select, create, refused name, delete with a lost or late refresh, rename, already logged in) and in legacy mode (`LsbSessionKeysTests`). **Unverified in-game.**

## XiPackets coverage audit (2026-09-28)

The per-opcode status (every XiPackets world packet, what GordianXI decodes or builds, and whether it is used) is in the [world packet registry](packets.md); this section keeps the audit's findings.

This audit compared every opcode in XiPackets `world/client/` and `world/server/` with the `S2C_0x*` decoder types and the header opcodes written by the `Build*` methods. Each opcode we handle was also checked field by field against its XiPackets README, with LandSandBoat `src/map/packets/{s2c,c2s}/` used as the tie-breaker because it is the server we target. The priorities come from the `Unhandled Packet ID` lines in `logs/gordian_system_20260928.log`.

**Coverage.** The counts, and which dropped packets arrive in an ordinary LSB session, are kept current in the [registry](packets.md#coverage-2026-10-01).

**Why a wrong size matters.** LSB's `ValidatedPacketHandler` (`packet_system.cpp`) silently drops a fixed-size C2S packet unless its header size equals `roundUp4(sizeof(struct))`. A C2S size that differs from XiPackets or LSB is therefore a dead packet, not a cosmetic difference. Only `0x01E`, `0x01F`, `0x02B`, `0x02C`, `0x0A0`, `0x0A1`, `0x0B5`, `0x0B6` and `0x0D3` are variable-length.

**Offsets.** XiPackets offsets count from the start of the packet. Our decoders receive the payload after the 4-byte header (`PacketParser`), so our offset = XiPackets offset − 4.

Fixed since the audit:
- [#97](https://github.com/jimmy58663/GordianXI/issues/97): linkshell C2S `0x0E1`/`0x0E2`/`0x0E4` are 144 bytes (`0x90`, XiPackets). `0x0E2` has two builders: `BuildSetLsMsg` sets byte +4 bit 6 (`0x40`, change the message) and `BuildSetLsWriteLevel` sets bit 5 (`0x20`, change the access level, level in bits 2-3 of +5). LSB ignores the packet unless one of them is set.

### S2C 0x063 misc data

`S2C_0x063_MiscData` (`ProgressionPackets.cs`) switches on the u16 `type` at packet +0x04 and is registered by `ProgressionPacketModule`. The payload starts at `type`; the per-type data starts at payload +4 (packet +0x08). Layouts from XiPackets `world/server/0x0063` and LandSandBoat `s2c/0x063_miscdata_*.h`.

| type | state | notes |
|---|---|---|
| `0x02` merits | `ProgressionState.LimitPoints`, `MeritPoints`, `MaxMeritPoints`, merit-mode flags | LSB layout: u16 limit points, u16 bitfield (7 merit points, 6 BLU bonus, 3 flags), u8 max merits |
| `0x05` job points | `ProgressionState.GetJobPointTotals(job)`, `JobPointsUnlocked` | flags byte, then 24 x (capacity, points, spent) u16 |
| `0x06` teleports | `ProgressionState.HasHomePoint` / `HasSurvivalGuide` / `HasWaypoint` / `HasTelepoint` / `HasAtmos` / `HasEschanPortal` | 16 mask words; home point, survival guide and waypoint are 4 words each |
| `0x07` Unity | `ProgressionState.UnityWeeks[0 previous, 1 current]` | one packet per kind: base (0x00, timestamp), members (0x01), points (0x02), personal ranking (0x14); the u32 arrays follow a u16 readiness flag at data +8 |
| `0x09` status icons | `LocalPlayerState.StatusIconIds` / `StatusIconTimestamps`, `GetStatusIconRemainingSeconds`, `GetStatusIconTimers` (the blinking status bar, #17) | 32 u16 icons (0xFF empty) then 32 u32 end timestamps; 0x7FFFFFFF = no timer |
| `0x03`, `0x04`, `0x0A` | not decoded | Monstrosity (post-MVP); 0x0A is unused by the client |

The status icon timestamp is meant to overflow a u32; `GetStatusIconRemainingSeconds` / `GetStatusIconTimers` subtract modulo 2^32. The unit is Earth seconds since the Vana'diel epoch x 60: LandSandBoat's `0x063_miscdata_status_icons.cpp` writes (seconds left + `earth_time::vanadiel_timestamp()`) * 60, and `vanadiel_timestamp` counts Earth seconds since the epoch (`common/earth_time.h`), so `now` is `VanaClock.GetEarthSecondsSinceEpoch` on the session's server clock (an earlier note here read it as Vana'diel seconds, 25 times too fast; corrected for [#17](https://github.com/jimmy58663/GordianXI/issues/17)). Not yet checked against a live capture. The Unity layouts (`0x07`) come from LSB only (XiPackets marks them as not reversed). Verify with `dotnet test tests/Gordian.Core.Tests --filter ProgressionPacketTests`.

### C2S 0x01A action kinds

`CombatPacketBuilder.BuildAction(kind, targetId, targetIndex, param)` writes every 0x01A: UniqueNo, ActIndex, ActionID, then `param` as ActionBuf[0] and the other three words zeroed (CastMagic adds its ground-target offset). The per-kind builders call it; `CombatPacketModule.RequestActionAsync` sends any kind. Layout from XiPackets `world/client/0x001A`; server behaviour from LandSandBoat `c2s/0x01a_action.cpp`.

- **ChangeTarget (0x0F):** `/attack` (or the command menu's Attack) on a different target while engaged sends ChangeTarget instead of Attack and moves the engagement.
- **Fish (0x0E), Sprint (0x16), ChocoboDig (0x11), Blockaid (0x18):** `/fish`, `/sprint`, `/dig`, `/blockaid [on|off]` (bare = toggle; ActionBuf[0] 0 off, 1 on, 2 toggle) target the player. LandSandBoat does nothing for Sprint.
- **Help (0x05):** `/callforhelp` (`/cfh`) against the engaged monster (else the current target). Retail's command is `/help`, which this client uses for command discovery.
- **MonsterSkill (0x19):** `/monsterskill <id> [target]` (`/ms`); the id is sent as given (retail sends the ability id less 1536).
- **Trust release (Talk, 0x00):** `/refa <name|all>` (`/returnfaith`; no argument = the current target). The player's Trusts are the party members whose entity is a Trust; one Talk is sent per Trust with ActionBuf[0] = 1 for a single release, or 0, 1, 2... for `all`. LandSandBoat ignores the value. Trusts are told apart by `Flags3.TrustFlag` in 0x00E (LSB writes `0x45` into packet byte 0x28 for every Trust), which makes the entity `EntityType.Trust` and keeps it so.
- **Death menus (HomepointMenu 0x0B, RaiseMenu 0x0D, TractorMenu 0x13; #103):** the answers of a dead character, UniqueNo / ActIndex = the character's own, ActionBuf[0] = `StatusId`: HomepointMenu 0 returns to the home point (1 and 2 are Monstrosity's Cancel and Retry, not sent), RaiseMenu and TractorMenu 0 accept, 1 decline (XiPackets `world/client/0x001A`). LandSandBoat rejects all three unless the character is dead, ignores RaiseMenu without a pending Raise, drops the Raise on a decline (it must be cast again), and moves the corpse to the caster on an accepted Tractor (a zone change into the same zone, still dead). The offers arrive as S2C **0x0F9** `GP_SERV_COMMAND_RES` (payload 0 u32 UniqueNo, 4 u16 ActIndex, 6 u16 type: 0 home point only, 1 Raise, 2 Tractor; XiPackets `world/server/0x00F9`, LSB `s2c/0x0f9_res.h`), kept in `LocalPlayerState.DeathMenu` (cleared when answered, on type 0, or when the character stops being dead) with `DeathMenuChanged`. LSB sends type 1 when Raise lands (`CLuaBaseEntity::sendRaise`) and about 12 s after a death with Reraise (`CDeathState::Update`), type 2 from `sendTractor`; a dead character is force-homepointed by the server after an hour (`CDeathState`). Senders: `CombatPacketModule.RequestDeathMenuAsync`, `PlayerActionService.HomePointAsync` / `AnswerDeathOfferAsync`, the dead window ([stock-ui.md](../ui/stock-ui.md#dead-window-103)) and `/homepoint`, `/acceptraise [decline]`, `/accepttractor [decline]` (GordianXI commands, not retail ones). **Beyond XiPackets:** what retail puts in UniqueNo / ActIndex for these kinds is not documented; the character's own are sent and LSB does not read them.
- **Dig:** after a ChocoboDig LandSandBoat spends the greens and sends S2C **0x02F** (`TarUniqueNo`, `TarActIndex`, `Flags`) for the digger. For the local player the client answers with C2S **0x063** (UniqueNo, `para` 0, ActIndex, `mode` 0x11); retail sends it when the dig animation ends, and since the animation is not played yet it goes at once. LSB ignores 0x063. Layouts from XiPackets `world/server/0x002F` and `world/client/0x0063`.

Not checked against a retail capture. Verify with `dotnet test tests/Gordian.Core.Tests --filter "FullyQualifiedName~DeathFlowTests|FullyQualifiedName~BuildAction|FullyQualifiedName~Dig|FullyQualifiedName~Refa|FullyQualifiedName~ChangeTarget|FullyQualifiedName~SelfActions|FullyQualifiedName~TrustFlag"`.

### C2S 0x05D emotes

`CombatPacketBuilder.BuildEmoteRequest` writes UniqueNo, ActIndex, `Number` (the emote id), `Mode` (0 both, 1 text, 2 motion; `EmoteMode`) and `Param`. The server echoes it to everyone in range, us included, as S2C 0x05A, which prints the line and plays the motion (see [Messages and event parameters](#messages-and-event-parameters-110)); `/emote` prints nothing of its own. `EmoteId` holds the protocol ids: 0 point, 1 bow, 2 salute ... 12 cheer, 13 clap ... 38 shocked, 43 hurray (`Param` 1), 44 toss; there is no "none" id. `ChatCommandRouter` routes `/<emote> [target]` and `/em <emote> [target]` for the emotes every character has; the dances, `/bell`, `/jobemote` and `/aim` need a `Param` and are not routed. `/sit` is not an emote (C2S 0x0EA, [#111](https://github.com/jimmy58663/GordianXI/issues/111)). Event opcode 0x6E plays the same ids. Ids from XiPackets `world/client/0x005D` and LandSandBoat `src/map/enums/emote.h` ([#178](https://github.com/jimmy58663/GordianXI/issues/178): the client used to number them from its own list, so `/cheer` sent bow). Verify with `dotnet test tests/Gordian.Core.Tests --filter "FullyQualifiedName~Emote"`.

### Treasure pool (S2C 0x0D2 / 0x0D3, C2S 0x041 / 0x042)

`TreasurePacketModule` (`TreasurePackets.cs`, `TreasurePacketModule.cs`) fills `TreasurePoolState` (`session.Treasure`, 10 slots). Layouts from XiPackets `world/server/0x00D2`, `0x00D3` and `world/client/0x0041`, `0x0042`; the values LandSandBoat sends from `s2c/0x0d2_trophy_list.cpp` and `0x0d3_trophy_solution.*`.

- **0x0D2** puts an item in `Slot` (a re-send after a zone change carries the local entry, lot and current leader). A packet with only `Gold` fills no slot. `TreasureFound` is raised for the log either way.
- **0x0D3** with `JudgeFlg` 0 updates the leader (`LootUniqueNo`, name, lot) and, when `EntryUniqueNo` is the local player, the local entry (`EntryFlg` 1 = lot, 0 = pass; `EntryPoint` = the roll). `JudgeFlg` 1 = won, 2 = winner cannot take it, 3 and up = silent clear; every judgement empties the slot. LandSandBoat sends 1 = Win, 2 = WinError, 3 = Lost.
- **C2S 0x041** carries the slot and the first empty bag slot (from 1) the client assumes; LandSandBoat ignores the second. **0x042** is the slot only (the 6 byte struct goes out as 8).
- **Commands:** `/lot [slot]` and `/pass [slot]` (slot 0-9; without one, every slot you have not entered). The result arrives as 0x0D3; the local state is not touched on send.
- **Message log** (`StockUiTreasure`, System channel): "You find a fire crystal on the Goblin." ("in the" for a container, no "the" for a named dropper, gil first), "X's lot for the fire crystal: N points.", "You obtain a fire crystal." / "X obtains ...", and the requirement failure plus "... lost." Passes and silent clears print nothing. The wording is from the XiPackets notes, not a capture. The local winner is `LootUniqueNo` 0 or the local id; LandSandBoat sends the real id, so this is untested against retail's own use of the field.
- A zone change empties the pool.

### Search (cache) server (#119)

The search server runs next to the world server on its own TCP port (LSB `SEARCH_PORT`, 54002) and answers what takes a long time: Auction House item lists and price histories, `/sea`, search comments and the party and linkshell member lists. `SearchClient` opens a connection per request, sends one frame and reads the answers until the final flag, so a request never blocks the UDP session. `SearchService` (`CharacterSession.Search`) holds the address and the answers (`SearchState`).

**Address.** `SearchService.ConfigureDefault` is called when the session connects: the host of the world connection and port 54002, unless `Configure(host, port)` was called (a server that runs the search server elsewhere; nothing in the login flow or the server profile carries a search address yet, so profiles for such servers need a field).

**Frame.** `[u16 total length][u16 0]["IXFF"][payload][MD5 of the payload, 16][key seed, u32]`. The payload and the hash are enciphered with the world server's Blowfish (key schedule and ECB; `LegacyBlowfishCryptoSuite`) in 8-byte blocks from byte 8, as many whole blocks as fit before the seed; the hash is of the plain payload. The key is the MD5 of a string, not the world session key: 16 constant bytes (`SearchFrame`), then the 4-byte seed the client chose (the last 4 bytes of its frame), and for answers also the 4 bytes of the request's plain payload just before its hash. A request is keyed by `MD5(constant + seed)` and every answer to it by `MD5(constant + seed + payload tail)`. The payload of a request pads to a multiple of 8 bytes; LSB's answers keep the 4-byte seed and end with their hash, with 8 extra bytes of padding in front of it for the Auction House answers.

**Payloads.** A request's bytes 0x08-0x0A and 0x0C-0x0F are ignored by LSB (we send the length and zeros); the type is at 0x0B. An answer: 0x08 the data length, 0x0A bit 7 on the last packet, 0x0B the type with bit 7 set, 0x0E the total result count. The player entries are bit streams, most significant bit first, which is how LSB's `packBitsLE` writes them and its `unpackBitsLE` reads requests. The per-type layouts are in [packets.md](packets.md#search-cache-server).

**`/sea [all] [job] [level] [party] [friend] [name]`.** `PlayerActionService.ParseSearchQuery`: `all` searches every zone (type 0), otherwise the current zone (type 3); a three-letter job code, a level or range (`75`, `70-75`, `lv75`), `party` (players seeking a party) and `friend` set filters; the first other word is the name. The result is in `SearchState.LastSearch`.

**Findings.** LSB answers a search comment request with nothing when the comment is empty, so the request runs out its wait (a timeout is not an error). The party list needs the party's group id from the world server (C2S 0x078 / S2C 0x0E1); the linkshell list needs the id in the first word of the worn linkshell item's extra data. LSB's Auction House history packet writes the item's listing counts into the price slot of its header; the sales list (price, date, seller, buyer) is the useful part.

**To verify against a live server.** The frame, key derivation and every layout are from reading LSB; no live search server was available. Check in game: open a connection and `/sea all` (a non-empty result proves the frame, the keys and the player entry layout); `GetAuctionListAsync(1)` and a history for a listed item; the party list in a party; the linkshell list with a linkshell equipped; and `/sea` with a name, a job and a level range (the request bit stream).


## Crafting and guild shops (#112)

`CraftingPacketModule` owns the synthesis and recipe packets; `CraftingState` holds the last results and the synthesis lock and raises events; `CharacterSession` prints the results through `CraftingLog` and the guild answers through `GuildShopLog`; `SynthesisAnimationController` plays the animation. The guild shop requests live in `InventoryPacketModule` (`BuyGuildItemAsync`, `RequestGuildBuyListAsync`, `SellGuildItemAsync`, `RequestGuildSellListAsync`) because the S2C answers already fill `InventoryState`.

- **Synthesis flow.** C2S 0x096, then S2C 0x030 (animation start: `EffectNum` is the crystal element 0x10-0x17, fixed in #100; `Type` is the result LSB already computed), then 0x06F to the crafter and 0x070 to those nearby, then the skill-up messages (S2C 0x029). LSB makes the client wait 15 s between synths and refuses a crystal that is not in the named inventory slot.
- **Synthesis lock (in-game test 2026-10-07).** Retail refuses commands during a synthesis with "You cannot use that command during synthesis." (pink) and sends nothing; a macro pressed three times prints it three times. `/synth` does the same while `CraftingState.IsSynthesizing` (from the send, 4 s to be confirmed by S2C 0x030, then until S2C 0x06F, 60 s at most). Other commands are not locked yet. A request the server refuses before it starts (LSB's "You must wait longer to perform that action.", S2C 0x029 message 94) simply prints that line.
- **0x096 packing.** Every ingredient is one item of one slot: a stack of four used in one synth takes four of the eight entries, and the crystal is not counted. `/synth 2 5 5 6` is crystal in slot 2, two items from slot 5, one from slot 6. The packet is sent as 36 bytes because the 34-byte struct is not word aligned (header size field 9).
- **Message wording.** Compared with a retail capture (2026-10-07). "You synthesized a ponze of shell powder." / "A seashell was lost." come from the system message table `ROM/27/76` (file id 7031): 160-163 own "synthesized" by grade, 164 "... was lost", 165 / 166 guild buy, 167 / 168 guild sell, 200-203 / 204 / 205 the same for other players with the crafter's name as string parameter 2. The messages' number codes are 0x04 (count) and 0x2A (count, item) / 0x27 (item): `EventMessageFormatter` prints a 0x04 of 1 as the article "a" / "an" when the context asks (`IEventMessageContext.CountOneIsArticle`), which the retail capture needs. The result lines ("Synthesis canceled. That combination of materials cannot be synthesized.", ...) are in the string table `ROM/0/49` (file id 49, plain NUL separated strings after an offset table; in the order bad recipe, failed, failed, interrupted, skill too low, canceled, "Too many materials.", rare item) and match XiPackets word for word. Not found in any table of the retail DATs scanned (file ids 6000-8000 and 49): "You cannot use that command during synthesis." (kept hard-coded, from the capture).
- **0x06F `Result`.** 0x00 and 0x0C succeed; 0x01 failed (crystal lost); 0x02 and 0x0E interrupted (crystal and materials lost); 0x03 bad recipe; 0x04 canceled; 0x06 skill too low; 0x07 rare item; 0x0D wait longer. Any other id is a failure that lost the crystal (retail's rule, kept by `CraftingLog`). `Grade` is the retail message index minus 160 (0x06F) or 200 (0x070): 0-3 "synthesized", 4 "lost", -1 failure.
- **Skill-ups.** The server also sends them as S2C 0x029 messages 38 (`Param` the skill id 49-56 for crafts, `Value` the gain in tenths) and 53 (reaches level `Value`); retail words them "Gemini's bonecraft skill rises 0.1 points." (capture 2026-10-07), which `CombatLogFormatter` now does with `SkillName` (the table of skill ids is from LandSandBoat's `SkillType`; the gain formats as tenths). Before this the line read "Knot's skill rises by 54 points." (the skill id printed as a gain). `UpKind` / `UpLevel` in S2C 0x06F stay decoded in `SynthesisOutcome.SkillUps` and are not printed, so the line does not appear twice. Since #335 every 0x029 line is worded from the basic message table, file id 7027 (`ROM/27/72`): message 38 there is "`{target}'s {05 00 skill} skill rises {7F 9B 01} points.`", so the skill name and the 0.1 value come from the table's codes ([message-codes.md](../events/message-codes.md#basic-message-table-335)); the hand-written text stays as the fallback.
- **Synthesis animation ([#315](https://github.com/jimmy58663/GordianXI/issues/315)).** S2C 0x030 sets `CraftAnimationEffect`, `CraftParam`, `StatusServer` and `CraftTimer` on the entity (XiPackets), and LSB also sets the crafter's status to 44 (`xi.animation.SYNTH`) in 0x037 / 0x00D for the whole synthesis. The body: status 44 plays the Healing posture (`RestPosture.StatusSynthesis`: `res0` sits down, `res2` stands up when the status leaves 44), and `SynthesisAnimationController` puts 0x030's `Status` on the crafter's entity so it sits with the effect. Evidence: the maintainer's retail video `Synth_Wind_Fire_Lightning_Breaks.mp4` (2026-10-16/17, a Tarutaru): a short sit into a seated pose with the hands at the chest, about 2.4 s still, about 11 s of effect, the result, about 1.4 s seated, then a roll back onto the back and up, about 16 s in all; Tarutaru's `rx2` is that roll (the head joint 0.12 yalms high and 0.59 behind the root at 0.4-0.5 s; `RestPostureRealDataTests.TarutaruStandUp_RocksBackOntoItsBack_AsRetailsSynthesisEnds`). The crystal and the element effect are the element's file **4912 + `EffectNum`** (ROM/16/56-63, directory `cris`, textures `cris_aq` water, `cris_ar` wind, `cris_ig` fire, `cris_tr` earth, `cris_th` lightning, `cris_ic` ice, `cris_lt` light, `cris_dk` dark: LandSandBoat's `SynthesisEffect` order; 4912 starts the item use effects, 4912 / 4913 the antidote's `doku`). Each holds 21-28 generators (the crystal `cri0` / `cri1`, rings `rng0`-`rng3`, rays `sen0` / `sen1`, motes, and the element's own: fire `fir?`, lightning `kyu0` / `kyu1` the sphere), five sounds, and the routines `frst` (630 ticks: plays the crafter's `ri0?`, the right hand up with the crystal, held; starts `strt`, the crystal and the intro, at 20 and `loop` at 180, 270, 360, 450, 540), the endings `ednn` (success: rays, rings, flash), `edmm` (break: `cri1` again, then `san3` scatters it, no rays), `edxx` (high quality) and `stcr` (stops it all). The file's `main` links a template name (`ed x`) the client fills in; its test routines `s000` / `t000` run `frst`, an ending at tick 630, then `stcr`. GordianXI (`ActionMotionLibrary.ResolveSynthesis`, `SynthesisAnimationController`) builds that `main` with the ending for `Type` (0 success `ednn`, 1 break `edmm`, 2-4 high quality `edxx`) and plays it on the crafter as an action presentation 2 s after 0x030 (PROVISIONAL delay: the video shows the crystal about 2.4 s after the crafter is seated), the body holding `ri0?` until the ending is over (`ActionAsset.HoldsBodyToEnd`). Found 2026-10-18 by texture name (a scan of every section of the install); the eight files ROM/160/19-26 (51371-51378) carry the same endings named `ng00` / `ok00` / `okex` with `kill` and an `rx2?` stand-up, use unknown (NPC or event crafting). **Beyond XiPackets, xi-tools and LandSandBoat.** C2S 0x059 at the end is still unsent (LSB ignores it).
- **0x031 layout.** **Differs from XiPackets:** its generic layout puts `Type` at 0x2C, but its per-mode layouts and LandSandBoat put it at 0x30 (after 8 ingredient ids and 8 counts, or after 16 list ids); GordianXI reads 0x30. A list holds 16 items; `itemnum_next` (0x32) is the first item of the next page and is what makes retail offer "View more recipes."
- **Guild shop precondition.** LSB answers C2S 0x0AA-0x0AD only for a character whose `guildShopNpc_` is set, which `xi.guildShops.onTrigger` does when the character **talks to the guild shop NPC** and the NPC opens the shop (`player:openGuildShop`, S2C 0x086). Without that the requests are silently dropped (their validators fail), so `/guild buylist` right after login logs only the "requested" line. Test: talk to the guild NPC (it must be inside its hours: S2C 0x086 prints "[Guild] The guild shop is open." or when it will open), then `/guild buylist`, `/guild selllist`, `/guild buy <item id> [n]`, `/guild sell <slot> [n]`. Answers print to the log: the lists ("[Guild] The guild sells N items:" with name, item id, price, stock/max), and "You buy a ... from the guild." / "You sell ... to the guild." or the failure text. A purchase at most a stack (LSB turns a larger count away with the generic failure text).
- **Windows ([#330](https://github.com/jimmy58663/GordianXI/issues/330)).** The Synthesis windows send C2S 0x096 and the guild shop window C2S 0x0AA-0x0AD ([stock-ui.md](../ui/stock-ui.md#synthesis-and-guild-shop-windows-330)); a successful synthesis is kept in the character's History (`SynthesisHistory`, from `CraftingState.LastRequest`).
- **Not done.** Recipes: retail sends C2S 0x058 from the guild NPCs' event scripts (event opcode 0x8C, which waits for S2C 0x031 and then lists the recipes in the event's menu); GordianXI steps over 0x8C, so nothing sends 0x058 beyond `PlayerActionService.RequestRecipeAsync` ([stock-ui.md](../ui/stock-ui.md#synthesis-and-guild-shop-windows-330)). C2S 0x059 `effectpara` at the end of the animation is still unsent.

## Scheduler packets (#109)

`SchedulerPacketModule` decodes S2C 0x038 (`GP_SERV_COMMAND_SCHEDULOR`) and 0x03A (`GP_SERV_COMMAND_MAGICSCHEDULOR`) into `SchedulerState`, which `CharacterSession.Scheduler` exposes. The requests are bounded (64 each), kept in arrival order, and dropped on a zone change. This is **decode only**: nothing plays them. The playback runtime (effect routines, #9, #10, #227, #232, #233) is what should call `TakeActorSchedulers` / `TakeMagicSchedulers`, or subscribe to `ActorSchedulerPosted` / `MagicSchedulerPosted`.

- **0x038** carries the caster and target (server id and index) and a FourCC naming a script in the caster's animation DATs. The layout is that of 0x039 (`S2C_0x039_MapSchedulor`), which instead names a routine of the zone DAT. LandSandBoat's keys: `kesu` fades an entity out (despawn state, battlefield exit), `hitl` is the sweating animation of fishing, and the Trust and gambit code sends animation strings straight from Lua, so an unknown key is normal. A key that is not four printable ASCII characters decodes with an empty `Routine` but keeps `RoutineId`.
- **0x03A** names an effect script by number (`FileNumber`) with a family `Type` (0 cast spell, 1 item, 2 ability, 6 weapon skill, 9 monster skill, 3 / 4 event animations and banners, the rest unknown). LandSandBoat only sends it from `independentAnimation(target, animId, mode)`. Which DAT `FileNumber` indexes (the spell / ability effect files that 0x028 actions use, or a separate table) is not yet established; the playback work has to settle that.
- Seen in logs: 0x038 once per session so far, with no 0x03A.
- **Playback ([#311](https://github.com/jimmy58663/GordianXI/issues/311), 2026-10-18, awaits the in-game test).** `SchedulerPlayback` (built by `PacketParser`, subscribed to `ActorSchedulerPosted` / `MagicSchedulerPosted`) plays each request on the network thread as it arrives; the viewport plays the effects (`WorldState.PostActorEffect`, dropped on a zone change). Details and evidence in [entities-and-animation.md](../world/entities-and-animation.md#models-and-equipment-phase-5c) (*Scheduler packets*, *Routine colour*). The fileNum reading for 0x03A types 0 / 2 / 6 / 9 is *inference*; the other types play nothing.
